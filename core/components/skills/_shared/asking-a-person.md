# Asking a Person

The rule for how a play, a skill or an agent asks a person a question — at a checkpoint, in a
draft the person approves, or in a brief that ends with questions. It does not say *what* to
ask; it says how each question is shown.

This file is not memory. The install lays it beside the installed skills, at
`_shared/asking-a-person.md`, and each part that asks a person reads it there: the plays
`edit-ontology` and `shape-slice`, the skills `author-product-ontology`, `find-slice-gaps` and
`author-slice-brief`, and the `product-os-keeper` agent.

## The opening

Before the first question, say in two or three plain sentences what the person decides, and
what happens with their answer. The person must know what is at stake before they read a
question.

## Each question

Each question asks one thing. When a question has an "and" in it, make it two questions.

Each question shows four parts, in this order:

1. **Question** — the one thing the person decides, in plain words.
2. **Answer** — what the model or the proposal gives back: a real answer, in general words.
   Never "the place where X is kept" or "see the file". If there is no answer yet, write the
   proposed answer and say that it is proposed.
3. **Why it matters** — what goes wrong, or what changes, if the answer is wrong.
4. **Example** — several examples from different domains, never just one (for example a
   clinic, a shop and a bank). One example pulls the answer into that one domain.

## Read it back

Read each question back with no context: not the issue, not the earlier questions, not the
files. Ask it only when a stranger could answer it. If a stranger could not, rewrite it.

## Words

- Plain English, in the style of ASD-STE100: short sentences, one idea each, common words.
- Personas only (for example "the clinic manager"). Never a real person's name.

## Checkpoints

A play's checkpoint shows its draft in this format. A draft that does not follow this rule is
not ready to show.
