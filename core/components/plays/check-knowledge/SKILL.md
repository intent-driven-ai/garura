# check-knowledge

Write the brief the loop shows the person: what we understood, what we built, where the gaps
are — each with its context and our proposed answer — so one reply confirms or corrects it.

**Pipeline position: none.** A member play the Shared Loop Run runs when a loop must ask
(R5b), last of `/search-knowledge` → `/research-knowledge` → `/check-knowledge`; it opens and
lands nothing.

## Role

You are the orchestrator. You run the check as a script, and hand the judgment — writing the
brief — to the `knowledge-builder` agent through a JSON contract over files on disk. You ask the
person nothing and decide nothing: the loop shows the brief and records the reply. You never
write the product model.

**Agent boundaries:**

| Agent | Domain | Skills it invokes | Phases |
|-------|--------|-------------------|--------|
| `knowledge-builder` | The knowledge a loop's round found missing | `author-knowledge-brief` | Brief |

`knowledge-builder` is the single **domain agent**; it lists the waiting knowledge pages through
the memory tool's `updates`. Everything else is a script.

## Workflow

### Phase: Brief

**Step 1 — Write the brief** · Owner: `knowledge-builder` · Depends on: pre-flight

    { "task":    "review: write the brief the loop shows the person",
      "inputs":  { "search": "<search>/search.json", "build": "<build>/build.json",
                   "run": "<the loop's working folder>", "issue": "<issue>",
                   "audience": "<who gave the loop its input — for Discovery, who shared the prototype>",
                   "check_script": "<play-dir>/scripts/check_brief.py",
                   "renderer": "<skills>/author-knowledge-brief/scripts/render_brief.py" },
      "outputs": { "brief": "<working>/brief.json", "brief_md": "<working>/brief.md",
                   "check_report": "<working>/brief-check.json" },
      "task_id": "check-knowledge" }

The agent reads the product model and the run for what we understood and what we built, lists
the waiting knowledge pages through the memory tool, and has `author-knowledge-brief` write the
brief: a few sentences each for understood and built; at most seven gaps, related proposals
sharing a theme, each with its context and our proposed answer; every settled point with why;
each page with what it says, its sources and our recommendation; the prototype notes counted
and pointed to. The skill writes the content into `brief.json` and renders `brief.md` from it
with `render_brief.py`; nobody writes `brief.md` by hand. `<skills>` is the folder the
installed skills sit in (`.claude/skills/` for Claude Code, `.agents/skills/` for Codex).
**SE-1 (F1/C1):** `brief.json` has `understood` and `built`.
**SE-2 (F2/C2):** every `proposal` group of `build.json` is in exactly one gap; at most seven
gaps; each has context and a proposed answer, none a question.
**SE-3 (F3/C3):** every update the memory tool lists as waiting for the issue is a page with its
sources and a recommendation; every `settled` build group is shown once with why;
`prototype_notes.count` equals the build's notes.

### Phase: Check

**Step 2 — Check the brief** · Owner: play (script) · Depends on: Step 1

```bash
python3 scripts/check_brief.py --brief <working>/brief.json --brief-md <working>/brief.md \
    --build <build>/build.json --issue <issue> \
    --memory-tool .garura/core/tools/memory/memory.py \
    --renderer <skills>/author-knowledge-brief/scripts/render_brief.py \
    --out <working>/brief-check.json
```

Exit 0 — clean. Otherwise send the report back to Step 1 (at most twice), then close HALTED.
**SE-4 (F4/C4):** the run asked the person nothing and decided no memory update — the memory
tool lists the same waiting updates as at the start.
**SE-5 (F5/C5):** `run.json` reads `in_loop: true`; every file this run wrote is under
`{stm_base}<issue>/`; `git status` shows no change under the product model.
**SE-6 (F6/C6):** `brief-check.json` reads `ok: true` from a run that passed `--renderer`, so
`brief.md` equals `render_brief.py`'s output from `brief.json`.

The loop then shows `brief.md` and records the person's reply with this play's
`scripts/record_review.py` (Shared Loop Run, R5b).

### Phase: Scenario Validation

**Step 3 — Scenario evals** · Owner: play · Depends on: Step 2
- **SCE-1 (S1 — Discovery loop, a round with many gaps):** `brief-check.json` reads `ok: true`
  with `gaps` at most 7.
- **SCE-2 (S2 — Discovery loop, the person agrees):** after the loop records a "yes",
  `person-answers-round-<n>.json` holds one answer per gap with `from: person` (checked by the
  loop, after this play).

## Recovery

| For | Trigger | Direction | Handoff |
|-----|---------|-----------|---------|
| F1 | no understood or built | write them from the run and the model | autonomous |
| F2 | a proposal missing or doubled, too many gaps, or a gap without context or proposal | regroup the proposals by theme; give each gap its context and our answer | autonomous |
| F3 | a page missing or without sources or a recommendation, a settled point not shown, or prototype notes asked | list every waiting page with its sources and a recommendation; show every settled point with why; point to the notes | autonomous |
| F4 | the play asked, waited or decided | stop; leave asking to the loop and deciding to the person | human |
| F5 | no loop contract, a write outside the issue, or a model write | halt; move the record under the loop's issue; undo the model write | human |
| F6 | `brief.md` differs from the rendering of `brief.json` | write the content into `brief.json` and render `brief.md` with `render_brief.py` | autonomous |

## Pause and Resume

The run's working folder is per round (`context/check-knowledge/round-<n>/`). On entry, skip a
step whose output exists and checks clean; a brief already written is not written again.
