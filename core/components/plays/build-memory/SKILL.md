# build-memory

Turn a drive round's open questions into memory: answers from the drive's sources and from
memory, researched knowledge pages a person approves, prototype feedback, and a few questions
only the person can answer.

**Pipeline position: none.** A member play the Shared Drive Run runs inside a drive's rounds
(R5c); it opens and lands nothing.

## Role

You are the orchestrator. You run the grouping and the checks as scripts, and hand the
judgment — confirming the groups, answering from the sources and memory, drafting knowledge
pages, writing the person's few questions — to the `memory-builder` agent through a JSON
contract over files on disk. You never decide, apply or promote a memory update, and you never
write the product model.

**Agent boundaries:**

| Agent | Domain | Skills it invokes | Phases |
|-------|--------|-------------------|--------|
| `memory-builder` | Close each group of open questions the cheapest honest way: the drive's sources again, memory, research as a memory update, the person | `answer-from-source`, `draft-knowledge-page` | Build |

`memory-builder` is the single **domain agent**. Everything else is a script.

## Workflow

### Phase: Group

**Step 1 — Group the round's open questions** · Owner: play (script) · Depends on: pre-flight

```bash
python3 scripts/group_questions.py --review-dir "<review_dir>" \
    --issue-dir "{stm_base}<issue>/" --out <working>/question-groups.json
```

**SE-1 (F1/C1):** `question-groups.json` lists every open question of the round once — every
`open-<play>.json` question and every waiting memory update — and the questions it names as one
topic (the same proof, the same speed target) share a group.

### Phase: Build

**Step 2 — Build the memory** · Owner: `memory-builder` · Depends on: Step 1

    { "task":    "build the memory this round of the drive found missing",
      "inputs":  { "groups": "<working>/question-groups.json",
                   "sources": ["<the drive's Source evidence folders — for a prototype: views, journeys, the page>"],
                   "issue": "<issue>",
                   "check_script": "<play-dir>/scripts/check_memory_build.py" },
      "outputs": { "build": "<working>/memory-build.json",
                   "check_report": "<working>/memory-build-check.json" },
      "task_id": "build-memory" }

The agent confirms the groups by judgment, gives each one plain question, and closes each in
the fixed order: the sources again (`answer-from-source`, quoted) → memory (through the memory
tool, traced) → research (`draft-knowledge-page`, a memory update waiting for a person) → the
person (once, in their words, 1–3 examples). A screen state the prototype lacks becomes
prototype feedback.
**SE-2 (F2/C2):** every group closed by `source` has a quote and its file; every group closed
by `memory` has its trace; no group closed by `person` or `update` is answered by the sources —
the agent's `source-answers.json` marks it `not-shown`.
**SE-3 (F3/C3):** every group closed by `update` names a memory update in the issue's
short-term memory with status `waiting`; no update was decided, applied or promoted in this run.
**SE-4 (F4/C4):** every group the agent's `source-answers.json` marks `should-show` is closed by
`prototype-feedback`.
**SE-5 (F5/C5):** every group closed by `person` has its plain question and 1–3 examples, and no
two such groups ask the same thing.

### Phase: Check

**Step 3 — Check the build** · Owner: play (script) · Depends on: Step 2

```bash
python3 scripts/check_memory_build.py --build <working>/memory-build.json \
    --groups <working>/question-groups.json --issue-dir "{stm_base}<issue>/" \
    --out <working>/memory-build-check.json
```

Exit 0 — clean. Otherwise send the report back to Step 2 (at most twice), then close HALTED.
**SE-6 (F6/C6):** `run.json` reads `in_drive: true`; every file this run wrote is under
`{stm_base}<issue>/`; `git status` shows no change under the product model.

### Phase: Scenario Validation

**Step 4 — Scenario evals** · Owner: play · Depends on: Step 3
- **SCE-1 (S1 — Kickoff drive, many repeated questions):** `memory-build-check.json` reads
  `ok: true`, its `asked_of_person` is smaller than its `questions`, and every question id is in
  exactly one group.
- **SCE-2 (S2 — Kickoff drive, an answer the prototype holds):** a group the prototype answers
  reads `closed_by: source`, with a quote and its file.
- **SCE-3 (S3 — Kickoff drive, knowledge no screen shows):** a group about a standard or rule
  reads `closed_by: update`, and that update waits in the issue's short-term memory.

## Recovery

| For | Trigger | Direction | Handoff |
|-----|---------|-----------|---------|
| F1 | a question in no group or two | regroup from `group_questions.py`'s output and confirm by judgment; re-run the check | autonomous |
| F2 | a group asked or researched while the source or memory answers it, or an answer without its quote or trace | re-run `answer-from-source` and the memory lookup for it; quote or trace the answer | autonomous |
| F3 | a researched answer used before approval, or an update decided, applied or promoted by the play | undo the use; leave the update waiting for a person | human |
| F4 | a missing screen state asked as a question | move it to prototype feedback | autonomous |
| F5 | a question asked twice, in Garura's words, or without examples | merge it, rewrite it for the person, add 1–3 examples from the source and memory | autonomous |
| F6 | no drive contract, a write outside the issue, or a product-model write | halt; move the record under the drive's issue; undo the model write | human |

## Pause and Resume

The run's working folder is per round (`context/build-memory/round-<n>/`). On entry, skip a
step whose output exists and checks clean; a round already built is not built again.
