# update-plan

A working session on one plan. The person gives instructions in their own words; the play works
out what each one changes, checks it against the plan's rules, and keeps a running list. On one
plain "approved", the whole list lands at once — the product model, GitHub and the plan file —
on the plan's own branch, and a check proves they agree and nothing else changed.

## Compiled From

This play was compiled from the update-plan ICE (`reference/ice.md`) by create-play (#730, with
#931's model part; feature #720, plan 717). Intent defines constraints (C1–C12) and failure
conditions (F1–F12); the expectation defines success scenarios (S1–S7), a Done means (D1–D3,
baked to `stop-condition.yaml`), and one recovery entry per failure condition.
To modify this play, update `reference/ice.md` and recompile with edit-play.
Do NOT edit this file manually — it is a compiled artifact.

## Role

You are the orchestrator. You own the session, the step order and the one question at the end.
You do no domain work: what an instruction means is `author-plan-changes`' judgment (through
`project-orchestrator`); where a new feature belongs and its page are the model's (through
`product-os-keeper`); every fixed rule — the plan's rules, the list, the answer, the writes'
order, the plan file's lines, the agreement, the commit, the screens — is a script. You show
each screen exactly as `render_screen.py` prints it.

**Forbidden:** guessing a plan or making one (C1/F1); switching away from uncommitted work, or
writing on any branch but the plan's beyond the plan-branch step (C2/F2); any write to GitHub, the
model or a plan file before `record_answer.py verify` exits 0, other than the plan-branch step
(C5/F3); adding to the list an entry the person did not ask for, or a status or direction no
instruction named (C8/F7); a tracker or model write outside the two sub-agents' skills (C9/F8);
wording a screen yourself (C10/F9); writing in any plan's `evals/` folder (C11/F10); running a
change play, merging a branch, or touching code (C7).

**Agent boundaries:**

| Agent | Domain | Skills it invokes | Phases |
|-------|--------|-------------------|--------|
| `template-manager` | Load the plan-update, plan-view and close templates | — | Prepare, Close |
| `project-orchestrator` | Read the plan's issues; turn an instruction into list entries; make the approved tracker writes | `track-plan-changes`, `author-plan-changes` | Prepare, Session, Landing |
| `product-os-keeper` | Place a new feature (its capability, the slice the plan holds) and draft its thin ICE; on approval write its page, its model entry with both thin marks and its place in the slice | `find-work-placement`, `enrich-grounding`, `link-model-part` | Session, Landing |

`template-manager` and `project-orchestrator` are **utility agents**. `product-os-keeper` is the
one **domain agent**, dispatched only for a new feature.

## Pre-flight

| Check | Constraint | Action on Failure |
|-------|-----------|-------------------|
| Resolve config (`.garura/core/config.yaml`) via `scripts/preflight.py` | — | Hard halt |
| One plan, via `scripts/find_plan.py find` | C1 | Exit 1: show the `not_found` screen and stop — never guess |
| The plan tool's plan-branch script is installed (`.garura/core/tools/plan/plan_branch.py`) | C2 | Hard halt |

```
git branch --show-current
git status --porcelain > <tmp>/porcelain.txt
python3 scripts/preflight.py --play update-plan --config .garura/core/config.yaml \
    --branch "$(git branch --show-current)" --porcelain-file <tmp>/porcelain.txt
test -f .garura/core/tools/plan/plan_branch.py || { echo "the plan tool is not installed — halt"; exit 1; }
```

`<plans>` is `plans.base-path` from config, else `.garura/project/plans/`. The working folder is
`<working> = ${stm_base}_plans/update-plan/<id>/`, once the plan is known; until then
`${stm_base}_plans/update-plan/_find/`. Right after, record the session identity stamp's start
marker (#463 — soft-fail, never a halt):

```
python3 scripts/session_stamp.py --phase start \
    --marker "${stm_base}_plans/update-plan/session-stamp-update-plan.json" \
    --cwd "$(pwd)" --branch "$(git branch --show-current)"
```

## Task DAG

Create ALL tasks immediately after pre-flight — before any domain work.

```
[T1]  Load the templates                    blockedBy: []
[T2]  Find the plan                         blockedBy: [T1]
[T3]  Get onto the plan's branch            blockedBy: [T2]
[T4]  Read the plan's issues; the list      blockedBy: [T3]
[T5]  Take instructions                     blockedBy: [T4]
[T6]  Ask: approved or rejected             blockedBy: [T5]
[T7]  Gate and plan the writes              blockedBy: [T6]
[T8]  Land: the model                       blockedBy: [T7]
[T9]  Land: GitHub                          blockedBy: [T8]
[T10] Land: the plan file                   blockedBy: [T9]
[T11] Check the agreement                   blockedBy: [T10]
[T12] One commit on the plan's branch       blockedBy: [T11]
[T13] Back to the starting branch           blockedBy: [T12]
```

session skips T7–T12 (marked skipped) and goes to T13; a session stopped on uncommitted work
(Step 3) goes to T14.

## Workflow

### Phase: Prepare

**Step 1 — Load the templates** · Owner: `template-manager` · Depends on: pre-flight

    { "task":    "load these templates into the run's working folder",
      "inputs":  { "issue": null,
                   "templates": ["standards/templates/plan-update.md", "standards/templates/plan-view.md",
                                 "standards/templates/delivery-report.md", "standards/rules/pipeline-next.md"] },
      "outputs": { "out_dir":  "${stm_base}_plans/update-plan/templates/",
                   "manifest": "${stm_base}_plans/update-plan/templates/manifest-update-plan.json" },
      "task_id": "load-templates" }

`<update>` and `<view>` are the copies of `plan-update.md` and `plan-view.md` there. Every
`render_screen.py` call below passes `--template <update> --view-template <view> --work <working>`.
**SE-1 (F9/C10):** the manifest names both templates with a source tier; a `template_missing` for
either is a hard halt — the play never words a screen of its own.

**Step 2 — Find the plan** · Owner: play (script) · Depends on: Step 1

```
python3 scripts/find_plan.py find --args="<the play's arguments>" --plans-dir <plans> --out <working>/plan.json
```

Exit 1: render `not_found`, show it, and stop (close HALTED, `exit_reason: no_plan`). Exit 0 with
`by: number`: go on. Exit 0 with `by: description`: render `found` and wait for the person's typed
answer. A yes runs `find_plan.py confirm --out <working>/plan.json`; any other plan number starts
Step 2 again with it; anything else stops. Move `plan.json` into `${stm_base}_plans/update-plan/<id>/`
once the plan is known.
**SE-2 (F1/C1):** `plan.json` reads `confirmed: true` before any later record exists, and its
`plan` is a plan file in `<plans>`; no plan file was made.

**Step 3 — Get onto the plan's branch** · Owner: play (script) · Depends on: Step 2

```
python3 .garura/core/tools/plan/plan_branch.py go --plan <id> --plans-dir <plans> \
    --ignore "${stm_base}_plans/" --out <working>/branch.json
```

Exit 3: render `stopped`, show it, and go to Step 14 — nothing was written; the person cleans up and
runs the play again. Exit 2: show its `error` and stop. Exit 0: render `on_branch` and show it.
**SE-3 (F2/C2):** `branch.json` reads `stay`, `switch` or `cut` and the branch checked out is
`plan/<id>/base`; or it reads `stop` with each uncommitted file named, and the branch checked out
and its commit are unchanged. A `cut` names its `main_commit`, and main's plan file reads
`status: In Progress` and `branch: plan/<id>/base` at that commit.

**Step 4 — Read the plan's issues; the list** · Owner: `project-orchestrator` · Depends on: Step 3
Collect every issue number of the plan file (and the plan's own number) into `<numbers>`, then:

    { "task":    "read the plan's issues (track-plan-changes, mode read)",
      "inputs":  { "issues": "<numbers>" },
      "outputs": { "snapshot": "<working>/snapshot.json" },
      "task_id": "read-issues" }

Then the list. When `<working>/changes.yaml` has entries from an earlier session, render `resume`
and wait: "carry on" keeps it; "start fresh" moves it to `changes-<ts>.yaml`. Then, when there is
no list:

```
python3 scripts/add_entries.py start --changes <working>/changes.yaml --plan <id> \
    --title "<the plan's title>" --plan-branch plan/<id>/base --at <UTC time>
```

### Phase: Session

**Step 5 — Take instructions** · Owner: play + `project-orchestrator` (+ `product-os-keeper` for a
new feature) · Depends on: Step 4 · repeats
The person types. A request about the list itself is handled here, never turned into a plan
change: "show the list" renders `list`; "take out 3" runs `add_entries.py remove --n 3`. Any other
words are an instruction: write them to `<working>/instruction.txt` and dispatch:

    { "task":    "turn this instruction into plan list entries (author-plan-changes)",
      "inputs":  { "instruction": "<working>/instruction.txt", "plan_file": "<plans>/<id>.yaml",
                   "snapshot": "<working>/snapshot.json", "changes": "<working>/changes.yaml" },
      "outputs": { "draft": "<working>/draft-entries.json" },
      "task_id": "draft-entries" }

When the draft holds a `new-feature` entry, place it by fixed rules before the check — the
capability the person named, else the one that shares an issue number with the item's parent (or
an item above it); the slice the plan holds when exactly one serves `bi-<id>`, none when none
does; a feature id; the person's title as its one-line. What no rule settles becomes a question
for the person. No ICE is drafted in the session: the page skill writes the thin ICE at the landing
(Step 8), from the person's words.

```
python3 scripts/place_feature.py --draft <working>/draft-entries.json --plan-file <plans>/<id>.yaml \
    --spine <product_base>product-os/_spine.yaml --plan <id>
```

When it leaves a question about the capability, dispatch `product-os-keeper` for a suggestion (the
`find-work-placement` skill; it writes only the routing result), run the script again with
`--suggestion <working>/routing-result.json`, and show the question with the suggestion:

    { "task":    "suggest a capability for this new feature (find-work-placement); write nothing in the model",
      "inputs":  { "draft": "<working>/draft-entries.json", "plan_id": "<id>", "product_base": "<product_base>" },
      "outputs": { "route": "<working>/routing-result.json" },
      "task_id": "suggest-capability" }

Then check it:

```
python3 scripts/check_entries.py --draft <working>/draft-entries.json --plan-file <plans>/<id>.yaml \
    --snapshot <working>/snapshot.json --changes <working>/changes.yaml --view-template <view> \
    --out <working>/checked.json
```

- `unknown_issues` not empty: dispatch the read again (Step 4's contract) for those numbers into
  `snapshot-more.json`, merge it into `snapshot.json`, and check again.
- `questions` not empty: show each one, as written, and take the person's answer as a new
  instruction. No entry is taken from a part with a question.
- Take every entry that may join: `add_entries.py add --changes <working>/changes.yaml --checked
  <working>/checked.json --out <working>/taken.json`, then render `taken` and show it.
- For each entry left as big: render `confirm --at <i>` and wait; a yes runs `add_entries.py add
  ... --pick <i> --confirmed <i>`.
- For each entry left with a problem: render `break --at <i>` and wait; "do it anyway" runs
  `add_entries.py add ... --pick <i> --override <i>`; other words are a new instruction.
**SE-4 (F6/C3, C4):** every entry of `changes.yaml` with a problem in `checked.json` carries
`override`, and every big one was confirmed (`add_entries.py` refuses either otherwise); nothing
is written outside the working folder during the session.
**SE-5 (F7/C8):** every entry of `changes.yaml` came from a draft of the person's instruction
(`asked` holds that instruction); no status or direction entry exists that no draft named.

**Step 6 — Ask: approved or rejected** · Owner: play (script) · Depends on: Step 5
When the person says they are done (or asks to see it), render `list` and show it. Record their
typed reply:

```
python3 scripts/record_answer.py record --reply "<the person's words>" --changes <working>/changes.yaml \
    --at <UTC time> --out <working>/answer.json
```

`approved` → Step 7. `rejected` → render `rejected` (nothing lands; it asks what to change) and go
back to Step 5. `abort` → put back as they were the files the session's sub-agents wrote in
the plan's own short-term folder (`git checkout -- ${stm_base}<id>/` for a changed file, delete a
new one), render `aborted`, show it, and go to Step 13, which undoes the branch step; the list is
dropped at the close. `other` → answer the question or follow the instruction (back to Step 5), show the
list again and ask again.
**SE-6 (F3/C5):** `answer.json` is written by the script, and only the plain word "approved" reads
`approved`.

### Phase: Landing

**Step 7 — Gate and plan the writes** · Owner: play (script) · Depends on: Step 6

```
python3 scripts/record_answer.py verify --answer <working>/answer.json --changes <working>/changes.yaml \
  && echo '{"ok": true}' > <working>/verify.json
cp <plans>/<id>.yaml <working>/plan-before.yaml
python3 scripts/check_agreement.py hash-evals --plans-dir <plans> --out <working>/evals-before.json
python3 scripts/plan_ops.py --changes <working>/changes.yaml --plan-file <plans>/<id>.yaml \
    --snapshot <working>/snapshot.json --out-github <working>/github-ops.json --out-model <working>/model-ops.json
```

A non-zero `verify` writes nothing: show the list again and ask again (REC4).
**SE-7 (F3, F4/C5, C6):** `verify.json` exists before `github-record.json`, `model-record.json`
and `plan-write.json`, and the list's sha256 equals `answer.json`'s `list_sha`.

**Step 8 — Land: the model** · Owner: `product-os-keeper` · Depends on: Step 7
*Skip when `model-ops.json` has no parts.* For each part: the page skill (`enrich-grounding`,
new-feature and thin modes) writes the feature's page under its capability, and its thin ICE from
the person's words (the part's title and description), nothing made up; then `link-model-part` adds its model entry (`mode: new`, thin, its intent `bi-<id>`,
its `issue` — the story, or the number the tracker step makes, filled in after Step 9 with
`mode: update` — and `identified_by`) and, when the entry names a slice, the slice's `add_features`.

    { "task":    "write each new feature of model-ops.json: page, model entry with both thin marks, its place in the slice",
      "inputs":  { "model_ops": "<working>/model-ops.json", "product_base": "<product_base>" },
      "outputs": { "record": "<working>/model-record.json" },
      "task_id": "land-model" }

`model-record.json`: `{parts: [{feature, doc, linked}], files: [every model file written]}`.
**SE-8 (F8, F10/C9, C11):** the model files were written by `enrich-grounding` and
`link-model-part` (their reports are in the record), and no path under any plan's `evals/` is in
`files`.

**Step 9 — Land: GitHub** · Owner: `project-orchestrator` · Depends on: Step 8

    { "task":    "make the approved tracker writes (track-plan-changes, mode apply)",
      "inputs":  { "ops": "<working>/github-ops.json", "changes": "<working>/changes.yaml",
                   "approval": "<working>/answer.json", "read": "<numbers>" },
      "outputs": { "record": "<working>/github-record.json",
                   "before": "<working>/snapshot-before.json", "after": "<working>/snapshot-after.json" },
      "task_id": "land-github" }

Exit 1: dispatch it again once (it goes on from its record); a second failure stops the landing and
names the failed op for the person (REC5). Exit 2: nothing was written; back to Step 6.
When a new feature's story was made in this step (an op `<n>-create` of a `new-feature` entry),
dispatch `product-os-keeper` once more to name it on the feature's model entry:

    { "task":    "name each new feature's story on its model entry (link-model-part, mode update, issue)",
      "inputs":  { "model_ops": "<working>/model-ops.json", "github_record": "<working>/github-record.json",
                   "product_base": "<product_base>" },
      "outputs": { "record": "<working>/model-record.json" },
      "task_id": "name-story" }
**SE-9 (F8/C9):** `github-record.json` reads `ok: true`, and every op of `github-ops.json` is in its
`done`.

**Step 10 — Land: the plan file** · Owner: play (script) · Depends on: Step 9

```
python3 scripts/write_plan_changes.py --plan-file <plans>/<id>.yaml --changes <working>/changes.yaml \
    --github-record <working>/github-record.json --at <UTC time> --out <working>/plan-write.json
```

**SE-10 (F4/C6, C7):** `plan-write.json` reads `ok: true`; the file read back as the approved list
(the script compares before it writes), and it holds no `history`.

**Step 11 — Check the agreement** · Owner: play (script) · Depends on: Step 10

```
python3 scripts/check_agreement.py hash-evals --plans-dir <plans> --out <working>/evals-after.json
python3 scripts/check_agreement.py --changes <working>/changes.yaml --plan-before <working>/plan-before.yaml \
    --plan-file <plans>/<id>.yaml --snapshot-before <working>/snapshot-before.json \
    --snapshot-after <working>/snapshot-after.json --github-record <working>/github-record.json \
    --model-record <working>/model-record.json --spine <product_base>product-os/_spine.yaml \
    --evals-before <working>/evals-before.json --evals-after <working>/evals-after.json \
    --out <working>/agreement.json
```

Exit 1: show each problem; nothing is committed (REC5).
**SE-11 (F5/C7):** `agreement.json` reads `ok: true`.
**SE-13 (F10/C11):** `agreement.json` reads `features_ok: true` and `evals_unchanged: true`.

**Step 12 — One commit on the plan's branch** · Owner: play (script) · Depends on: Step 11

```
python3 scripts/commit_plan.py --plan <id> --plan-branch plan/<id>/base --plan-file <plans>/<id>.yaml \
    --changes <working>/changes.yaml --model-record <working>/model-record.json \
    --records-dir "${stm_base}<id>/" --out <working>/commit.json
```

The commit message names each instruction as the person typed it (`Asked:`), each override with
its rule (`Override:`) and what a new feature still owes (`Owed:`). The plan file keeps no history;
git does.

Then render `landed` and show it.
**SE-14 (F2/C7):** `commit.json` reads `ok: true` and `pushed: true`, its files are only the plan
file, the model record's files and the decision records in the plan's own short-term folder, and it
was made on `plan/<id>/base`.
**SE-12 (F6/C3):** `commit.json` reads `overrides_recorded: true`: every override of the list is an
`Override:` line of the commit message.

### Phase: Back

**Step 13 — Back to the starting branch** · Owner: play (script) · Depends on: Step 12 (or Step 6
on "abort")

```
python3 .garura/core/tools/plan/plan_branch.py back --record <working>/branch.json --ignore "${stm_base}_plans/"
```

On "abort", run `abort` in its place: it undoes a branch the session cut (the branch deleted, main's
plan file put back by a revert commit) when nothing else has landed on it — else it stops and names
what is there, for the person — and then goes back:

```
python3 .garura/core/tools/plan/plan_branch.py abort --record <working>/branch.json --ignore "${stm_base}_plans/"
```

**SE-15 (F12):** the branch checked out is `branch.json`'s `back_to` (or the plan's branch, when the
session started there).

### Phase: Scenario Validation

**Step 14 — Scenario evals** · Owner: play · Depends on: Step 13

```
python3 scripts/close_session.py --work <working> --out <working>/session.json
```

- **SCE-1 (S1 — product owner, several instructions, one approval):** `session.json` reads
  `outcome: landed` and `ok: true`, and `agreement.json` reads `ok: true`.

- **SCE-5 (S5 — product owner, an override):** `commit.json` reads `overrides_recorded: true`.
- **SCE-6 (S6 — product owner, a new feature in a plan with no slice):** `agreement.json` reads

**SE-16 (F11/C12):** the stop condition (D1 the person answered; D2 the session closed as it
should; D3 it ended on the starting branch) reads **held** before the run closes COMPLETED; it is
evaluated before the self-clean below.

## Pause and Resume

A session's list is kept in `<working>/changes.yaml` until it lands. A new `/update-plan` on the
same plan finds it and asks: carry on, or start fresh (Step 4). A landing that stopped part way
goes on from its records: the tracker step skips every op its record holds, and the plan file step
writes only when the tracker record reads `ok: true`. Nothing is resumed past a failed agreement
check: the person decides.
