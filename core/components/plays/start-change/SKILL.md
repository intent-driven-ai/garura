# start-change

Open a unit of work cleanly — the one the person names, never the branch they are on: ensure
a tracked issue, a branch for it — a sub-branch of its
plan's branch (`plan/<plan-id>/<issue>-<slug>` off `plan/<plan-id>/base`) when the issue
sits in a plan, else `feature/<issue>-<slug>` cut from an up-to-date main — a git worktree
when config calls for it, and an initialized STM workspace — so every play that runs after
start-change begins from a known, identified context. It is never locked to a plan: any issue
(a bug, a chore, a story, a feature), by its number or a short description, starts the same way.
On top of that, `plan <id>` starts a plan's work on its own — main's plan file first, then the
plan's branch — and stops, with no story branch (#989).

**Pipeline position: start.** start-change is the start-of-pipeline primitive. The D2
pipeline-position rule injects it into any other play declared `position: start`. As the
primitive itself, start-change does not get a start composed into it.

## Role

You are the orchestrator. You own the workflow and the step order. **Issue** work goes to a
utility agent (the fresh-issue match from a description is genuine judgment); the mechanical
**branch** work runs in a bundled script calling git directly, not an agent (C8, #484). You
never reason out git/gh inline in play prose.

**Forbidden:** running the mechanical branch work (cut/worktree/push) through an agent
dispatch (the #484 bug); ad-hoc `gh`/`git` in play prose; reimplementing issue logic inline;
taking the change from the branch name, or going on when nothing was typed (C10); cutting a
plan's branch any way but the plan tool's `plan_branch.py`, main first (C9/C11).

**Agent boundaries:**

| Agent | Domain | Skill it invokes | Phases |
|-------|--------|------------------|--------|
| `project-orchestrator` | Issues: resolve an existing issue, create a new one (fresh-match judgment) | `track-issue` | Execution |

`project-orchestrator` is a **utility agent** (issue plumbing + the fresh-issue match),
exempt from the domain-agent budget. The branch work is the bundled `setup_branch.py`, and
every cut of a plan's branch is the plan tool's `plan_branch.py` — no agent (C8). A plan's start
(`plan <id>`) dispatches no agent at all. This play uses **zero domain agents**.

## Pre-flight

| Check | Constraint | Action on Failure |
|-------|-----------|-------------------|
| Resolve working base + config (`.garura/core/config.yaml`) | — | Hard halt |
| Git repository present | C2 | Hard halt |
| Platform CLI available (`gh`) | C1 | Hard halt |
| What the person typed: an issue number, a description, or `plan <id>` — via `scripts/resolve_args.py` | C10 / C11 | **Hard halt** on nothing typed, or a plan that cannot start — print its `error` line; nothing is started |
| The plan tool is installed (`.garura/core/tools/plan/plan_branch.py`) | C9 / C11 | Hard halt |
| Read `start-change.worktree` flag (default `false`) | C3 | — |
| The plan files' folder is the resolver's `plans_base` (`plans.base-path`, default `.garura/project/plans/`); a plan is read from git at the latest main and the plan's own branch, never the checkout | C9 | — |
| Resume marker check for this issue's start-change | C6 | Resume |

Resolve the deterministic pre-flight facts with the bundled resolver — not by inference. The
orchestrator captures the current branch and passes it in:

```
python3 scripts/preflight.py --play start-change \
    --config .garura/core/config.yaml --branch "$(git branch --show-current)"
```

It returns the facts as JSON — `stm_base`, `worktree` (the `start-change.worktree` flag,
absent ⇒ false), `plans_base` (the plan files' folder), `branch`, `issue`, `on_default_branch`,
`evidence_record`, `ltm_project_target`. The orchestrator holds these for every later path;
the table keeps the policy. The live checks (git repo present, `gh` available) stay as the
orchestrator's environment reads, not the resolver. **The resolver's `issue` (read from the
branch name) never names the change (C10):** the change is what the person typed.

Then read what the person typed — the play's arguments, as they are:

```
python3 scripts/resolve_args.py --args="<the play's arguments>" --plans-dir "<plans_base>" \
    --description-out "<stm_base>_start/work-description.txt" \
    --out "<stm_base>_start/args.json"
test -f .garura/core/tools/plan/plan_branch.py || { echo "the plan tool is not installed — halt"; exit 1; }
```

`args.json` reads `mode`: `issue` (a number; words after it are a `note`), `description`
(words; written to `work-description.txt`), `plan` (`plan <id>`, read from main in git), or
`none`. Exit 1 — nothing typed, or a plan no file on main names, or main marks Done or Dropped —
is a **hard halt**: print its `error` line to the person and start nothing (REC10; S10, S11).
Exit 2 is a hard halt with the error named. `mode: plan` takes the **Plan path** below; every
other mode takes the **Change path** (Steps 1–5). `<stm_base>_start/` is a scratch folder: its
files move into the issue's STM at Step 5, or into the plan's working folder on the Plan path.

**Resume check (C6, F5):** when the typed issue already has a status marker or an existing
`feature/<issue>-*` or `plan/<plan-id>/<issue>-*` branch, resume — switch to the existing
branch, reuse the existing STM, and do NOT create a second issue or branch. Skip completed
steps, reset any in-progress step to pending, continue from the first incomplete one. The
branch the session is on never makes a resume (C10).

## Workflow

### Phase: Execution

**Step 1 — Resolve Issue** · Owner: `project-orchestrator` · Depends on: pre-flight
Dispatch a JSON contract; the agent invokes `track-issue` (`action: resolve`) to find
an existing issue matching the work (or the issue number passed in), and writes the
result to disk. The contract moves only paths, never data:

    {
      "task":    "resolve an existing tracked issue for this change (do not create)",
      "inputs":  { "description": "<working>/work-description.txt",
                   "issue_number": "<args.json issue, when mode is issue>" },
      "outputs": { "issue": "<working>/issue.json" }
    }

The issue comes only from `args.json` (C10): its `issue` for `mode: issue`, else the match the
agent finds for the typed description (it confirms the issue — a bug, a feature, a chore, a
story — or reports none). For `mode: issue`, `<working>/work-description.txt` holds the
issue's title and the typed `note`, when there is one.

`issue.json` records `{ resolved: true|false, issue_number, title, created: false }`.

**Step 2 — Confirm New Issue** · Owner: play · Depends on: Step 1
*Skip when `issue.json.resolved == true`.* When no issue was resolved, creating one is an
outward-facing action (class: standard). Resolve the gate switch per
`standards/rules/gate-config.md` FIRST:

- **off** (this project: `gates.plays.start-change: off`) → do not wait; record
  `gate skipped by config (gates.plays.start-change)` as a Checkpoint Decisions row in
  evidence and proceed. A skip is always recorded, never silent.
- **on** → present the proposed new issue (title + summary) and wait for a typed
  approval. Approve → continue to Step 3; cancel → halt.

**Either way — the machine wall (C1/F7), never gated by the switch:** before Step 3
creates anything, run the bundled validator on the proposal record:

```
python3 scripts/validate_issue.py \
    --issue-json <working>/issue.json \
    --description <working>/work-description.txt
```

It checks the title is present, ≥15 chars, and tagged (`[ENH]/[BUG]/[FEAT]/[DOCS]/[TASK]`
or a conventional prefix), and that the work description is complete. A non-zero exit is
a **hard halt** regardless of the gate state — REC7 hands to a human (fix the
title/description, re-run). This is the deterministic check that replaced the human eye
when the gate went off (#467).

**Step 3 — Create / Finalize Issue** · Owner: `project-orchestrator` · Depends on: Step 2
When Step 1 resolved an issue, carry it forward unchanged. When Step 2 approved a new
issue, the agent invokes `track-issue` (`action: create`) and writes the finalized
`issue.json` (`created: true`, `issue_number` set).
**SE-1 (F1/C1):** `issue.json` has a non-empty `issue_number` (an issue is anchored
before any branch work); on resume, `created == false` and no new issue exists (F5).
**SE-8 (F7/C1):** `validate_issue.py` ran BEFORE the create (its verdict predates
`created: true`), and it exits 0 when re-run on the created issue's record — title
present/tagged, description complete. A non-zero exit at either point halted the run
to a human (REC7); no issue exists over a failed validation.

**Step 4 — Set Up Branch + Worktree** · Owner: play (script) · Depends on: Step 3
First read which plan the issue sits in, from the plan files — never guess it (C9):

```
python3 scripts/resolve_plan.py --plans-dir "<pre-flight plans_base>" \
    --issue <issue_number> --slug <slug> --out "<working>/plan.json"
```

It fetches origin and reads the plan files from git, never from the checked-out branch: at the
latest `origin/main`, and, for a plan whose own branch `plan/<plan-id>/base` is on origin, on
that branch too (a plan session writes there first); an issue in either copy belongs to the plan.
It returns `{ plan_id, plan_branch, issue_branch, source }` — `plan/<plan-id>/base` and
`plan/<plan-id>/<issue>-<slug>` for an issue in a plan, or `plan_branch: null` and
`feature/<issue>-<slug>` for an issue in no plan; `source` names the ref read, whether the fetch
worked (`fetched: false` means the last fetched copies were read — say so in the report) and each
plan branch read. Exit 2 (the issue sits in two plans, a plan file cannot be read, or there is
no `origin/main`) is a hard halt — REC9.

Then run the bundled branch script with those names. It pulls `main` to its latest origin
tip. For an issue in a plan whose branch is not on origin yet, it has the plan tool cut
`plan/<plan-id>/base` main first (C9, ADR 061): main's plan file is set to In Progress with the
branch named, committed and pushed on main, and the branch is cut from that commit. When the
plan's branch exists, it merges the latest main into it. It then cuts the issue's branch from
it; a merge conflict exits 1 and halts for a person. A plan branch gone on origin but
still here is deleted and cut fresh only when every commit on it is on main — the plan tool's rule — and branch.json
records it (`stale_plan_branch: {deleted, tip, on_main}`); otherwise, or when origin cannot be
reached, it exits 1, keeps the copy and names why (the commits that are not on main). A push or
a delete that fails exits 1; a call to origin gives up after a time limit. For an issue in no plan it cuts
`feature/<issue>-<slug>` from main. It switches to the branch if it already exists, sets up
a git worktree **iff** `start-change.worktree` is true, pushes, and writes `branch.json`.
No agent (C8):

```
python3 scripts/setup_branch.py --issue <issue_number> \
    --branch-name "<plan.json issue_branch>" --base main \
    $( [ "<plan.json plan_branch>" != "null" ] && echo --plan-branch "<plan.json plan_branch>" \
         --plan-tool .garura/core/tools/plan/plan_branch.py --plans-dir "<plans_base>" \
         --ignore "<stm_base>" ) \
    $( [ "<start-change.worktree>" = "true" ] && echo --worktree ) \
    --out "<working>/branch.json"
```

`branch.json` records `{ branch_name, base_sha, on_default_branch: false, worktree_path|null,
plan_branch|null, plan_branch_created }`.
**SE-2 (F2/C2):** the current branch is not `main` and equals `plan.json.issue_branch`. For an
issue in no plan, `branch.json.base_sha` equals the current `origin/main` tip. For an issue
in a plan, origin/main is an ancestor of `plan_branch`, and `base_sha` equals its tip.
**SE-10 (F9/C9):** when `plan.json.closed_plan` is set (the issue sits in a plan main marks Done or
Dropped), `plan_id` is null, `branch.json.branch_name` starts with `feature/`, and no
`plan/<closed_plan>/base` was made; when `branch.json.plan_branch_created` is true, `plan-branch.json` (the plan
tool's record, beside `branch.json`) reads `action: cut` with a `main_commit`, and main's plan
file at that commit reads `status: In Progress` and `branch: plan/<plan_id>/base` — the plan's
branch was cut main first, through the plan tool. `plan.json` exists and was written by `resolve_plan.py` before the branch
was cut, and its `source.ref` is `origin/main` (read from git, not the checkout); when
`source.fetched` is false, the delivery report says the plan was read from the last fetched
copies; when `branch.json.stale_plan_branch` is set, its `tip` is an ancestor of `origin/main`
(no commit was lost); when `plan.json.plan_id` is set, `branch.json.branch_name` starts with
`plan/<plan_id>/` and `branch.json.plan_branch` is `plan/<plan_id>/base`.
**SE-3 (F3/C3):** `git worktree list` shows a worktree for the branch **iff**
`start-change.worktree` is true (present when on, absent when off).
**SE-6 (C5):** issue work went through the `track-issue` skill (`issue.json` exists) and
the branch work through the bundled `setup_branch.py` (`branch.json` exists) — no inline
`gh`/`git` in play prose.
**SE-9 (F8/C8):** the branch cut/worktree/push ran as `setup_branch.py`, not an agent
dispatch — no `repo-orchestrator`/`cut-branch` was invoked for the branch work.

**Step 5 — Initialize STM Workspace** · Owner: play · Depends on: Step 4
Record the session identity stamp's start marker first (#463 — soft-fail, never a halt); the stamp start runs here rather than at pre-flight because pre-flight has no issue yet:

```
python3 scripts/session_stamp.py --phase start \
    --marker "{stm_base}{issue}/status/session-stamp-start-change.json" \
    --cwd "$(pwd)" --branch "$(git branch --show-current)"
```

Run the mechanical script (it creates the five permitted structure keys idempotently):

```
python3 scripts/init_stm.py --stm-base <stm.base-path> --issue <issue_number>
```

Move the scratch files of `<stm_base>_start/` (`args.json`, and `work-description.txt` when a
description was typed) into `{stm_base}{issue}/context/`. Then commit the run artifacts on the fresh feature branch (C7) — play-owned mechanical
work, run as a command: the workspace opens with a clean tree and its own record
(issue.json, branch.json, work-description) aboard:

```
git add "{stm_base}{issue}/context/"
git commit -m "chore(stm): record start-change workspace context (#<issue>)"
```

**SE-4 (F4/C4):** `<stm.base-path>/<issue_number>/` exists and contains the five
structure dirs (`specs`, `evidence`, `checkpoint`, `context`, `review`) before close.

**SE-11 (F10/C10):** `args.json` exists and was written by `resolve_args.py` before Step 1;
its `mode` is `issue` or `description`, and `issue.json`'s `issue_number` is `args.json`'s
`issue` (mode issue) or the agent's match for the typed description — never the number in the
branch name. For `mode: none` the run halted at pre-flight with no issue, branch or STM made.

### Plan path — `plan <id>` (C11)

The working folder is `<working> = ${stm_base}_plans/start-change/<id>/`, made fresh; it is never
committed. Move `<stm_base>_start/args.json` into it, and record the session identity stamp's
start marker there (#463 — soft-fail, never a halt):

```
python3 scripts/session_stamp.py --phase start \
    --marker "<working>/session-stamp-start-change.json" \
    --cwd "$(pwd)" --branch "$(git branch --show-current)"
```

**Step P1 — Start the Plan's Branch** · Owner: play (script) · Depends on: pre-flight
Record the branches, then get onto the plan's branch with the plan tool — the one way to cut
it, main first (ADR 061):

```
python3 scripts/check_plan_start.py --save-branches <working>/branches-before.txt
python3 .garura/core/tools/plan/plan_branch.py go --plan <id> --plans-dir "<plans_base>" \
    --ignore "<stm_base>" --out <working>/plan-branch.json
```

Exit 0 reads `action: cut` (main's plan file set to In Progress with `branch: plan/<id>/base`,
committed and pushed on main; the branch cut from that commit and pushed), `switch` or `stay`
(the branch exists; nothing changes). Exit 3 (uncommitted work, the files named) or 2 (a Done or
Dropped plan, a stale copy with commits not on main, a git step that failed) is a **hard halt**:
print the record's `error` and `files`, and start nothing. No issue is looked up, no story
branch is cut, no STM workspace is made, and nothing is committed on the plan's branch.

**Step P2 — Check the Plan's Start** · Owner: play (script) · Depends on: Step P1

```
python3 scripts/check_plan_start.py --record <working>/plan-branch.json --plans-dir "<plans_base>" \
    --branches-before <working>/branches-before.txt --out <working>/plan-start-check.json
```

**SE-12 (F11/C11):** `plan-start-check.json` reads `ok: true`: `on_plan_branch` (the session is
on `plan/<id>/base`, and it is on origin), `main_agrees` (for a cut: the branch equals the main
commit it was cut from, which is on origin/main, and main's plan file there reads In Progress
on the branch; for a switch or stay: true) and `no_story_branch` (no `plan/<id>/…` branch but
the base was made). A problem applies REC11.

The Plan path then runs **SCE-8** and **SCE-9** (Step 6) and the Close (Step 7) with
`stop-condition-plan.yaml` over `<working>`.

### Phase: Scenario Validation

  `plan/<P>/<issue>-<slug>` both exist on origin; `plan/<P>/base` equals the origin/main tip;

- **SCE-6 (S6 — developer, plan already started):** origin/main is an ancestor of

- **SCE-7 (S7 — developer, an issue added on main while the checkout is older):** `plan.json`

- **SCE-8 (S8 — product owner, start a plan on its own):** `plan-start-check.json` reads

  description typed, `args.json` reads `mode: description` and `issue.json`'s

- **SCE-13 (S13 — developer, a bug in a finished plan):** `plan.json` reads `plan_id: null` and

- **SE-5 (F5/C6):** a re-run for the same issue created neither a duplicate issue nor a

| For | Trigger | Direction | Handoff |
|-----|---------|-----------|---------|
| F1 | no issue resolved or created before branch work | create the issue from the work description via `track-issue`, then continue | autonomous |
| F2 | branch base is not the latest main (for an issue in a plan: not the plan branch with the latest main merged in), or current branch is `main` | bring the base up to date and re-cut the branch from it, or move off main | autonomous |
| F3 | worktree state does not match `start-change.worktree` | reconcile to config — remove the stray worktree, or create the missing one | autonomous |
| F4 | close check finds the STM workspace missing | run `scripts/init_stm.py` to initialize it before reporting done | autonomous |
| F5 | a second run would create a duplicate issue or branch | detect the existing issue and branch and resume them instead of creating new ones | autonomous |
| F6 | the close would report COMPLETED without the Done means held | evaluate the stop condition and surface the unmet clauses; the run closes HALTED until state is fixed | autonomous |

| F9 | the plan was not read by `resolve_plan.py` from git, an issue in a plan got a branch outside `plan/<plan-id>/`, a plan's branch was cut without main's plan file first, or a stale local plan branch was at risk | run `resolve_plan.py` and re-cut the branch with its names, the plan's branch through the plan tool; an issue in two plans, or `setup_branch.py` stopping on a stale copy with commits found nowhere else or on an origin it could not reach, stops for a person (fix the plan files, push or move the commits, or run again when origin can be reached) | human |
| F10 | a run started a change the person did not name: nothing was typed and it went on, or the change came from the branch name | stop with the one line naming what to give; take the change only from `resolve_args.py` | autonomous |

## Pause and Resume

Steps run top to bottom. On entry, resolve the issue (from what was typed — `args.json` — then its status marker, or its
existing `feature/<issue>-*` or `plan/<plan-id>/<issue>-*` branch; never from the branch the session is on), check the status marker, skip completed steps,
reset any in-progress step to pending, and continue. A fresh start with no marker runs
everything and creates the marker at Step 1. Resuming never duplicates the issue or
branch (C6, F5). A plan's start (`plan <id>`) does not resume: run again, it finds the plan's
branch and switches to it, changing nothing (S9).
