# sample-drive

From a written statement, run `/intent` then `/vision` as one drive: one issue, one branch,
questions first, no stop for the plays' approvals, a checker at the end, and one pull request.

**Pipeline position: both.** The drive opens its change (`start-change`) and lands it (the end
sequence). The plays inside open nothing (drive contract, step 3).

## Compiled From

This drive was compiled from the sample-drive ICE (`reference/ice.md`) by drive-creator.
Intent defines constraints (C1–C4) and failure conditions (F1–F4); the expectation defines
success scenarios (S1–S2), a Done means (D1–D4, baked to `stop-condition.yaml`), and one
recovery entry per failure condition. To modify this drive, update `reference/ice.md` and
recompile with `/drive-editor`.
Do NOT edit this file manually — it is a compiled artifact.

## Role

You are the drive. You run the plays below in their fixed order and do no work of your own
(ADR 029 §2): every rule lives in the plays. You ask the drive's questions first, hand every
play the same contract, check each play's done check, commit its run files, have the checker
judge the result, and land the change. Each play runs as a sub-agent (or headless, by config)
and dispatches its own agents and judges.

**Forbidden:** doing a play's work yourself; answering a question nothing in memory or the
person's answers supports; starting a play before the one before it proved done; ending done
without the checker's pass.

## Pre-flight

## Workflow

Run the Shared Drive Run with this drive's values:

```bash
# --- Shared Drive Run (shared; see ../_shared/drive-run.md) ---
drive=sample-drive
plays=intent,vision
questions=who_asks -> answers.intent.who_asks; proof -> answers.intent.proof
runner_key=drives.sample-drive.runner
checker_key=drives.sample-drive.checker
end=commit-change, propose-change, review-change, merge-change (merge pinned)
# --- end Shared Drive Run ---
```

### Phase: Open

**Step 1 — Open the change** · Owner: `start-change` · Depends on: pre-flight
Run R2 of the shared run.
**SE-1 (F1/C1):** `start-change.json` names one issue and one branch; every file the run writes
is under `{stm_base}<issue>/`.

### Phase: Questions

**Step 2 — Questions first** · Owner: drive · Depends on: Step 1
Run R3: ask "Who asks for this product?" and "How will we know it worked?", memory first.
**SE-2 (F2/C2):** `answers.json` exists before `contract.json`, and every answer names its
source (memory, or the person's typed words).

**Step 3 — Write the drive contract** · Owner: drive (script) · Depends on: Step 2
Run R4 with the statement as `inputs.intent.statement`.

### Phase: Plays

**Step 4 — Run /intent** · Owner: `intent` · Depends on: Step 3
Run R5 for `intent`.

**Step 5 — Run /vision** · Owner: `vision` · Depends on: Step 4
Run R5 for `vision`. Before it starts, R5's hand-on step adds `inputs.vision.intents` — the
intents `/intent` saved — to the contract.
**SE-3 (F3/C3):** `intent-done.json` and `vision-done.json` read `done: true`, each written
before the next play started; `intent-commit.json` and `vision-commit.json` show no leftover.

### Phase: Check

**Step 6 — The checker** · Owner: checker · Depends on: Step 5
Run R6.
**SE-4 (F4/C4):** `check.yaml` reads `verdict: pass` from a checker that is not the drive's own
model; a reject halted the drive.

### Phase: End sequence (injected — D2 position: both)

**Step E1 — commit-change** · Owner: `commit-change` · blockedBy: Step 6
**Step E2 — propose-change** · Owner: `propose-change` · blockedBy: E1
**Step E3 — review-change** · Owner: `review-change` · blockedBy: E2
**Step E4 — merge-change** · Owner: `merge-change` · blockedBy: E3

### Phase: Scenario Validation

**Step 7 — Scenario evals** · Owner: drive · Depends on: Step E4
- **SCE-1 (S1 — product owner):** `contract.json`, `intent-done.json`, `vision-done.json` and
  `check.yaml` (`verdict: pass`) exist under the issue; one pull request carries the change.
- **SCE-2 (S2 — product owner):** the person's answer to `/vision`'s question is in the issue's
  short-term memory, and `vision-done.json` reads `done: true`.

**Step 8 — Close** · Owner: drive · Depends on: Step 7

## Recovery

| For | Trigger | Direction | Handoff |
|-----|---------|-----------|---------|
| F1 | a write outside the issue, or a second issue or branch | move the record under the drive's issue and run on the contract's branch | autonomous |
| F2 | a play ran before the questions, or answered from nothing | stop, ask the person, record the answer, re-run the play | human |
| F3 | a play started before the last one proved done, or on an unclean tree | halt; finish or fix the earlier play, commit its run files, resume | human |
| F4 | the drive would end done with no checker pass | run the checker; a reject halts the drive | autonomous |

## Pause and Resume

The drive's run lives under its issue (`{stm_base}<issue>/context/sample-drive/<run-ts>/`). On
entry, find the last run folder: skip every play whose `<play>-done.json` reads `done: true`
and whose run files are committed, and continue from the first play not done.
