# list-plans

Print every plan of the project at once, from the plan files alone: the list (the default), or
the graph of each plan's branch against main (`--graph`). The plan tool prints the view from the
plan-view template; a check proves it holds every plan once, in order, the same way twice, and
that nothing changed.

## Compiled From

This play was compiled from the list-plans ICE (`reference/ice.md`) by create-play (#719,
stories #729 and #806). Intent defines constraints (C1–C9) and failure conditions (F1–F7); the
expectation defines success scenarios (S1–S5), a Done means (D1–D4, baked to
`stop-condition.yaml`), and one recovery entry per failure condition.
To modify this play, update `reference/ice.md` and recompile with edit-play.
Do NOT edit this file manually — it is a compiled artifact.

## Role

You are the orchestrator. You own the workflow and the step order, and you do no domain work.
Every mechanical part — the mode, the view, the check — is a script (C5): the plan tool prints
the view, `check_list.py` proves it. You delegate one thing: loading the template, which is
`template-manager`'s job, because a play reads no memory (ADR 039).

**Forbidden:** reading the tracker, the product model or any source other than the plan files
and git's branches (C1/F3); writing a plan file, an issue or a branch (C2/F2); writing, editing
or re-wording any line of the view yourself — you present the plan tool's output as it is
(C4/F3); guessing a mode (C8); showing a list when the plan tool stopped (C6/F5).

**Agent boundaries:**

| Agent | Domain | Skills it invokes | Phases |
|-------|--------|-------------------|--------|
| `template-manager` | Load the plan-view template and the close templates into the run's working folder | — | Prepare |

`template-manager` is a **utility agent**, exempt from the domain-agent budget. This play uses
**zero domain agents**: there is nothing to decide.

## Pre-flight

| Check | Constraint | Action on Failure |
|-------|-----------|-------------------|
| Resolve config (`.garura/core/config.yaml`) via `scripts/preflight.py` | — | Hard halt |
| The mode resolves to `list` or `graph` via `scripts/resolve_args.py` | C8 | **Hard halt** — print its `error` line; never guess a mode |
| The plan tool is installed (`.garura/core/tools/plan/plan.py`) | C1 / C4 | Hard halt — without it there is no deterministic view |
| The plans folder (`plans.base-path`, default `.garura/project/plans/`) exists | C7 | Graceful — a missing folder is the same as an empty one: the view says there are no plans |

```
python3 scripts/preflight.py --play list-plans --config .garura/core/config.yaml \
    --branch "$(git branch --show-current)"
python3 scripts/resolve_args.py --args="<the play's arguments>" --out <working>/mode.json
test -f .garura/core/tools/plan/plan.py || { echo "the plan tool is not installed — halt"; exit 1; }
```

The working folder is `<working> = ${stm_base}_plans/list-plans/` (the play has no issue of its
own). Create it fresh: a prior run's files are overwritten, never resumed. `<plans>` is
`plans.base-path` from config, else `.garura/project/plans/`.

Right after, record the session identity stamp's start marker (#463 — soft-fail, never a halt):

```
python3 scripts/session_stamp.py --phase start \
    --marker "<working>/session-stamp-list-plans.json" \
    --cwd "$(pwd)" --branch "$(git branch --show-current)"
```

## Workflow

### Phase: Prepare

**Step 1 — Load the template** · Owner: `template-manager` · Depends on: pre-flight
Dispatch one JSON contract for the view's template and the close's templates — paths only:

    { "task":    "load these templates into the run's working folder",
      "inputs":  { "issue": null,
                   "templates": ["standards/templates/plan-view.md",
                                 "standards/templates/delivery-report.md",
                                 "standards/rules/pipeline-next.md"] },
      "outputs": { "out_dir":  "<working>/context/templates/",
                   "manifest": "<working>/context/templates/manifest-close-list-plans.json" },
      "task_id": "load-templates" }

`<template>` is `<working>/context/templates/standards/templates/plan-view.md`.
**SE-1 (C4/F3):** the manifest exists, names `plan-view.md` with a source tier and fingerprint,
and `<template>` holds a ```` ```yaml plan-view ```` block. A `template_missing` for
`plan-view.md` is a hard halt (REC3) — the play never prints a layout of its own.

### Phase: View

**Step 2 — Print the view** · Owner: play (script) · Depends on: Step 1
Record the plan files' hashes, then print the view twice with the plan tool — the second print
is the determinism proof (C5):

```
python3 scripts/check_list.py hash --plans-dir <plans> --out <working>/before.json
python3 .garura/core/tools/plan/plan.py <mode> --template <template> --plans-dir <plans> \
    > <working>/view.txt 2> <working>/tool-error.txt; echo "{\"exit\": $?}" > <working>/tool-exit.json
python3 .garura/core/tools/plan/plan.py <mode> --template <template> --plans-dir <plans> \
    > <working>/view2.txt 2>> <working>/tool-error.txt
```

`<mode>` is `list` or `graph`, from `mode.json`.
**SE-2 (C6/F5):** `tool-exit.json` reads 0. An exit of 2 is a hard halt: print
`tool-error.txt` (it names the plan file and its status) and show no list (REC5).

**Step 3 — Check the view** · Owner: play (script) · Depends on: Step 2

```
python3 scripts/check_list.py check --plans-dir <plans> --template <template> --mode <mode> \
    --view <working>/view.txt --view2 <working>/view2.txt --before <working>/before.json \
    --out <working>/check.json
```

**SE-3 (C3/C4/C5/C7, F1/F3/F4):** `check.json` reads `all_listed: true` (every plan once — F1;
an empty folder holds the template's no-plans line — C7), `in_order: true` (C3),
`template_used: true` (every plan line is the template's line — F3) and `same_twice: true`
(F4). On a GAP, apply REC1/REC3/REC4 and re-run Steps 2–3.
**SE-4 (C2/F2):** `check.json` reads `unchanged: true` — every plan file hashes the same as
before the tool ran — and no tracker or branch verb was run in this play (the play's only
commands are the ones written above). A changed hash is a hard halt (REC2).
**SE-5 (C1/F6):** for `graph`, `check.json` reads `graph_numbers_match: true`: every
ahead/behind number equals git's own count (`git rev-list --left-right --count`). On a GAP,
apply REC6.

**Step 4 — Present the view** · Owner: play · Depends on: Step 3
Output `<working>/view.txt` to the person **as it is**, in a code block, with one plain line
before it: how many plans and which mode. Never re-word, sort, trim or add to a line of it (C4).

### Phase: Scenario Validation

**Step 5 — Scenario evals** · Owner: play · Depends on: Step 4
- **SCE-1 (S1 — developer, every plan at once):** in `list` mode, `check.json` reads
  `all_listed: true` and `in_order: true`, and `plans_in_folder` equals the number of plan
  files.
- **SCE-2 (S2 — lead, plans against main):** in `graph` mode, `check.json` reads
  `graph_numbers_match: true` and `all_listed: true`.
- **SCE-3 (S3 — newcomer, no plans yet):** with no plan file, `view.txt` holds the template's
  no-plans line and `check.json` reads `all_listed: true`.
- **SCE-4 (S4 — operator, an old plan file):** with a plan file whose status the template does
  not know, `tool-exit.json` reads 2, `tool-error.txt` names the file, and no view was
  presented.
- **SCE-5 (S5 — auditor, nothing changed and nothing drifted):** `check.json` reads
  `same_twice: true`, `unchanged: true` and `template_used: true`.

### Phase: Evidence & Close

**Step 6 — Close** · Owner: play · Depends on: Step 5
Run the Standard Play Close. `/list-plans` has no issue of its own: its run's short-term folder
is `<working>`, and the close finds the templates Step 1 already loaded there.
**SE-6 (F7/C9):** the close is stop-condition gated — `check_stop_condition.py` over

files printed the same way twice; D4 no plan file changed) reads **held** before the run closes
COMPLETED; anything else closes HALTED with the unmet clauses named. It runs BEFORE Step 7's
self-clean.

## Recovery

| For | Trigger | Direction | Handoff |
|-----|---------|-----------|---------|
| F1 | the check finds a plan missing or listed twice | re-run the plan tool over the plans folder and check again; if it still fails, report the plan and close HALTED | autonomous |
| F2 | a plan file's hash changed during the run, or a write to the tracker or a branch was made | stop, report what changed, and leave it for a person; read only is never repaired by a retry | human |
| F3 | a line of the view does not match the template's layout | load the template again through template-manager and re-run the plan tool with it | autonomous |
| F4 | the two prints differ | re-run both prints; if they still differ, report the difference and close HALTED | autonomous |
| F5 | the plan tool exits 2 on a status it does not know | stop, name the plan file and its status, and show no list; a person fixes the plan file | human |
| F6 | a graph number does not equal git's count | re-run the graph and check again; if it still differs, close HALTED with both numbers | autonomous |
| F7 | the close would report COMPLETED without the Done means held | surface the unmet clauses and re-run the step that makes the missing record, or close HALTED | autonomous |

## Pause and Resume

Steps run top to bottom. `/list-plans` does not resume: a view is only as good as the plan files
it was printed from, so any interruption means a fresh run. Prior files in `<working>/` are
overwritten. There is no status marker.
