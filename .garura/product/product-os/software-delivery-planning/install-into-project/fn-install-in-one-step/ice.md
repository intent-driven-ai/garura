## Intent
- Goal: From one command in the project's folder, with no copy of Garura's source and through the same engine as the install play, Garura's parts of the chosen kind are laid whole for the team's coding tool, from the version named or the default, with the version and every part and file laid kept in the project's install record and shown at the end, and with every file the project already had left as it was.
- Limit: A file or part the project already has is never written over; Garura's version goes beside it, and a part of the project's own with a Garura part's name is named, not replaced.
- Limit: A version that does not exist stops the install with nothing laid; it never falls back to another version.
- Limit: No stale or deprecated part, no memory, and no part without the shared files and workers it needs is laid, and Garura's own development guide never becomes the project's instructions.
- Fails if: A file the project had before the install is changed, replaced or gone afterwards.
- Fails if: The project holds no record, or a record that misses a part laid, the kind or the version, or the two front doors lay different parts for the same version and kind.
- Fails if: A laid part points to a file the install did not lay, or an install of a named version lays another one.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the files already in the project where Garura lays its parts, such as its instructions file and its own skills and agents; the version named and the releases there are; the kind chosen and any named plays; that version's parts with their workers and shared files, and which are stale or deprecated; the team's coding tool; and any record and version file from an earlier install.
- Never read: any memory file by its path, and any ICE page.
- Persona: the product owner, who brings Garura into the project with one command.
- Scope: In: laying the parts of the chosen kind, the shared files, the memory tool and its guide, the tools, the settings file and Garura's instructions, keeping each file of the project's own as it was, and keeping the record with the version. Out: choosing the kind, the check, updating the choice, moving to a new version, each tool's shape, and the set-up after the install.

## Expectation
- Scenario: A bank's payments service has its own instructions file and a skill of its own named like one of Garura's. The product owner runs the one command with no version named. Garura is laid in the full kind: its guide goes beside the team's instructions file, the same-named skill is named in the report and left as it was, and the agents' shared files are in the shared folder. The record names every part, the kind, the tool and the version, and the report ends with the next step, Initialize.
- Done means: Someone other than the one who installed it compares the project's files before and after, and finds every file of the project's own as it was, every part the record names in the project, and every laid part's pointers leading to laid files; and a second install of the same version and kind through the other front door, into a copy of the project, gives the same parts and the same record.
