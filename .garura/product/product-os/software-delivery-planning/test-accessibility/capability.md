# Capability: Test accessibility

## Directional intent
Test accessibility, against the product profile's accessibility level and each surface's accessibility guideline: the running build is tested in the testing environment, by tools and by a person who uses it with a keyboard alone and with a screen reader, against the accessibility level the product profile commits to and the accessibility guideline of each declared surface, and each finding goes back to the developer or to a person.
Accessibility means that a person can use the product in the way they need to, for example with a keyboard and no mouse, with a screen reader, a tool that reads out what is on the screen, or with larger text. The product profile is the record of the product's shape and the quality levels it commits to. For accessibility it holds a level, one of none, low, medium, high and xhigh, and a pass bar: the standard that says when the product meets that level, and how it is checked, such as "WCAG 2.1 AA", which names an accessibility standard and the grade of it the product meets. Specify the product sets the profile, and each capability adds its own accessibility need under it. A surface is a place where a person or another system uses the product, such as a browser page, a mobile app, a command line or an endpoint another system calls. Manage surfaces declares each surface with its guidelines, what every design on it must handle; for a browser surface, one of them is "meeting the accessibility level the product commits to", and a guideline meets the profile's level and never changes it. In the product owner's words, Code → Validation "also needs to handle other forms of testing i.e. security and performance and accessibility, ux (responsive)", and the list he approved adds this capability as new. It runs those tests once the work is built and runs in the testing environment:
- With tools. On each declared surface a person opens, a part that is not the builder runs the tools that check what the pass bar, each capability's accessibility need and the surface's guideline say a tool checks, such as whether text stands out from its background or whether each field has a label a screen reader can read out.
- By a person. What a tool cannot check, such as whether each step of the slice can be done with a keyboard alone and whether a screen reader reads it out in a way a person can follow, a person who is not the builder checks by walking the slice end to end on its surface. A slice is an ordered group of features that one person can test end to end on one surface.
- The verdict. Each part of the pass bar, each capability's accessibility need and each surface's accessibility guideline gets a pass or a fail, each part not tested is named with its reason, and the verdict is a pass only when every part passes.
- The way back. Each finding goes back as a handoff plan: what a person cannot do, where, and the way back, never the test itself. It goes to the developer when the builder can fix it alone, and to a person when a person must decide.
- Again as the product changes. The tests run again after a fix, when more work is built, when an approved decision raises the accessibility level, and when a surface's accessibility guideline is updated, so that a pass stays true.

Where accessibility ends and the user experience begins is drawn by the yardstick. What the accessibility level, its pass bar, a capability's accessibility need or a surface's accessibility guideline names is tested here, even when it is about layout, such as text that must still read when a person makes it larger. What the surface's other properties and guidelines name, such as how a browser page lays out across screen sizes and the design system its screens are built from, and what the screen design from Design the work shows, is tested by Test the user experience on each surface. One run of a tool, or one walk by a person, may serve both; each capability reads only what its own yardstick names.
The review of each change is not repeated here. Check the code against its standards matches the review's accessibility rules, such as a picture with no text beside it, against the lines each change adds, and Build the work test first runs the tests inside the code by a separate check. This capability takes both records as evidence. The builder's own word is not evidence: "A builder believes its own work, so its opinion isn't evidence."
What the tests cover comes from memory first: the project's own code and memory, then Garura memory, the memory Garura keeps for the project, then Phoenix memory, the shared memory on the machine that every project draws from. Only when none of them has an answer is it researched, and what research finds is raised as a memory update, a proposed addition to memory, and used only after a person approves it. Nothing comes from what the AI agent knows by itself.
It matters to software delivery planning because that domain turns a business intent into working code that a check from the outside can prove. This capability is that check for the accessibility level the product commits to.

Features:
- Test the running build for accessibility with tools, in the testing environment (fn-test-accessibility-with-tools): once the built work runs in the testing environment, runs on each declared surface a person opens, by a part that is not the builder, the tools that check what the pass bar, each capability's accessibility need and the surface's accessibility guideline say a tool checks, and records each result with what was checked and where.
- Walk the running build with a keyboard alone and with a screen reader, in the testing environment (fn-walk-with-keyboard-and-screen-reader): once the built work runs in the testing environment, a person who is not the builder, named by the product owner, uses the slice end to end on its surface with a keyboard alone, with a screen reader and in any other way the surface's guideline names, and records what they could and could not do, where, and how they walked.
- Give the accessibility verdict, and send each finding to the developer or to a person (fn-send-accessibility-findings): gives one verdict for the built work against the profile's accessibility level and each surface's accessibility guideline, with a pass or a fail for every part, and sends each finding back as a handoff plan to the developer when the builder can fix it alone, or to the product owner when a person must decide.
- Test accessibility again as the product changes (fn-retest-accessibility): runs the tools and the walk again after a fix, when more work is built, when an approved decision raises the accessibility level and when a surface's accessibility guideline is updated, keeps each verdict, names what passed before and fails now, and sends a finding that keeps coming back to a person once the rounds the project allows are used up.

What is not built yet:
- Nothing tests a product against its accessibility level. Garura's own profile sets no accessibility level, no capability in its model has an accessibility need, and its one surface in use is a command line.
- No surface is declared, so no surface has an accessibility guideline yet, because Manage surfaces is not built.
- The old slice check, /validate-epic, is stale and waits for a rebuild. Its page-audit runner, a "frontend audit tool class (lighthouse, pa11y, axe).", ran only on a local page, "Code-level + local-page audits only (C5).", read every score of a page audit, an accessibility score among them, and the count of errors an accessibility tool printed, and compared each with a target written for the slice. Nothing in it used a keyboard alone or a screen reader, or named a part a person must check.
- The quality auditor, an agent, can "Run Lighthouse audits (if threshold defined and URL provided)", a page audit, when a check asks; only the stale plays ask.
- The quality-check runner, a skill that runs each quality check written down for a slice, is built, and no live play runs it. A check a person owns is skipped in view, never judged by it: "Human-owned cards are visibly skipped, never judged." Nothing does the person's part or records what the person found.
- The review of each change has accessibility rules, and it belongs to Check the code against its standards. They match words on the lines a change adds, such as a picture with no text beside it, rank accessibility as minor, and at most highlight: "Highlights without blocking."
- The scored quality check, built and never used, has accessibility items with fixed numbers, and reads a frontend standard file that is in no memory tier.
- No testing environment is declared or built, and nothing says which tests run in which environment, because Environment setup and Deployment design are not built.
- Memory holds one learning on accessibility, for any public screen, written for browser pages. No tier says what a named standard asks of a test part by part, which parts a tool can check, or how to test a mobile app, a command line or a coding agent's surface for accessibility.
- No play name is agreed for this work: the agreed names hold /validate-security and /validate-perf, and none for accessibility.

### Benefit hypothesis
- Who it serves: the product owner, who set the accessibility level through the product profile, reads the verdict, names who walks the build, and decides each finding that a person must decide; and the developer, who builds the code and gets back, as a handoff plan, each finding the builder can fix alone.
- What we believe: when the running build is tested in the testing environment, by tools and by a person, neither of them its builder, against the accessibility level and pass bar the profile commits to and each surface's accessibility guideline, a pass shows that people can use the product in the ways that level and guideline name, if the work stands on these rules:
  - The yardstick is the profile's accessibility level and pass bar, with each capability's accessibility need under it, and each declared surface's accessibility guideline, which never asks for less.
  - A part that no tool checked and no person walked never counts as a pass, and a tool's clean run never passes a part that a person must check.
  - The builder knows the level and the guidelines it must meet, but never gets the tests, their results or the verdict.
  - A handoff plan names what a person cannot do, where, and the way back, never the test, its rule, its id or its tool.
  - No test touches anything outside the testing environment.
- How we will know: two runs of the tools on the same built work give the same results; a second person who walks the same steps finds the same parts met and not met; every part of the pass bar, each capability's accessibility need and each surface's accessibility guideline has a pass, a fail or a reason it was not tested; each walk names who walked it and how; no test touched production; and no person finds, after a pass, a part of the product they cannot use in a way the level or the guideline names.
  - This is not tested today, because nothing tests accessibility.

### Boundary (In / Out / Never)
- In: testing the running build in the testing environment with tools, on each declared surface a person opens, for what the pass bar, each capability's accessibility need and the surface's accessibility guideline say a tool checks.
- In: a person who is not the builder walking the slice end to end on its surface with a keyboard alone, with a screen reader and in any other way the guideline names, for what a tool cannot check.
- In: giving the verdict against the profile's accessibility level and each surface's accessibility guideline, after taking the records of the review of each change and of the build's separate test run as evidence.
- In: sending each finding back as a handoff plan, to the developer or to a person.
- In: testing accessibility again as the product changes, when an approved decision raises the accessibility level, and when a surface's accessibility guideline is updated.
- Out: the review of each change against its standards, with the review's accessibility rules on the lines a change adds. Check the code against its standards owns it; this capability reads its record and never runs the same rules again.
- Out: the tests inside the code. Build the work test first runs them by a separate check, and this capability takes that check's record as evidence.
- Out: an accessibility line in a story's expectations, such as a form that can be sent with a keyboard alone. The slice's eval tests it, in Test what the product does, with evals the builder never sees.
- Out: the surface's other properties and guidelines, such as how a browser page lays out across screen sizes and the design system, and the screen design from Design the work. Test the user experience on each surface owns them.
- Out: testing security and performance. The other capabilities of Code → Validation own them. One run of a page-audit tool may give both an accessibility figure and a speed figure; a tool is not a capability, and the speed figure is Test performance's.
- Out: setting the accessibility level, its pass bar and each capability's accessibility need, and moving any of them, also when a law or a contract asks for more. Specify the product sets them, and only an approved decision moves them; this capability reads them and never writes them.
- Out: declaring each surface with its accessibility guideline, and updating it. Manage surfaces owns it, and this capability reads it.
- Out: which tests run in which environment. Deployment design owns it, and this capability reads it.
- Out: declaring and building the testing environment, with its data and its test accounts. Environment setup owns it.
- Out: fixing what fails. Build the work test first fixes a finding before the work is accepted, and Fix defects test first fixes one after.
- Out: recording a defect in the tracker, and making and running the plan, with the loops that run building and validation in rounds. Orchestration owns them.
- Never: test anything outside the testing environment: not production, not a builder's own machine, and no system the testing environment does not hold. The reason, in the product owner's words: "We are never touching production."; and a builder's machine "is not where the path's tests are counted".
- Never: give the accessibility tests, their results or the verdict to the builder or to any part that builds the work, or let the builder walk its own work. Only the handoff plan reaches the builder. The reason: "A builder believes its own work, so its opinion isn't evidence.", and a result checked after the work exists is a failure condition: "giving it to the builder only invites teaching-to-the-test."
- Never: skip, switch off or let through a finding, or loosen a test, to reach a pass. The reason: Code → Validation must not "weaken a check to pass", and "The box moves ONLY by an approved decision."
- Never: count a part that no tool checked and no person walked as a pass, or count a tool's clean run as a pass for a part a person must check. The reason: "An unmeasured bar is not a passed bar.", and the quality-check runner already holds that a check a person owns is never judged by a tool.
- Never: make a choice, such as what to check, with which tool or in which way, from what the AI agent knows by itself. The reason: a source in the project or in memory can be checked and read back, while the agent's own knowledge cannot.

### Guiding rules
- Against the profile and the surface, per product. What is tested comes from the product profile's accessibility level and pass bar, each capability's accessibility need and each declared surface's accessibility guideline, never from this capability. The reason: the approved list tests accessibility "against the product profile's accessibility level and each surface's accessibility guideline", and "The NUMBERS live in the product profile, per product — never in this KB."
- The profile's level is the floor. Each surface's guideline meets it and may add what its surface needs; a guideline that asks for less is named, and the profile's level is tested on that surface. The reason: the approved Manage surfaces rule: "A guideline meets the levels the profile commits to, such as an accessibility level, and never changes them.", and a guideline below it is "named as below the profile, and the profile's level stands."
- Every surface a person opens. Accessibility is tested on each declared surface where a person meets the product, a command line and a coding agent's surface among them, against that surface's own guideline; a surface where only another system meets the product, such as an endpoint, is not tested here. The reason: memory's one learning holds for "Any public or user-facing UI.", and memory's surface rule counts a command line as "a command-line entry point a human runs".
- How each part is checked comes from the bar. The pass bar, a need or the guideline says for each part whether a tool checks it or a person walks it; a part that does not say, and a surface whose guideline names nothing for accessibility, are named as not tested and go to the product owner. The reason: the profile's pass bar is "(the standard / how it's measured)", and Specify the product sets each need with "a target someone can measure and how it is checked".
- A tool's own score is not the verdict. Each result is compared with its part of the bar, and a page-audit score counts only when the pass bar names that score. The reason: the old slice check held that "Green is the entry condition, never the verdict".
- Not tested is never passed. A part no tool checked, a part no person walked, and a tool that could not run are fails, each named with its reason. The reason: "An unmeasured bar is not a passed bar."
- Not the builder. A part that is not the builder runs the tools, and a person who is not the builder walks the build, on a copy of the built work. The reason: "A builder believes its own work, so its opinion isn't evidence."
- The product owner names who walks. The person who walks is named for the project or for the run, and each walk records who walked, on which surface, which steps and in which way, so a second person can walk the same steps. The reason: the product owner decides each finding a person must decide, and a walk no one else can repeat proves nothing.
- The builder knows the level, never the tests. The accessibility level, its pass bar and each surface's accessibility guideline shape how the builder writes code, so it knows them; the tests, their results, the walks and the verdict are kept where no part that builds the work reads them. The reason, from the rule that divides the two: "Would knowing this change how the builder writes code?"
- What a person cannot do, where, and the way back. A handoff plan says what a person cannot do, on which surface and screen, in which way, such as with a keyboard alone, and what must be true again, as guidance, never code; it never names the test, its rule, its id, its tool or the figures measured. The reason: a handoff plan "never names the failure condition, its id or the check", and the builder gets no results.
- The builder only when it can fix it alone. A finding goes to the developer only when its way back is a change of the code the builder controls, from what it already has. One that needs judgment or authority the builder does not hold, such as a change of the design system's colours that every screen uses, of the screen design, of a part the builder does not control, of a surface's declaration or guideline, or of the accessibility level itself, goes to the product owner. When in doubt, a person. The reason: the recovery rule's test, "Can the builder fix this from information it already has, deterministically?", and the product owner's approval that he is "the one who gets a finding that changes the architecture".
- In the testing environment. The tools run, and the person walks, on a copy in the testing environment that Environment setup declares, with its made-up data and its own test accounts, never in production and never on a builder's own machine. The reason: the product owner's list recorded it for security and performance tests, "in the testing environment Environment setup declares, never in production.", and he approved the same for the eval and for Test performance; a builder's machine "is not where the path's tests are counted".
- Only a person moves the bar. A fail is fixed, or the product owner moves the accessibility level by an approved decision; a finding is never let through any other way. The reason: "The box moves ONLY by an approved decision."
- Records are evidence, not run again. The record of the review of each change and the record of the build's separate test run are taken as evidence. The reason, from the product owner's approved list: "BI-4 takes the record of BI-3's separate test run as evidence and does not run the same tests again."
- Rounds have an end. When the same finding comes back after the rounds the project allows, it goes to a person, not round again to the builder. How many rounds is a project setting. The reason: the old slice check stopped "after 3 rejections on the same epic", and "Everything that can be turned on or off lives in settings."
- The project's memory first, then Garura memory, then Phoenix memory, then research through a memory update a person approves. What nothing answers stays open, with no default, and is named as not tested. The reason: research is new knowledge that nobody has checked yet, and the person's approval is the check.
