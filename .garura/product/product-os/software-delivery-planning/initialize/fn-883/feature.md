# Feature: Update each project's own memory as Phoenix memory changes

## What it does
A person sets up many projects on one machine from the one Phoenix memory. Each project keeps only the blocks its own answers called for, and each run of Initialize in a project compares those blocks with Phoenix memory as it is now and names what changed, so the product owner takes a change into that project, and only that project, on a typed yes.
- Words this page uses. Phoenix memory is the one shared memory on a machine (the domain shelves, the standards, the templates) that every project on that machine draws from. A project's Garura memory is the project's own memory, kept in the project's own folders and read before Phoenix memory; it is built from only the part of Phoenix memory the project needs and is never a copy of a Phoenix file. A memory block is the relevant part of Phoenix memory that one setup answer selects, down to the part of a file: for example only the checkout part of the commerce knowledge for a project that needs checkout, the Java standards for a Java answer, the .NET standards for a .NET answer, or the React front-end standards for a React answer. The block's selection is the place in Phoenix memory where the part for that choice is kept (for example the folder of the Java standards, or the checkout part of the commerce shelf). A part is what a block takes from one Phoenix memory file: the sections of that file that speak to the answer. The brief is the summary Initialize shows the product owner, where they type yes or no.
- Initialize never takes a whole Phoenix file into the project, even when every section of it speaks to the answer: it reads the file through the memory tool and builds the project's own memory from what it read, written for the project and never a copy. This is the product owner's rule (in the review of the change that first recorded these pages, round 2), beside ADR 039 Decision 4. How a project's memory is written from a file is set in Build the project's memory (fn-project-memory), where it is not decided yet.
- Memory reaches a project in three steps, and this feature is the third. First, Phoenix memory reaches the machine: today the memory tool downloads it the first time a command needs it, and a Phoenix install, once per machine, is planned; Memory owns that step. Second, the Garura install runs once per project and lays only the pieces (the plays, agents, skills, tools and the memory tool) and no memory. Third, initialize runs in the project, asks the questions, and sets up the project's Garura memory from Phoenix memory with only the blocks the answers call for.
- It keeps each project's blocks its own. A person sets up Phoenix memory once on a machine and initializes many projects there, each with different answers, so two projects hold different blocks taken from the one Phoenix memory, and initializing one project never changes another project or Phoenix memory.
- It records, in the project, which blocks the project holds and which parts of Phoenix memory each was built from, as they were then, so the project can learn later that Phoenix memory changed. On each run, initialize compares those parts with Phoenix memory and names in the brief each block whose parts changed, so the product owner can have the block rebuilt from Phoenix memory as it is now. A re-run rebuilds the relevant part; it never copies the new Phoenix file. No install ever reaches into a project to do this.
- Examples, in different kinds of project:
  - On one machine, a shop's checkout service set up with Java and a bank's payments service set up with .NET: only the first holds the Java standards block, and only the second the .NET block.
  - A clinic's booking app holds the database block; when the database standards change in Phoenix memory, nothing in the app's memory changes until its next run names the change and the product owner says yes.
  - A shop whose checkout block was built from the checkout part of the commerce knowledge: when that part changes, the run rebuilds only what was built from it, and nothing from the rest of the file comes in.
- How it meets the capability: the capability's third check, "Two projects on one machine, initialized with different answers, hold different memory blocks taken from the one Phoenix memory", is met here, with the part of its last check that follows Phoenix memory as it changes.

Status: not built. The memory tool reads Phoenix memory only at its approved version, and its check of past decisions already names each one "whose source no longer says what it said", but nothing keeps a list of a project's blocks or compares them with Phoenix memory.

## Inputs / Outputs
- In: one project's confirmed setup answers (from Ask the setup questions, fn-setup-questions), which decide the blocks.
- In: Phoenix memory on the machine, read only through the memory tool. The tool's interface hides where Phoenix memory is kept: today a folder on the machine that the tool downloads to the first time a command needs it, and later a remote place; this feature does not change when that moves.
- In: on a later run, the project's own block list from the earlier run.
- Out: the project's own Garura memory, holding only the blocks its answers call for (the blocks are built through Build the project's memory, fn-project-memory).
- Out: the project's block list, kept in the project beside the blocks. For each block it holds the answer that selected it, the block's selection, and, for each part the block was built from, its place in Phoenix memory (the file and the part of it) and what lets a later run tell that the part changed. The selection is kept so that a later run can find a part Phoenix memory has added to the block.
- Out: on a later run, a plain list in the brief of each block that changed in Phoenix memory since it was built: the parts changed, added or taken out, each with the Phoenix file it is in, and the answer that selected the block.
- Out: when Phoenix memory cannot be reached, a plain message that says so, and no memory built.

## Rules & behavior
- The Garura install lays no memory. A project that has had the Garura install and no initialize run holds no Garura memory of its own, and initialize is the only part that sets it up.
- initialize reads Phoenix memory and writes only the project's own Garura memory. It never writes Phoenix memory and never writes another project's memory, because Phoenix memory is shared by every project on the machine and a write there from one project would change what the others draw from.
- A project takes a block only when one of its answers calls for it. Two projects with different answers (one Java, one .NET; one with a React front end, one with none) hold different blocks from the one Phoenix memory.
- How a project learns that a block changed. Each run of initialize reads through the memory tool, for each block in the list, the parts its selection finds in Phoenix memory now. A part the list holds that now reads differently is changed. A part the selection now finds that the list does not hold is added. A part the list holds that the selection no longer finds is taken out. The brief names each one under its block. The reason: it is asked that initialize "can run again to take in changes".
- Not decided: how a run tells that a part now reads differently from when it was built.
- A change is taken in only on the product owner's typed yes in that run's brief, because the blocks a project holds are its people's choice and a new standard can change what a review finds. The reason: Install and distribute must not "Change what a project's people changed without asking them."
- Not decided: whether the product owner says yes to each changed part or to each block as a whole.
- A yes rebuilds, adds or takes out what the project's Garura memory holds for that part, from what Phoenix memory holds now, and brings the block list up to date; it never copies the changed Phoenix file.
- A no leaves that part and its block-list entry as they were, so the next run names it again. The reason: Orchestration must not "Stop a person. Every gate has a way past it that records what's owed."
- The check runs only when initialize runs. No install and no other play changes a project's memory or checks its blocks, so a project's memory never changes in the middle of other work. A product owner who wants a Phoenix memory change runs initialize again (Update the setup as the project changes, fn-rerun-initialize). The reason: the install and initialize "never write the same files", and the capability's reliability need, "an install changes 0 files in any project's Garura memory".
- Phoenix memory reaching the machine again, or a second Garura install, changes no file in any project's Garura memory. Phoenix memory may change under a project, but the project's own memory changes only on its next initialize run, after the product owner's yes.
- When the memory tool cannot reach Phoenix memory (it says the tier is missing), initialize stops, builds and changes no project memory, and says in plain words that Phoenix memory could not be reached. An empty answer there would look like "no block fits" and leave the project with too little memory. It never takes memory from Garura's source or from another project instead, because installed parts read memory only through the memory tool.
- A block whose answer the product owner changed is no longer a change to take in: the re-run adds or takes out the whole block from the new answer (Update the setup as the project changes, fn-rerun-initialize, owns that), because the new answer, not Phoenix memory, decided it.

## Acceptance criteria
- Given a project after the Garura install and before initialize, when its Garura memory is read, then it holds no memory files.
- Given two projects on one machine, one answering Java and one answering .NET, when initialize runs in each, then only the first holds the Java standards block, only the second holds the .NET standards block, and both block lists name the same Phoenix memory as the source.
- Given a project already initialized, when initialize runs in a second project, then no file in the first project's Garura memory and no file in Phoenix memory changes.
- Given a project that took the database block, when Phoenix memory changes a part that block was built from, then no file in the project's Garura memory changes.
- Given a project that took the database block and a part that block was built from changed in Phoenix memory, when initialize next runs in the project, then its brief names the database block and the changed part, with the Phoenix file it is in.
- Given Phoenix memory added a part where the database block's selection looks, or no longer keeps one the block was built from, when initialize next runs in the project, then its brief names that part as added or taken out under the database block.
- Given a project whose checkout block was built from the checkout part of the commerce knowledge, when that part changes in Phoenix memory and the product owner types yes, then the project's Garura memory holds the rebuilt checkout part, none of the rest of the commerce file, and no whole Phoenix file.
- Given a brief that names a changed part in the database block, when the product owner says no, then the block and the block list are unchanged, and the next run names the same change again.
- Given an initialized project, when Garura is installed again in it, then no file in that project's Garura memory changes.
- Given a machine where the memory tool cannot reach Phoenix memory, when initialize runs, then it builds no memory and says that Phoenix memory could not be reached.

## Out of scope
- How Phoenix memory reaches the machine and is brought up to date, including the planned Phoenix install: Memory, in Standards, structure, settings and memory, owns it. This feature only reads what Phoenix memory holds.
- Laying the plays, agents, skills, tools and the memory tool in a project: Install into a project owns it, and it lays no memory.
- Which part of Phoenix memory each answer selects, building it into the project, and recording the answers in the product profile: Build the project's memory (fn-project-memory) owns it.
- Adding or taking out a whole block when an answer changes: Update the setup as the project changes (fn-rerun-initialize) owns it.
- How Garura's source memory reaches the Phoenix memory repository without hand copying, and promoting a person's answer or an approved memory update from a project up to Phoenix memory: Memory owns them, because both change what every project on the machine draws from.
