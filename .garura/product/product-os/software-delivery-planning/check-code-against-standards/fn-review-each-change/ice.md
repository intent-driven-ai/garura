## Intent
- Goal: Before a change is merged, a part that is not its builder reads which kinds of work the change holds, reviews each against its own standards, the review's rules that fit the project, the project's coding standards and the checks its code holds, and for each part that carries a design the architecture and the design in force as committed before the change, takes the record of the build's separate test run where it covers the change's code, and records each finding with the standard it rests on, the file, the line and its rank, each check that could not run with its reason, and each kind with nothing to check against.
- Limit: A design is read only from what was committed before the change, and the kinds of work only from what the change holds, never from a fixed list.
- Limit: A tool runs every check that needs no judgment; an agent that is not the builder judges only what no tool checks, and names the standard it rests on.
- Limit: The tests are not run again when the separate run's record covers the change's code, and no rule group the project's record skips runs.
- Fails if: A finding rests on what the change itself adds, or has no standard, file or line.
- Fails if: A check that could not run, or a kind with nothing to check against, is recorded as a pass.
- Fails if: The builder reviewed its own change, or the tests were run again over a separate run's record that covers the change's code.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the change, what it adds and what was committed before it; the review's rules for each kind of work and the project's record of the rule groups that fit it; the project's coding standards and the checks its code already holds; the architecture with its technology, the deployment design, the declared surfaces and the design of the work in force; and the record of the build's separate test run.
- Never read: the value of any secret, such as a password or a key; anything in production; and a plan's evals folder with the slice's hidden file, which only the eval reads.
- Persona: the product owner, who relies on every change being checked from outside before a person approves its merge.
- Scope: In: reading the kinds of work a change holds, running the tools the standards name, judging the parts that carry a design against what was committed before, and recording each finding. Out: raising and merging the change, the verdict and the handoff plans, the whole built work, choosing the rule groups, and writing any standard.

## Expectation
- Scenario: A school's timetable app gets a change that adds a printable week view and its tests. The review reads two kinds of work, the app's code and its tests. The record of the build's separate test run covers the change's code, so the tests are not run again. A tool matches the review's rules on the added lines and the project's linter runs, both clean. An agent reads the architecture as committed before the change and finds that the change adds a library for printing that the architecture's technology does not include, and records it with the architecture as its standard, the file and the line.
- Done means: Someone other than the reviewer reads the review's record beside the change and the standards as committed before it, and finds each kind of work named with its files, each finding with the standard it rests on, the file and the line, each check that could not run named and not passed, no standard taken from the change itself, and the separate test run's record named where it covered the change.
