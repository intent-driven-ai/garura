## Intent
- Goal: Every change, before it is merged, and the whole of each piece of built work, once it is built, are checked by a part that is not their builder against the standards the project set before the change: the review's rules that fit the project, the project's coding standards and the checks its code already holds, the architecture and the design of the work in force, and the product profile's maintainability level with its reliability level where the pass bar names a check of the code; every standard touched gets a result with where it was checked and what it rests on; one verdict follows one fixed rule over the findings, decided by a person or by that rule as the project's setting says; each finding goes back as a handoff plan to the developer when the builder can fix it alone, to the test writer when it is about a test, or to the product owner when a person must decide; and the checks run again as the product and its standards change.
- Limit: The standards come only from what the project set before the change, read and never set, and never from the change's own new content or from what the AI agent knows by itself.
- Limit: A tool checks what needs no judgment; an agent that is not the builder judges only what no tool checks, and each finding names the standard it rests on and the file and line it breaks.
- Limit: The builder never gets the checks, their results, a finding's rule or id, or the verdict; only the handoff plan reaches it, with what is wrong, where and the way back.
- Limit: The record of the build's separate test run is taken as evidence and the same tests are not run again; opening, committing, raising and merging the change, with the person's yes on the merge, stay with Ship every change the same way.
- Fails if: The verdict is a pass while a standard the change or the built work touches failed or was not checked, or a standard was taken from the change under review.
- Fails if: The builder reviewed its own change, or was given a check, its result, a finding's rule or id, or the verdict.
- Fails if: A finding that needs a person's judgment or authority, such as a change of the architecture, the deployment design, an environment, a standard or a level, went to the developer, or a finding about a test went to the builder.
- Fails if: The same findings gave two different verdicts, or a person's decision that differs from the fixed rule's verdict is not on record with each finding it left open.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the change and what it adds, or the whole built work; what was committed before the change; the review's rules and the record of the rule groups that fit the project; the project's coding standards and the checks its code already holds, such as its linter settings; the architecture with its technology, the deployment design, the declared surfaces and the design of the work in force, with their confirmed updates; the product profile's maintainability and reliability levels with their pass bars and each capability's needs; the record of the build's separate test run; the project's settings for who decides the review and for rounds; and the recovery rule.
- Never read: the value of any secret, such as a password or a key; anything in production, such as its data or its traffic; and a plan's evals folder with the slice's hidden file, which only the eval reads.
- Persona: the product owner, who relies on every change being checked before a person approves its merge, reads the verdict, decides the review when the project's setting asks a person, and decides each finding a person must decide; the developer gets back, as a handoff plan, each finding the builder can fix alone, and its test writer each finding about a test.
- Scope: In: reviewing each change against the standards for each kind of work it holds, checking the whole built work against the coding standards, the architecture, the design and the maintainability and code-level reliability levels, the verdict, the handoff plans, and checking again as the product and its standards change. Out: opening, committing, raising and merging the change, the tests inside the code, what the product does against each story, security, performance, accessibility and the user experience, setting any standard or level, writing a project's coding standards, fixing, recording defects and running the plan.

## Expectation
- Scenario: A clinic's booking app gets a change that adds a search for a patient's visits and a cancel button. A part that is not the builder reviews it: the record of the build's separate test run covers the change's code, so the tests are not run again; the project's linter runs; a tool matches the review's rules on the added lines and finds the search query built by joining in what the patient typed, a finding of the rank that blocks; and an agent, reading the design of the work in force, finds that the cancel button reads the bookings database straight from the screen's code, where the design says the booking service does. The verdict is not a pass. The developer gets two handoff plans: in the visit search, what the patient types is joined into the database query, so a typed command could reach the database, and the search must pass what was typed as a value only; and the cancel button must go through the booking service, as the design says. Neither names a rule, an id or a tool. After the fix the change is reviewed again and passes, and the product owner gives the merge their yes in Developer tooling.
- Done means: Someone other than the reviewer reviews the same change by the same standards and gets the same verdict and the same blocking findings, and finds every finding naming the standard it rests on and where, no standard counted as passed that no check ran on, the separate test run's record named and the tests not run again, and each handoff plan sent where the recovery rule's test says, with no check, rule, id or tool in it.
