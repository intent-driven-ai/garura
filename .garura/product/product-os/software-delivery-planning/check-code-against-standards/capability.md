# Capability: Check the code against its standards

## Directional intent
Check the code against its standards: every change, before it is merged, and the whole of each piece of built work, are checked by a part that is not their builder against the standards the project set before the change, and each finding goes back to the developer or to a person.
The code here is what a project keeps in its repository and builds from: the code it runs, its tests and its settings, and the documents, decision records, product model pages and memory written with them. For a coding agent's harness, the plays, skills and agents that tell a coding agent how to work, such as Garura, those are its code. A change is one piece of work raised for review and merged on its own, such as a pull request on GitHub. A standard is what the project decided its code must keep to, before the change was made: the review's rules for each kind of work, the project's own coding standards, the architecture with its technology and the design of the work in force, and the product profile's maintainability and reliability levels. The product profile is the record of the product's shape and the quality levels it commits to, each with a pass bar, the standard or measure that says when the product meets that level. In the product owner's words, Code → Validation "is about testing", and the list he approved renamed "Validate its own code" to this name, "because the old name read like the builder grading itself, which BI-4's Must not forbids." Build the work test first hands the check here: "Out: checking the code against the project's standards. Check the code against its standards, in Code → Validation, owns it; the build follows the standards while it writes."
- Each change. Before a change is merged, a part that is not its builder reads which kinds of work the change holds and reviews each against its standards. A tool matches the review's rules against the lines the change adds; the checks the project's code already holds, such as its linter, run; and for a part that carries a design, an agent that is not the builder judges the change against the design decided before it, read from what was committed before the change. This is built: the review of each change, /check-change, runs on every change in Garura's own repository.
- The whole built work. Once a piece of work is built, the whole of its code, not only one change's lines, is checked against the project's coding standards, the architecture and the design in force, and the profile's maintainability level, with its reliability level where the pass bar names a check of the code. This is not built.
- The verdict. One fixed rule over the findings gives the verdict, so the same findings always give the same verdict; a standard that was not checked is named with its reason and is never a pass. A project setting says whether a person decides the review or the rule's verdict stands.
- The way back. Each finding goes back as a handoff plan: what is wrong, where it is and the way back, never the check itself. It goes to the developer when the builder can fix it alone, to the test writer, who writes the tests apart from the builder, when it is about a test, and to a person when a person must decide.
- Again as the product changes. A change is reviewed again after a fix, and the whole built work is checked again when more work is built, when a standard changes, and when an approved decision raises a level, so that a pass stays true.

Landing the change is not done here. Opening the branch, committing, raising the change with its self-review, and merging it with a person's yes stay with Ship every change the same way, in Developer tooling, whose merge reads this capability's verdict first. The tests inside the code are not run again here: Build the work test first runs them by a separate check, and this capability takes that check's record as evidence. The other capabilities of Code → Validation test security, performance, accessibility and the user experience against their own yardsticks, and each takes this capability's record of the review's rules on the lines each change adds as evidence. The builder's own word is not evidence: "A builder believes its own work, so its opinion isn't evidence."
What the checks use comes from memory first: the project's own code and memory, such as its coding standards and the checks it already holds, then Garura memory, the memory Garura keeps for the project, then Phoenix memory, the shared memory on the machine that every project draws from. Only when none of them has an answer is it researched, and what research finds is raised as a memory update, a proposed addition to memory, and used only after a person approves it. Nothing comes from what the AI agent knows by itself.
It matters to software delivery planning because that domain turns a business intent into working code that a check from the outside can prove. This capability is that check for the standards the code must keep to.

Features:
- Review each change against the standards for what it holds (fn-review-each-change): before a change is merged, a part that is not its builder reads which kinds of work the change holds, runs the checks the standards of each kind name on what the change adds, judges each part that carries a design against what was committed before the change, and records each finding with the standard it breaks and where.
- Check the whole built work against its standards and the profile's levels (fn-check-whole-built-work): once a piece of work is built, checks the whole of its code, not only one change's lines, by a part that is not the builder, against the project's coding standards, the architecture and the design in force, and the profile's maintainability level, with its reliability level where the pass bar names a check of the code.
- Give the verdict on the code, and send each finding to the developer or to a person (fn-send-code-findings): gives one verdict for each change and for the whole built work by one fixed rule over the findings, decided by a person or by that rule as the project's setting says, and sends each finding back as a handoff plan to the developer when the builder can fix it alone, to the test writer when it is about a test, or to the product owner when a person must decide.
- Check the code again as the product and its standards change (fn-recheck-code): reviews a change again after a fix, checks the whole built work again when more work is built, when a standard changes and when an approved decision raises a level, keeps each verdict, names what passed before and fails now, and sends a finding that keeps coming back to a person once the rounds the project allows are used up.

What is not built yet:
- The review of each change checks against its own rules and industry practice only. For a project's code its standard is "industry best practice"; no review reads a project's own coding standards, its architecture or the design of its work. The design is checked only for Garura's own harness and memory.
- It runs every rule group, a set of the review's rules that check one kind of thing, such as a database, on every project. Initialize, which sets a project up for Garura after the install, records which rule groups fit a project, and changing the review to read that record is a later story (#862).
- Its rule table matches names and words on the lines a change adds and the names of the files it changes, with "No LLM judgment."; it measures nothing. A rule whose evidence asks for a figure, such as a function's complexity, matches only a file's name. In Garura's own repository its code rules check none of the scripts inside plays and skills, which it classes as prose (#890, #535).
- In practice its agent also reads the code against the review's rubric for code and ranks each finding, how serious it is, by the table's words; these findings carry no rule of the table, and a second run may not find the same.
- It runs the tests whenever a change touches them. Nothing reads the record of the build's separate test run, which is not built.
- It has no standard for product model pages (#870), it reviews the agents' working records along with the change (#939), and it goes on when its rules cannot be found (#974).
- A tool that did not run is recorded and is never a pass, but the fixed rule can still approve the change.
- Its findings come out as an id, a class and a short label, each naming its rule (#902); they are posted on the change and kept on the change's branch, where a part that builds the work could read them. Nothing writes a handoff plan, or sends a finding to the developer or to a person by who can fix it. One severity for findings and defects is planned (#934).
- Each new run of the review writes over the last one's record; earlier rounds are kept only where someone saved them by hand, and nothing counts rounds.
- In Garura's own repository the setting that turns off the person's decision still names the review's old play name, so a person decides there (#772).
- Nothing checks the whole built work. The old check of a whole slice, an ordered group of features that one person can test end to end, /validate-epic, is stale and waits for a rebuild; it compared tool results with the product profile's floors. The quality auditor's full run, the build, the type check, the linter and the unit tests with their coverage, is used only by stale plays. The runner for a slice's written quality checks is built, and no live play runs it.
- Garura's own profile sets maintainability and reliability at medium, with pass bars that name tests and linters; nothing checks the code against them.
- No memory tier holds a project's coding standards, and no approved capability writes them. The technology shelves in Phoenix memory are learnings for choosing a technology, and no live review reads them.
- /validate-work and /validate-slice, the play names agreed for this work, are names only.

### Benefit hypothesis
- Who it serves: the product owner, who relies on every change being checked before a person approves its merge, reads the verdict, decides the review when the project's setting asks a person, and decides each finding that a person must decide; and the developer, who builds the code and gets back, as a handoff plan, each finding the builder can fix alone, with each finding about a test going to its test writer.
- What we believe: when every change, and the whole of each piece of built work, are checked by a part that is not their builder against the standards the project set before the change, a pass shows that the code keeps to those standards, if the work stands on these rules:
  - The yardstick is the standards set before the change, read and never set, and never the change's own new content.
  - A tool checks what needs no judgment, and an agent judges only the rest, each finding naming the standard it breaks and where.
  - A standard that was not checked never counts as a pass, and a tool's clean run is not the verdict.
  - The builder knows the standards it must meet, but never gets the checks, their results or the verdict.
  - A handoff plan names what is wrong, where and the way back, never the check, its rule, its id or its tool.
- How we will know: two reviews of the same change by the same standards give the same verdict and the same blocking findings; every finding names the standard it breaks and where; every standard the change touches has a result or a reason it was not checked; no change is merged without a review on record; and no person finds, after a pass, a break of a standard the review covers.
  - This is tested today only in part: the tool that matches the rule table gives the same findings on every run of the same change; the agent's findings are not compared across runs.

### Boundary (In / Out / Never)
- In: reviewing each change before it is merged, whatever kinds of work it holds, each against its own standards, by a part that is not its builder.
- In: checking the whole built work of a piece of work against the project's coding standards, the architecture and the design in force, and the profile's maintainability level, with its reliability level where the pass bar names a check of the code.
- In: running through tools the checks the standards name, and judging by an agent only what no tool checks, each finding with the standard it rests on.
- In: giving the verdict, after taking the record of the build's separate test run as evidence.
- In: sending each finding back as a handoff plan, to the developer, to the test writer, or to a person.
- In: checking again after a fix, when more work is built, when a standard changes, and when an approved decision raises a level.
- Out: opening the branch, committing, raising the change with its self-review, and merging it with a person's yes. Ship every change the same way, in Developer tooling, owns them; its merge reads this capability's verdict.
- Out: the tests inside the code. Build the work test first runs them by a separate check, and this capability takes that check's record as evidence.
- Out: what the product does, against each story's goals and expectations. The slice's eval tests it, in Test what the product does, with evals the builder never sees.
- Out: testing security, performance, accessibility and the user experience on each surface against the profile's levels, the surfaces and the screen design. The other capabilities of Code → Validation own them, and take this capability's record as evidence.
- Out: setting the standards: the profile's levels and each capability's needs (Specify the product, moved only by an approved decision), the architecture (Design the technology and architecture), the design of the work (Design the work), the surfaces (Manage surfaces), the deployment design and the environments, and the review's rules with which of them fit a project (memory, and Initialize's record). This capability reads them and never writes them.
- Out: writing a project's coding standards. No approved capability writes them yet; the build follows them, and this capability reads them.
- Out: fixing what fails. Build the work test first fixes a finding before the work is accepted, and Fix defects test first fixes one after.
- Out: recording a defect in the tracker, and making and running the plan, with the loops that run building and validation in rounds. Orchestration owns them.
- Never: let the builder review its own change, or take the builder's word as a check. The reason: "A builder believes its own work, so its opinion isn't evidence.", and Code → Validation must not "Let a builder grade itself".
- Never: take a standard from the change under review. The reason: "The guiding rule: the change under review is never its own standard.", "otherwise the branch grades its own homework."
- Never: give the checks, their results, a finding's rule or id, or the verdict to the builder or to any part that builds the work. Only the handoff plan reaches the builder. The reason: a result checked after the code exists is a failure condition, and "giving it to the builder only invites teaching-to-the-test."
- Never: skip, switch off or loosen a check, or let a finding through, to reach a pass. The reason: Code → Validation must not "weaken a check to pass", and "The box moves ONLY by an approved decision."
- Never: count a standard that no check ran on as a pass. The reason: "An unmeasured bar is not a passed bar.", and the review's own rule for a tool that did not run: "Neither is a pass, and neither stops the review."
- Never: make a choice, such as which rule fits, what a finding's rank is or whether code keeps to a design, from what the AI agent knows by itself. The reason: a source in the project or in memory can be checked and read back, while the agent's own knowledge cannot.

### Guiding rules
- Against the standards set before the change, per project. What is checked comes from the review's rules that fit the project, the project's coding standards and the checks its code holds, the architecture and the design in force, and the profile's levels, never from this capability; a learning in memory that no owner took as the project's standard, such as a technology shelf's advice on which library fits, is not a standard. The reason: Build the work test first hands over "checking the code against the project's standards", the design is made "against the project's standards, which Spec → Design sets for the whole project", and the review's guiding rule is "the change under review is never its own standard."
- The rules that fit the project. The review runs only the rule groups the project's record keeps, names the groups it skipped, and keeps a group no answer speaks to. The reason: "a review in that project runs only the rule groups that fit it", and "a group skipped by mistake hides real findings".
- The architecture and the design in force. Code is checked against the architecture with its technology and against the design of the work as last confirmed; code that departs from either with no confirmed update is a finding for the product owner. The reason: each slice "is then designed and built on the project's architecture, and does not choose its own.", and "From its confirmation, the updated design is the one in force."
- The profile's levels, per product. Maintainability is checked against its level, its pass bar and each capability's maintainability need; reliability only where its pass bar or a capability's reliability need names a check of the code; a part that can only be measured on the running product is named as not checked here and goes to the product owner. The reason: the numbers live in the product profile, per product, and "The box moves ONLY by an approved decision."
- A tool checks, an agent judges only the rest. A tool runs every check that needs no judgment; an agent that is not the builder judges only what no tool checks, such as whether code keeps to a design, and each judgment names the standard it rests on, from a committed source, and the file and line it breaks. The reason: the rule table is matched with "No LLM judgment." and gives the same findings on every run, while an agent's judgment can be checked only against the standard it names.
- One fixed rule gives the verdict. The same findings always give the same verdict. What blocks follows each finding's rank in the rank table in force, and a profile pass bar may make more block; a standard that was not checked makes the verdict not a pass. The reason: the verdict rule reads the findings with "no LLM judgment.", and "An unmeasured bar is not a passed bar."
- A tool's own pass is not the verdict. Each result is compared with its standard. The reason: the old slice check held that "Green is the entry condition, never the verdict".
- Nothing to check against is said plainly. When the project holds no standard for a kind of work, or the profile sets no level, the verdict names it, and that part is neither a pass nor a fail; when the review's rules cannot be found at all, the review stops and says what is missing. The reason: the product owner approved the same for performance, "neither a pass nor a fail", and "It should stop and say the rules are missing."
- Records are evidence, not run again. When the record of the build's separate test run covers the code the change holds, the tests are not run again; when no such record is there, as for a change made outside the build, the tests run once, through a tool, by a part that is not the builder, and the verdict says no separate run was on record. The reason, from the product owner's approved list: "BI-4 takes the record of BI-3's separate test run as evidence and does not run the same tests again."
- Who decides the review is a project setting. With the setting off, the fixed rule's verdict is the verdict, recorded and shown as the harness's own, not a person's; with it on, a person who is not the builder decides, and when that person's decision differs from the rule's, the record keeps both and names each finding left open. Either way the merge waits for a person's yes in Developer tooling. The reason: "Everything that can be turned on or off lives in settings.", and "The merge proceeds solely on the typed approval".
- The builder knows the standards, never the checks. The coding standards, the architecture, the design and the levels shape how the builder writes code, so it has them; the checks, their results, the findings' rules and ids and the verdict are kept where no part that builds the work reads them. The reason, from the rule that divides the two: "Would knowing this change how the builder writes code?"
- What is wrong, where, and the way back. For people, each finding says in plain words what is wrong, where, what it leads to and its rank, with the standard it rests on after it; the handoff plan for the builder says what is wrong, where and what must be true again, as guidance, never code, and never names the check, its rule, its id or its tool. The reason, in the product owner's words: "A defect needs to have a problem statement clearly defined.", "Where is the problem happening, and what would it lead to?"; and a handoff plan "never names the failure condition, its id or the check".
- The builder only when it can fix it alone. A finding goes to the developer only when its way back is a change of the code the builder controls; a finding about a test goes to the test writer; one that needs judgment or authority the builder does not hold, such as a change of the architecture, the deployment design, an environment, a standard or a level, goes to the product owner. When in doubt, a person. The reason: the recovery rule's test, "Can the builder fix this from information it already has, deterministically?", "Only the test writer changes, adds or takes out a test", and the product owner's approval with Test security of "the line on a finding that changes the architecture, the deployment design or an environment settled as the product owner's".
- Only a person moves the yardstick. A finding is fixed, or a person confirms an update of the standard it rests on through its owner, or a person decides the review on record; a finding is never let through any other way. The reason: the architecture: "An agent proposes each choice and a person confirms it."; the design: "the technical lead confirms or changes each choice"; the levels: "the box moves only by an approved decision."
- Rounds have an end. When the same finding comes back after the rounds the project allows, it goes to a person, not round again to the builder. How many rounds is a project setting. The reason: the old slice check stopped "after 3 rejections on the same epic", and "Everything that can be turned on or off lives in settings."
- The project's memory first, then Garura memory, then Phoenix memory, then research through a memory update a person approves. What nothing answers stays open, with no default, and is named as not checked. The reason: research is new knowledge that nobody has checked yet, and the person's approval is the check.
