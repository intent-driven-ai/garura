# Capability: Test security

## Directional intent
Test security, against the product profile's security level: the built work is tested for security, at rest and while it runs in the testing environment, against the security level the product profile commits to, and each finding goes back to the developer or to a person.
The product profile is the record of the product's shape and the quality levels it commits to. For security it holds a level, one of none, low, medium, high and xhigh, and a pass bar: the standard or the measure that says when the product meets that level. A pass bar may name a security standard with no serious findings allowed, or say what must never happen, such as a write to the team's tracker before a person's typed yes. Specify the product sets the profile, and each capability adds its own security need under it: a level, a target someone can measure, and how it is checked. In the product owner's words, Code → Validation "also needs to handle other forms of testing i.e. security and performance and accessibility, ux (responsive)", and he moved the planned security testing here from Validation → Run. This capability runs those tests once the work is built:
- The code at rest. The whole built code is tested for weaknesses in how it is written, the libraries it uses are tested for versions with known weaknesses, and the code, its settings and the records of the build are checked for any secret's value, such as a password or a key.
- The running build. In the testing environment, on the product's declared surfaces, it tries what the pass bar and each capability's security need say to try, the way a person or another system meets the product there. A surface is a place where a person or another system uses the product, such as a browser page, a command line or an endpoint another system calls.
- The verdict. Each part of the pass bar and each capability's security need gets a pass or a fail, each part not tested is named with its reason, and the verdict is a pass only when every part passes.
- The way back. Each finding goes back as a handoff plan: the weakness, where it is and the way back, never the test itself. It goes to the developer when the builder can fix it alone, and to a person when a person must decide.
- Again as the product changes. The tests run again after a fix, when more work is built, and when an approved decision raises the security level, so that a pass stays true.

The review of each change is not repeated here. Check the code against its standards matches the review's security rules against the lines each change adds, and Build the work test first runs the tests inside the code by a separate check. This capability takes both records as evidence. The builder's own word is not evidence: "A builder believes its own work, so its opinion isn't evidence."
What the tests cover comes from memory first: the project's own code and memory, such as the security tools its settings already name, then Garura memory, the memory Garura keeps for the project, then Phoenix memory, the shared memory on the machine that every project draws from. Only when none of them has an answer is it researched, and what research finds is raised as a memory update, a proposed addition to memory, and used only after a person approves it. Nothing comes from what the AI agent knows by itself.
It matters to software delivery planning because that domain turns a business intent into working code that a check from the outside can prove. This capability is that check for the security level the product commits to.

Features:
- Test the built code, its settings and its libraries for security weaknesses (fn-test-code-security): once the work is built, tests the whole built code at rest, by a part that is not the builder, for weaknesses in how it is written, for libraries with known weaknesses and for any secret's value, and compares each result with the profile's pass bar and each capability's security need.
- Test the running build for security in the testing environment (fn-test-running-security): once the built work runs in the testing environment, tries on its declared surfaces what the pass bar and each capability's security need say to try, with the environment's made-up data and test accounts, and never touches anything outside that environment.
- Give the security verdict, and send each finding to the developer or to a person (fn-send-security-findings): gives one verdict for the built work against the profile's security level, with a pass or a fail for every part of the pass bar and each capability's security need, and sends each finding back as a handoff plan to the developer when the builder can fix it alone, or to the product owner when a person must decide.
- Test security again as the product changes (fn-retest-security): runs the security tests again after a fix, when more work is built, and when an approved decision raises the security level, keeps each verdict, names what passed before and fails now, and sends a finding that keeps coming back to a person once the rounds the project allows are used up.

What is not built yet:
- Nothing tests a product against its security level. Garura's own profile sets security at medium, with a pass bar that is itself a test of the running product: "no tracker or mapping write before the typed yes, on a test GitHub organization"; nothing runs it.
- The one security check that runs today is the review of each change, and it belongs to Check the code against its standards. A script matches the review's security rules against the lines a change adds, with "No LLM judgment.", and any finding of the most serious rank rejects the change. It matches names and words and runs no scanner: its rule for the libraries asks for "file, cve-list", a list of known weaknesses, but matches only the name of the file that lists them, so nothing scans the libraries. Three defects are open: #438 (planning pages rejected as security defects), #890 (scripts in plays and skills never checked as code) and #535 (the review does not know what the project is).
- The old slice check, /validate-epic, is stale and waits for a rebuild. It tested security at the level of the code only: "static analysis, lint, dependency scans — never penetration-style probing", through a family of tool runners, and compared the results with the profile's bars. The quality auditor, an agent, can run a scan of the libraries and a static security scan when it is asked; only the stale plays ask.
- Nothing tests a running build for security. No testing environment is declared or built, and nothing says which tests run in which environment, because Environment setup and Deployment design are not built.
- Memory holds no rule for what a security test must cover, for any kind of product. No tier has a shelf of security standards, and the scored quality check, built and never used, names three security standard files that are in no tier. So what a pass bar that names a security standard asks of a test is not decided.
- /validate-security, the play name agreed for this work, is a name only.

### Benefit hypothesis
- Who it serves: the product owner, who set the security level through the product profile, reads the verdict, and decides each finding that a person must decide; and the developer, who builds the code and gets back, as a handoff plan, each finding the builder can fix alone.
- What we believe: when the built work is tested at rest and running, by a part that is not its builder, against the security level and pass bar the profile commits to, a pass shows that the product meets that level, if the work stands on these rules:
  - The yardstick is the profile's security level and pass bar, with each capability's security need under it.
  - A part of the pass bar that no test measured, and a test that could not run, never count as a pass.
  - The builder knows the level it must meet, but never gets the tests, their results or the verdict.
  - A handoff plan names the weakness, where it is and the way back, never the test, its rule or its id.
  - No test touches anything outside the testing environment, and no record holds a secret's value.
- How we will know: two runs on the same built work give the same verdict; every part of the pass bar and each capability's security need has a pass, a fail or a reason it was not tested; no record holds a secret's value; no test touched production; and no person finds, after a pass, a weakness that the pass bar covers.
  - This is not tested today, because nothing tests security.

### Boundary (In / Out / Never)
- In: testing the whole built code at rest: its own weaknesses, the libraries it uses for known weaknesses, and the code, its settings and the records of the build for any secret's value.
- In: testing the running build in the testing environment, on its declared surfaces, for what the pass bar and each capability's security need say to try.
- In: giving the verdict against the profile's security level, after taking the records of the review of each change and of the build's separate test run as evidence.
- In: sending each finding back as a handoff plan, to the developer or to a person.
- In: testing security again as the product changes, and when an approved decision raises the security level.
- Out: the review of each change against its standards, with the review's security rules on the lines a change adds. Check the code against its standards owns it; this capability reads its record and never runs the same rules again.
- Out: the tests inside the code. Build the work test first runs them by a separate check, and this capability takes that check's record as evidence.
- Out: a security line in a story's expectations. The slice's eval tests it, in Test what the product does, with evals the builder never sees.
- Out: testing performance, accessibility and the user experience on each surface. The other capabilities of Code → Validation own them.
- Out: setting the security level, its pass bar, each capability's security need and the compliance needs, and moving any of them. Specify the product sets them, and only an approved decision moves them; this capability reads them and never writes them.
- Out: where secrets and settings are kept, and which tests run in which environment. Deployment design owns them, and this capability reads them.
- Out: declaring and building the testing environment, with its data and its test accounts. Environment setup owns it.
- Out: fixing what fails. Build the work test first fixes a finding before the work is accepted, and Fix defects test first fixes one after.
- Out: recording a defect in the tracker, and making and running the plan, with the loops that run building and validation in rounds. Orchestration owns them.
- Out: keeping a secret's value out of each commit, and landing the change. Ship every change the same way, in Developer tooling, owns them.
- Never: test anything outside the testing environment: not production, not a builder's own machine, and no system the testing environment does not hold. The reason, in the product owner's words: "We are never touching production."; and the old slice check went further and tried no running system at all: "No penetration-style probing of running systems." This capability tries a running build only in the testing environment, where it was set up to be tested.
- Never: write a secret's value into a finding, the verdict, a handoff plan or a log. The reason: people and agents read these records, "so a secret written there is no longer secret."
- Never: give the security tests, their results or the verdict to the builder or to any part that builds the work. Only the handoff plan reaches the builder. The reason: "security scan results" are checked after the work exists, and "giving it to the builder only invites teaching-to-the-test."
- Never: skip, switch off or let through a finding, or loosen a test, to reach a pass. The reason: Code → Validation must not "weaken a check to pass", and "The box moves ONLY by an approved decision."
- Never: count a part of the pass bar that no test measured as a pass. The reason: "An unmeasured bar is not a passed bar."
- Never: make a choice from what the AI agent knows by itself. The reason: a source in the project or in memory can be checked and read back, while the agent's own knowledge cannot.

### Guiding rules
- Against the profile, per product. The pass bar, its numbers and any standard it names come from the product profile and each capability's security need, never from this capability. The reason: the approved list tests security "against the product profile's security level", and Specify the product sets each capability's need with "a target someone can measure and how it is checked".
- A tool's own pass is not the verdict. Each result is compared with the pass bar, and a weakness the pass bar does not allow fails even when the tool's own check passes. The reason: the old slice check held that "Green is the entry condition, never the verdict".
- Not tested is never passed. A part of the pass bar that no test measured, and a test that could not run, are fails, each named with its reason. The reason: "An unmeasured bar is not a passed bar."
- Not the builder. A part that is not the builder runs the tests, on a copy of the built work. The reason: "A builder believes its own work, so its opinion isn't evidence."
- The builder knows the level, never the tests. The security level, its pass bar and the security rules of the architecture and of the deployment design shape how the builder writes code, so it knows them; the tests, their results and the verdict are kept where no part that builds the work reads them. The reason, from the rule that divides the two: "Would knowing this change how the builder writes code?"
- The weakness, where it is, and the way back. A handoff plan says what is weak in the product, where it is, and what must be true again, as guidance, never code, and never names the test, its rule, its id or its tool. The reason: a handoff plan "never names the failure condition, its id or the check", and a weakness in the code cannot be fixed without knowing where it is.
- The builder only when it can fix it alone. A finding goes to the developer only when its way back is a change of the code the builder controls, from what it already has. One that needs judgment or authority the builder does not hold, such as a change of the architecture, of the deployment design or of an environment, a secret to change where it is kept, or the security level itself, goes to the product owner. When in doubt, a person. The reason: the recovery rule's test, "Can the builder fix this from information it already has, deterministically?", and its rule that "any irreversible / outward-facing decision" needs a person.
- No secret's value, ever. A test that needs a secret, such as a test account's password, takes it at run time from where the deployment design keeps the testing environment's secrets, and a finding names only where a secret's value was found. The reason: the deployment design "names only where each secret is kept", and the old release play read secrets so that "no secret literal appears in the logs, the deploy record, or the repo."
- In the testing environment. The running build is tested on a copy in the testing environment that Environment setup declares, with its made-up data and its own test accounts, never in production and never on a builder's own machine. The reason: the assumption recorded with the product owner's list, that the security tests of Code → Validation run "in the testing environment Environment setup declares, never in production.", and a builder's machine "is not where the path's tests are counted".
- Only a person moves the bar. A fail is fixed, or the product owner moves the security level by an approved decision; a finding is never let through any other way. The reason: "A capability need above the box stops for the product owner, and the box moves only by an approved decision."
- Records are evidence, not run again. The record of the review of each change and the record of the build's separate test run are taken as evidence. The reason, from the product owner's approved list: "BI-4 takes the record of BI-3's separate test run as evidence and does not run the same tests again."
- Rounds have an end. When the same finding comes back after the rounds the project allows, it goes to a person, not round again to the builder. How many rounds is a project setting. The reason: the old slice check stopped "after 3 rejections on the same epic", and "Everything that can be turned on or off lives in settings."
- The project's memory first, then Garura memory, then Phoenix memory, then research through a memory update a person approves. What nothing answers stays open, with no default, and is named as not tested. The reason: research is new knowledge that nobody has checked yet, and the person's approval is the check.
