# Capability: Environment setup

## Directional intent
Which environments exist, how many, and how each is set up.
An environment is one place where a copy of the project runs. This capability declares which environments the project has and how each one is set up, and it builds and manages each one on its own when a deployment to it is needed. A deployment is a change put on an environment. The environments follow these lines:
- there are at least three: dev, testing and pre-production. A project may add more, each before pre-production. None of them is production, the live product that people use, and nothing here touches production;
- each declared environment holds its properties, what it offers and how it behaves: its data, such as made-up records written for the tests; its size, such as how many copies of each service run and how big its data store is; its network, such as whether it can be reached from the internet or only from inside the team's network; who can reach it; and the settings that are its own. A secret's value is never one of them;
- each environment is built and managed on its own, from the one design of its underlying technology that Deployment design makes and reuses for every environment, and it is built only when a deployment to it is needed. Building one more environment repeats that design and adds only what that environment's declaration says;
- a builder's own machine is not an environment and not in the path. It is a dev sandbox, where a builder runs the project's code while building it. It is needed, so this capability sets it up too, with no container platform, such as Docker, and no cloud service needed to run it;
- for each part, its reason, its source and the person who confirmed it.

The environments are declared once for the project, before the slices are designed, and they are updated as the project changes. A slice is an ordered group of features that one person can test end to end on one surface. What each environment is for, the order a change takes through them and the tests that run in each are part of the deployment design, which this capability reads and never changes.
An agent proposes each environment and each property, and a person confirms it. The agent looks first at what the project already holds, its code, its settings and its own records, then at Garura memory, then at Phoenix memory. Garura memory is the memory Garura keeps for the project, and it holds the product model, the shared map of the product that people and agents read. Phoenix memory is the shared memory on the machine that every project draws from; its architecture and technology learnings say how environments are set up for a product in given conditions. Only when none of them has an answer does the agent research it. It then raises what it found as a memory update, a proposed addition to memory, and a person approves it before it is used. Nothing comes from what the AI agent knows by itself.
It matters to software delivery planning because that domain prepares the work before agents build it. Without declared environments, each builder and each pipeline invents its own place to run a change, with its own data and its own access, and environments that no deployment needs yet are built and paid for.

Features:
- Declare the environments and how each is set up (fn-declare-environments): declares which environments the project has, at least dev, testing and pre-production and never production, and for each one its data, its size, its network, who can reach it and its own settings, so every deployment and every test runs in a place that was set up on purpose.
- Build and manage an environment when a deployment needs it (fn-build-environment): when a deployment needs an environment that is not built yet, builds it on its own from the one design of the underlying technology and its declaration, after a person's yes, checks that it answers, and from then on keeps it apart from the others until a person asks to take it down.
- Update the environments as the project changes (fn-update-environments): when the project needs another environment, or an environment's data, size, network, access or settings must change, a person confirms an update, and what held before stays readable with why it changed.
- Set up a dev sandbox on a builder's machine (fn-dev-sandbox): sets up a place on a builder's own machine where the builder runs the project's code while building it, with each part running on the machine itself and no container platform or cloud service needed, so a builder can try a change before it goes to dev.

What is not built yet:
- None of the four features is built. Nothing declares the environments of the whole project.
- As built, each slice's own run design records its environments, one at a time. The design play for a slice's run is stale and waits for a rebuild. Its names are fixed, local, dev, qa, stage and prod, in that order, so its list ends with production and has no testing or pre-production. For each environment it records whether it runs on a builder's machine or on a cloud, how to bring it up and an optional step that fills it with test data, and for a cloud one its region, the size of what runs, its network and firewall rules, the identity its services use, where its secrets are kept and the command that deploys to it. Run again, it adds or changes one environment and keeps the others. Nothing gathers these for the whole project.
- The agent that operates environments, and its two skills, are stale. It brings up only an environment the slice's run design declares, counts it up only when a check shows it answers, leaves a failed attempt as it was before, never prints a secret, and takes the environment down when asked. Production is never its target. The play that brings a slice up on a builder's machine for a person to accept brings that copy up only for the walk and takes it down after it. Nothing does the same for the environments of the path, and nothing builds an environment from a design made for the whole project.
- As built, a builder's copy is the run design's first environment, brought up by one command or a compose file. The examples bring it up with Docker compose, so a container platform is allowed, though not required. Nothing sets up a builder's machine as a sandbox apart from the environments.
- Reading memory first exists only in parts. Phoenix memory's learnings for running give each environment its own stance on data, such as test records only on a builder's machine and a cleaned copy shaped like real data in the environment before the live one, and show a dev environment that only the team's network can reach. Their paths end in production, and none of them names testing or pre-production. Memory has nothing on building an environment only when a deployment needs it, or on taking one down.
- The review checks, in each change, files of test data against the rule that an environment other than production holds masked or made-up data, and checks that the settings each environment needs are written down. It reads what was built; nothing gives it declared environments to compare with.
- The product model has no kind for an environment, so where the declared environments are kept is not decided.
- No work for this capability is planned in the tracker.

### Benefit hypothesis
- Who it serves: the devops engineer, who decides which environments the project has and how each is set up; the product owner, who set the three environments, kept production out of the project's reach, and asked that each environment be built only when a deployment needs it; the agents and pipelines that deploy and test each change in an environment; and the developer, a person or an agent who builds the project's code in a dev sandbox on their own machine.
- What we believe: every change is deployed and tested in environments declared for the whole project, each built the same way every time, none of them production, and none built before a deployment needs it, if the work stands on these rules:
  - Which environments exist, and how each is set up, is decided once for the whole project, never in a slice.
  - There are at least dev, testing and pre-production, and none of them is production.
  - Each environment is built and managed on its own, from the one reused design, and only when a deployment to it is needed.
  - Each property comes from the project's code or memory, or from research a person approved into memory, and a person confirms it.
  - The environments are updated as the project changes, and what held before stays readable with why it changed.
  - Nothing waits for the declaration.
- How we will know: each environment a release reached matches its declaration in its data, its size, its network and who can reach it; two environments built at different times come from the same design of the underlying technology; no environment was built before a deployment needed it; and none of them is production or holds data taken from production.
  - This is not tested today, because nothing declares the environments of the whole project.

### Boundary (In / Out / Never)
- In: declaring which environments the project has and how many: at least dev, testing and pre-production, and any more a project adds before pre-production.
- In: declaring each environment's properties: its data, its size, its network, who can reach it and the settings that are its own.
- In: building each environment on its own when a deployment to it is needed, from the one design of the underlying technology and the environment's own declaration; checking that it answers; keeping it apart from the others; applying a confirmed change to it; and taking it down when a person asks.
- In: updating the environments and their properties as the project changes, keeping what held before and why it changed.
- In: setting up a dev sandbox on a builder's own machine: how each part of the project starts and stops there, its data and its settings, with no container platform or cloud service needed, and updating that setup as the project changes.
- Out: the path a change takes through the environments, what each environment is for, the tests that run in each, and the one design of the underlying technology that every environment is built from. Deployment design owns them, with the cloud, the container platform, where secrets and settings are kept, and the cost of running the environments in the path. This capability reads them and never changes them. The size declared here for each environment is what that cost is worked out for, so a change of size calls for the cost to be worked out again.
- Out: deploying each change into an environment. Continuous delivery (Validation → Run) takes each accepted change along the path, and the plays that bring a slice up for a person to accept, or deploy a slice to an environment, read the declarations and never change them. When a deployment needs an environment that is not built yet, it is built here first.
- Out: making the files an environment is built from, such as infrastructure files and container files. Build the work makes them, from work items. This capability builds each environment from them.
- Out: writing and running the tests. The testing capabilities of Validation → Run, Test with evals the builder never sees (Code → Validation), and Design for evaluation and testing own them.
- Out: where a person's acceptance walk runs. User acceptance testing (Validation → Run) decides it. A builder's own machine is a dev sandbox for building, not one of the environments.
- Out: the product profile, the record of the product's shape and the quality levels and compliance needs it commits to. Specify the product sets it. This capability reads its compliance needs, such as rules for personal data, to set each environment's data, and never writes them.
- Out: writing the decision record behind each choice, accepting it and keeping its history. Manage ADRs (Orchestration) owns the records; this capability decides what each choice says and hands it over.
- Out: putting the memory that fits the environments into the project. It belongs to the play that starts the build, not to the product model.
- Out: moving an approved memory update into Phoenix memory. A memory update goes to the project's short-term memory, and moving it up is a promotion a person makes on purpose, outside this work.
- Never: declare, build or touch production. No environment here is production, and nothing here reads from it or writes to it, which includes copying its data into an environment. The reason, in the product owner's words: "We are never touching production."
- Never: need a container platform, such as Docker, or a cloud service to run the dev sandbox. A part that cannot run without one is named as not decided. The reason, in the product owner's words: "we don't need to burden a local laptop with cloud like setup - for example things like docker etc."
- Never: build an environment before a deployment to it is needed. The reason, in the product owner's words: "we needed these to be done only [when] a deployment is needed".
- Never: block work on a missing declaration. Design and build go on from the project's code and memory, and what is open is named. The reason: the Spec → Design business intent blocks no work, and each design can run at any time.
- Never: make a choice from what the AI agent knows by itself, or build an environment that no person confirmed. The reason: an environment set up on an agent's guess is found wrong only when a test or a release fails in it, and an environment built that nobody asked for is paid for every month.
- Never: write the value of a secret into a declaration, a record of a build or a log. The reason: every agent reads the declarations and the records, so a secret written there is no longer secret.
- Never: change a declaration's words in place. An update replaces what held before and keeps it. The reason: releases already tested in an environment must still be explainable by how it was set up then.

### Guiding rules
- Once for the whole project, never in a slice. The reason: when each slice decides its own environments, the first slice decides for every later one, and two slices are tested in places set up in different ways.
- At least dev, testing and pre-production, in that order, and never production. The reason: the product owner set the three, "The environment setups: yes, minimum 3: dev, testing, and then pre-production.", and kept production out of the project's reach.
- Each environment is built and managed on its own, from one design of the underlying technology that is reused for every environment, and only when a deployment to it is needed. Building one more environment repeats the design and never invents it again. The reason, in the product owner's words: "each env can be built separately and managed separately, the underlying tech and reusability is important but we needed these to be done only [when] a deployment is needed".
- A builder's machine is a dev sandbox, not an environment. It runs the project's code on the machine itself, holds only made-up data and no secret's value, and is not where the path's tests are counted. The reason, in the product owner's words: "local machine is dev sandbox and not an environment - but we do need this."
- A declaration says only what makes its environment different: its data, its size, its network, who can reach it and its own settings. What is the same in every environment comes from the deployment design. The reason: what is written twice drifts apart, and the product owner asked that the underlying technology be reused.
- The project's memory first, then Garura memory, then Phoenix memory, then research. Each environment and property is proposed first from what the project holds: its infrastructure files, its container and compose files, its pipeline files that name environments, its example settings file, and the deployment design, the architecture and the surfaces set so far. Then from Garura memory, and from Phoenix memory's architecture and technology learnings, matched to the project's conditions, such as its architecture, its stage, its users and whether it holds personal data. Only when no memory has an answer does the agent research it, and it raises what it found as a memory update for a person to approve. A choice is never made from what the AI agent knows by itself. The reason: a source in the project or in memory can be checked and read back, while the agent's own knowledge cannot.
- Research is used only after a person approves it. Until then the property stays open, with no default, and the work goes on. The reason: research is new knowledge that nobody has checked yet, and the person's approval is the check.
- What the project already has is described as it is. When the project already deploys to environments, they are read from its files and proposed as they are. The reason: a declaration that contradicts the environments the project uses sends every builder after places that nobody runs.
- Each property names its source: a file of the project, a memory file or an approved memory update. The reason: a person can check each one without a search, and when a source changes, the properties built on it can be found.
- The product profile's compliance needs bound each environment's data, and no environment's data comes from production. The reason: the profile is the box the product commits to, the review already treats real personal data in an environment other than production as a finding, and production is never touched.
- A person says yes before an environment is built, and an environment is taken down only when a person asks. The reason: standing up a live environment is outward-facing, and Garura's rules already pin that step to a person.
- An environment counts as built only when a separate check shows it answers, and a failed build leaves things as they were and is reported. The reason: a build command can end without an error while nothing answers, and a half-built environment fails the next deployment in a way nobody can explain.
- A missing declaration is a gap, not a stop. Slices are designed and built with an environment still open, and the gap is named. Only building an environment needs its confirmed declaration, because it stands up something live. The reason: the Spec → Design business intent blocks no work, each design can run at any time, and a person's yes before a live step is already the rule.
- The declarations are kept where every agent looks first. Agents gather context from the project's code and the project's own memory, Garura memory, before Phoenix memory, and the product model is part of Garura memory. The reason: a declaration that builders and pipelines do not find is no declaration. Not decided: the place in the model, because the model has no kind for an environment.
