## Intent
- Goal: Every decision on how the project is built is recorded as an ADR from the one template, as it is made, with every older ADR it supersedes or amends named with the part, what it changes named by real paths, its effect on agent intent, its business-intent check and every point found on the way; it becomes accepted only on a person's word, by hand or at a loop's end review; and once it is accepted, each older ADR it changes points forward to it and the index lists it, so people and agents coordinate the pieces from the decisions that hold.
- Limit: Only a person accepts an ADR; an agent gathers, drafts and checks, and never accepts.
- Limit: An accepted ADR is never edited, except for its forward pointer, and a pointer is written only after the newer ADR is accepted.
- Limit: An ADR never changes a person's business intent; a decision that would is shown to the person and not written.
- Limit: A run writes only the record, the forward pointers, the index and its own run records.
- Fails if: An ADR reads accepted with no person's typed answer on record.
- Fails if: An older ADR that an accepted ADR supersedes or amends is not named with its part, or has no forward pointer to it, or the index does not list the accepted ADR with its status.
- Fails if: An ADR changes a person's business intent, or a run changes anything other than the record, the pointers, the index and its own records.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the decision brief and who gave it, the ADR template, the ADR folder and its index, the older ADRs the decision may supersede or amend, the files, rules, schemas, plays and agents it changes, the agent intents it changes, the business intent pages, the person's typed answer, and, inside a loop, the loop's contract.
- Never read: any memory file by its path, and any ICE page.
- Persona: the technical lead or the developer, who records a decision on how the project is built; and the product owner or the technical lead, who accepts it.
- Scope: In: recording a decision as an ADR from the template with what it overrides and changes, accepting it only on a person's word, keeping older ADRs pointing forward and the index current, and giving the person who accepts every point found on the way; and, not built yet, recording the ADR in the change it belongs to, keeping ADRs to how the project is built, and taking in each design choice. Out: product decisions in the model, what each design choice says, the ADR cards in the review tool, the template as a standard, reviewing a change that adds an ADR, opening and landing the change, running a loop, and the way past a gate.

## Expectation
- Scenario: In a clinic's booking app, the technical lead records the decision to keep all bookings in one region, which amends the part of an older ADR on where bookings are stored. The draft names that ADR with its part, lists the files the decision changes, and holds one point found on the way: a help page that still says two regions. The product owner reads it, types accept, and the ADR reads accepted with their name; the older ADR's status line now points to it, and the index lists it as Accepted. In the same week, in a shop's checkout service, a drafted ADR that would drop a feature a person asked for is stopped and shown to the product owner, and no ADR is written.
- Done means: Someone other than the one who recorded it reads the ADR folder, the index and the run's records, and finds the clinic's ADR written from the template and naming the older ADR with its part, the product owner's typed accept on record before it reads accepted, the older ADR changed only on its status line with a pointer to the new one, the index row reading Accepted, nothing else changed in the repository, and, for the shop, no ADR written.
