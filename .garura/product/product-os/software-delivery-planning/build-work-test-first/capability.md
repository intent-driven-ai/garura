# Capability: Build the work test first

## Directional intent
Build the work under a chosen plan item test first: all the tests for the work are written and shown to fail, then all the code until every test passes, then the code is tidied while they stay passing. The builder never sees the tests; a separate check runs them.
A business intent is what a person or the organisation wants, in their own words. Its plan holds its work items as a tree, and each work item is an issue in the team's tracker, the tool where the team keeps its issues. Each slice, an ordered group of features that one person can test end to end on one surface, has one epic that stands for it. Under an epic sit stories; a story stands for one feature of the product and delivers it. Under a story sit its chores, bugs and spikes: a chore is upkeep for the story, a bug is a defect its work brought in, and a spike is a proof tried on the built story.
The technical lead names one item of the plan. Gather the work under a chosen plan item gathers it and every item under it into short-term memory, the issue's own folder where a run keeps its working files, and splits each story in two: the builder's part, with the story's title, goals, limits and Context guidance, and the test writer's part, with the story's expectations. Design the work designs that work, and the design is the input for the code. In the product owner's words: "this design is input for writing code and building the application". This capability writes the tests and the code, in the product owner's words: "we have to do this such that coding is also test driven".
- The tests first. A test writer writes all the code-level tests for the work, from the test writer's part and the design. A code-level test is a test inside the project's code, in the project's own test tool, that checks one expected result of a story by calling the code. A separate check runs them on the code as it is and shows that each one fails, because what it checks is not built yet.
- Then the code. The builder writes all the code for the work from its own part, each story's collected context and the design, in the order it chooses, until the separate check finds every test passing. The builder never sees a test; the check tells it which expected results still fail.
- Then the tidy, where the code needs it: the builder improves how the code is written, never what it does, and the check finds every test still passing. In the product owner's words: "You write the test, make sure they are failing, then you build the code, then you refactor if needed, and then you move forward."
- Grouped, not one line at a time. In the product owner's words: "This can be grouped so that all the tests are written, and then all the code is written to make sure all the tests are passing."
- With the build, the builder writes the slice's usage guide, which tells the eval how to reach the built work. An eval is the outside test of a slice, on the surface where a person uses it; Write the evals that check the work writes it before the build, and no one who builds the work reads it.

One setting shapes the build. A setting is a choice a team turns on or off, or picks, once for the project; Garura keeps every one in its settings: "Everything that can be turned on or off lives in settings."
- The test model setting picks which model or service writes the tests and runs them, apart from the model that builds the code: for example a different model, such as Codex, or another service. In the product owner's words: "i need a config that would send test building and running to a different model, like a codex or another service."
- The tests are run through a tool, not by an agent's judgment. In the product owner's words: "test running can be done via a tool."
- Which model each part of the work runs on belongs to the agreed capability Intelligent model routing: "Each part runs on the right model and effort for its job, for speed and token cost, on each harness that supports it." This capability reads the setting and sends the tests where it says.

The work is done by the developer: "The coding will be done by the developer, including the TDD." The developer is a person or an AI agent who builds the code. The role has two parts that are never held by the same one for the same work: the test writer and the builder. The technical lead confirms each departure from the design.
What the build follows comes from memory first: the project's own code and memory, such as its coding standards and the way its tests are written, then Garura memory, the memory Garura keeps for the project, which holds the product model, then Phoenix memory, the shared memory on the machine that every project draws from. Only when none of them has an answer is it researched, and what research finds is raised as a memory update, a proposed addition to memory, and used only after a person approves it. Nothing comes from what the AI agent knows by itself.
It matters to software delivery planning because that domain turns a business intent into work that agents can build and that a check from the outside can prove. This capability is where the work becomes code, and the tests written first, apart from the builder, show that each expected result was built and not taught to a test.

Features:
- Write all the tests for the work, and show each one fails (fn-write-failing-tests): before any code, a test writer who is not the builder writes a code-level test for each expectation of each story under the chosen item, and the separate check shows each one fails because what it checks is not built yet.
- Build the code until every test passes, then tidy it, without seeing the tests (fn-build-code-to-pass): once every test for the work has failed on the check's record, the builder writes all the code for the work under the chosen item from its own part, the collected context and the design, in the order it chooses, until a separate check, which runs the tests through a tool on the model or service the test model setting names, finds every test passing, then tidies the code where it needs it while every test stays passing, and never sees or changes a test.
- Write the usage guide that tells the eval how to reach the built work (fn-write-usage-guide): with the build, the builder writes the slice's usage guide, what its surface is, how to reach it and the steps a person takes, in the plan's guides folder, without seeing the eval.
- Update the tests and the code as the work changes (fn-update-tests-and-code): when the design, a story or an eval's finding changes the work, the test writer updates the tests first and the check shows the new ones fail, then the builder changes the code until every test passes again.

What is not built yet:
- None of the four features is built for the work under a chosen item. Nothing builds a story, a chore or a spike test first.
- The only live test-first build is a bug fix's, in the bug fix play: a failing test is written and proven to fail before any code, the code builder may not change it, and another agent proves it passes. It is live only in a full install, and Fix defects test first keeps it. There the code builder is handed the test as a file it may read.
- The old build play, /build-epic, is stale and waits for a rebuild. Its test agent wrote a test for every expected result from the spec before the code, and its code builder never saw the tests or the evals, but nothing showed a test failing before the code.
- The code builder's test mode reads each test to make it pass, and a check of each test file before and after keeps it from changing one. Reading the tests is against this capability's rule.
- The old play that tidies code, /refactor-code, is stale. It proved the tests passing before and after, with no test weakened.
- Nothing writes a usage guide, and nothing keeps the tests from the builder when they sit in the project's code.
- The test model setting does not exist, and nothing sends the writing or the running of a project's tests to another model or service. The only part that runs on a model a setting names is the loop's own check of a finished loop, which must run on a model that is not the session's.
- No memory tier holds a rule for test-driven development.

### Benefit hypothesis
- Who it serves: the developer who builds the code, as test writer or as builder; and the technical lead, whose design the code follows and who confirms each departure from it.
- What we believe: when every test for the work is written and shown to fail before any code, and the code is built until they pass by a builder who never sees them, the code does what the work asks and is not shaped to pass a test, if the work stands on these rules:
  - Every expectation of each story under the chosen item has a test, written before any code by a test writer who is not the builder.
  - Each test is shown to fail, on the record of a check the builder does not run, before any code is written.
  - The builder never sees, writes or changes a test, and learns from the check only what still fails.
  - The code is tidied only while every test stays passing, and no test is weakened or taken out.
  - What the build follows comes from the design, the project's code and memory, never from what the AI agent knows by itself.
- How we will know: the check's record shows each test for the work failing before the code and passing after the build and after the tidy; no test file differs between the first run and the last; the build session's record shows no read of a test or the evals folder; the tests the project already had still pass; and the slice's eval, run later from the outside, passes on work whose builder never saw it.
  - This is not tested today, because nothing builds the work under a chosen item test first.

### Boundary (In / Out / Never)
- In: writing the code-level tests for every story under the chosen item, from the test writer's part and the design, before any code.
- In: running the tests by a check apart from the builder: before the code to show each one fails, while the builder builds to tell it what still fails, and after the tidy to show every test still passes.
- In: writing the code for every story, chore and spike under the chosen item, from the builder's part, the collected context and the design, in the order the developer chooses.
- In: tidying the code while every test stays passing.
- In: writing the slice's usage guide with the build.
- In: updating the tests and the code as the work changes, and sending a departure from the design back to the technical lead with its reason.
- In: handing each part of the build only its own part: the test writer the test writer's part, the builder the builder's part.
- In: sending the writing and the running of the tests to the model or service the test model setting names, and running the tests through a tool.
- Out: choosing the item, gathering the tree under it, splitting each story and collecting its context. Gather the work under a chosen plan item owns them.
- Out: designing the work and updating the design. Design the work owns them; a departure found while building goes back to it.
- Out: writing the evals and the hidden file of failure conditions, and checking that no build was given or read them. Write the evals that check the work owns them.
- Out: running the evals, giving the verdict and writing the handoff plan, which tells the builder or a person what went wrong and the way back. Test with evals the builder never sees, in Code → Validation, owns them.
- Out: checking the code against the project's standards. Check the code against its standards, in Code → Validation, owns it; the build follows the standards while it writes.
- Out: tracing a defect to its cause and fixing it. Fix defects test first owns it; a bug gathered under the chosen item is handed on to it.
- Out: choosing what is built next, the status of each item, the loops that run plays, and tracking the work in the tracker. Orchestrate agent work through planning owns them.
- Out: opening the branch, committing, reviewing and landing the change. Ship every change the same way, in Developer tooling, owns them.
- Out: setting up the place where the builder runs the code while building it. Environment setup owns it, through its dev sandbox.
- Out: keeping the test model setting, and which model each part runs on. Settings, where everything that can be turned on or off lives, and Intelligent model routing own them; this capability reads the setting.
- Out: putting what was built into the product model. Keep the spec matched to what's built owns it.
- Never: give the builder a test, a test file, the test writer's part, an eval, the hidden file or the evals folder, or show it a test's code. The reason, in the product owner's words: "the code, when being written, should not get to see what tests there were". A builder "cannot teach to a test it cannot see."
- Never: let the builder write, change, weaken or take out a test. The reason: a test the builder can change no longer checks the builder, and what is built already holds this line: "If any test file is modified, the build is rejected."
- Never: write code before every test for the work is written and shown to fail, or count a test that the check never saw fail. The reason, in the product owner's words: "make sure they are failing"; a test that passes before the code proves nothing about it.
- Never: take the builder's word that a test passes. The reason: "any builder self-report of pass/fail is not a valid signal", and Code → Validation must not "Let a builder grade itself".
- Never: change the design, a project standard, a work item, the plan file or a status. The reason: the design is the input and a departure goes back to it, and, in the product owner's words, "This intent's job is to execute on the plan".
- Never: make a choice from what the AI agent knows by itself. The reason: a source in the project or in memory can be checked and read back, while the agent's own knowledge cannot.

### Guiding rules
- All the tests, then all the code, then the tidy. The work is grouped: every test for the work under the chosen item comes before any of its code. The reason, in the product owner's words: "What we don't want is that every single line of code is being written sequentially."
- Shown to fail, for the right reason. Each new test fails on the code as it is because what it checks is not built yet. A test that passes, or that cannot run because of a fault in the test itself, goes back to the test writer. The reason: the built test skill refuses a test that already passes: "if it passes on the unfixed code, the test is not a regression test and the skill fails."
- Two developers, kept apart. The test writer and the builder are never the same one for the same work, and neither sees the other's output while it works. The reason: an earlier build "has the same agent writing tests and code (context bias)", and the old build play kept the two apart.
- A separate check runs the tests, and its record is the proof. The check is not the builder, and a pass counts only on its record. The reason, in the product owner's words: "The builder never sees the tests; a separate check runs them.", and in the bug fix play "the verifier is never the implementer".
- The tests on their own model, run by a tool. The test model setting picks the model or service that writes and runs the tests, apart from the model that builds the code, and a tool, not an agent's judgment, runs them. The reason, in the product owner's words: "i need a config that would send test building and running to a different model, like a codex or another service. test running can be done via a tool."; and a tool that runs the tests means "no agent burns inference executing test commands."
- The builder learns what still fails, never the test. How much it is told of each failing test is not decided. The reason: the builder needs to know what is left, and a full failure message can give the test away.
- Just enough. The builder writes the code the work asks for and no more. The reason, in the product owner's words: "write just enough ... Don't take it literally, because we are in coding", and what is built already says "No scope creep".
- The design is the input. The builder builds to the classes, functions and interfaces the design names, and picks its own build order. Where the design is wrong, it builds another way, writes down why, and the departure goes back to the technical lead as a design update. The reason, in the product owner's words: "this design is input for writing code and building the application", and Design the work leaves the order to "the developer".
- The tidy changes how the code is written, never what it does. The reason: a refactor is to "Improve code without changing what it does", and the old tidy play proved that "tests are green before and after, and no test was weakened."
- Nothing that passed before breaks. The check also runs the tests the project already had, and one that passed before the build and fails after is named. The reason: those tests are the safety net, and "these must still pass after the change".
- Done is proven, not assumed. The work is built when the check's record shows every test passing after the tidy, not when the steps run out. The reason: a play ends when done was proven, "not because its step list ran out."
- Stuck goes back, never round in circles. When the builder cannot make an expected result pass after the tries the project allows, the work goes back: to the technical lead for a design update, or to the test writer to check the test against its expectation, and a person decides when they disagree. The builder never changes the test. The reason: the bug fix play sends the design and the test back when its tries run out, and "it does not halt blindly."
- The project's memory first, then Garura memory, then Phoenix memory, then research through a memory update a person approves. What nothing answers stays open, with no default, and the rest goes on. The reason: research is new knowledge that nobody has checked yet, and the person's approval is the check.
