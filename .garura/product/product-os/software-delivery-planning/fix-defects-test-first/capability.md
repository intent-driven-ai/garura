# Capability: Fix defects test first

## Directional intent
Fix a reported defect quickly and test first: the defect is understood against the product model, its tests and its code, the tests that prove it are written and shown to fail, then the code is fixed while every test of the project is run, and then tidied while they all pass. The builder never sees the tests; a separate check runs them.
The product model is the shared map of the product that people and agents read. A feature in it is one thing a person can do inside a capability. A defect is a fault in a feature a user wants: the product model holds the feature, and the product does not do what the feature says. In the product owner's words: "There needs to be a matching map to a product model that says this is a feature a user wants, and it's a defect." A bug is how a plan keeps a defect as a work item, an issue in the team's tracker: it sits under the story whose work brought it in, and a story stands for one feature and delivers it.
A defect can be reported anywhere: in a person's own words, as a finding in the review of a change, by the eval after the work was accepted, or as a bug in a plan. In the product owner's words: "Whenever a defect is reported, a defect can be reported anywhere." The fix starts from the report itself. A bug that Gather the work under a chosen plan item gathers is one such report: "a bug gathered here is handed on to it." Recording the defect in the tracker is not this capability's work.
- Understand the defect first, as one job. Match it to the product model: find the feature that the defect breaks. A defect that no feature covers is not fixed here; it is named as a new need for Specify the product. In the product owner's words: "If it can't find it in a product model, then it really isn't a defect per se, right, in some of those areas." Then find the tests the project already has for that behaviour and, when they pass while the defect is there, why: "Identify whether any tests exist and, if they are passing, why." Then find the root cause, the file, the logic and why it is wrong, from the code and those tests: "Find the root cause, which is part of understanding tests and everything and whatnot." The understanding holds only what the fix needs: the feature, the tests and why they pass, the cause, and what the fix changes.
- Then the tests. A test writer writes the code-level tests that prove the defect. A code-level test is a test inside the project's code, in the project's own test tool, that calls the code and checks one result. A separate check runs them on the code as it is and shows that each one fails, because the defect is still there.
- Then the fix and the whole testing. The builder changes the code from the cause and what the fix changes until the separate check finds every test of the project passing, the new tests and every test the project already had. The builder never sees a test; the check tells it which results still fail. In the product owner's words: "Write the tests. 2. Do the implementation. 3. Do the entire testing and stuff."
- Then the tidy, where the code needs it: the builder improves how the fixed code is written, never what it does, and the check finds every test still passing. In the product owner's words: "then you refactor if needed".
- Quick, with no full design. The fix never goes through Design the work, and writes no design document and no steps for the builder. In the product owner's words: "we want it to be really quick. We don't want it to go through the full-blown design and all these and stuff and things like that. It just takes too much time, but writing tests and getting the tests to be right is still important."
- When a test still fails after the tries the project allows, the defect is understood again, the tests are updated first, and the fix goes on.

Two settings shape the fix. A setting is a choice a team turns on or off, or picks, once for the project; Garura keeps every one in its settings: "Everything that can be turned on or off lives in settings."
- The test model setting, the same one Build the work test first reads, picks which model or service writes the tests and runs them, apart from the model that fixes the code. In the product owner's words: "i need a config that would send test building and running to a different model, like a codex or another service." The tests are run through a tool, not by an agent's judgment: "test running can be done via a tool."
- A second setting decides whether the fix code waits for the technical lead's yes on the understanding. When it does not wait, no fix code is written until the understanding and the failing tests are on record.

The work is the developer's: "The coding will be done by the developer, including the TDD.", where TDD is test-driven development, the tests before the code. The developer is a person or an AI agent who builds the code. With no full design, the developer both understands the defect and fixes it, in two parts that are never held by the same one for the same defect: the test writer, who understands the defect and writes the tests that prove it, and the builder, who fixes the code. Understanding reads the project's tests, so it is never the builder's. The technical lead agrees the fix only when the project's setting asks for that yes.
What the fix follows comes from memory first: the project's own code and memory, then Garura memory, the memory Garura keeps for the project, which holds the product model, then Phoenix memory, the shared memory on the machine that every project draws from. Only when none of them has an answer is it researched, and what research finds is raised as a memory update, a proposed addition to memory, and used only after a person approves it. Nothing comes from what the AI agent knows by itself.
It matters to software delivery planning because that domain turns a business intent into work that agents can build and that a check from the outside can prove. When something built turns out wrong, this capability keeps that proof, quickly: the tests written first, apart from the builder, show that the defect was there and is gone, and the whole testing shows that nothing else broke.

Features:
- Understand the defect: its feature in the product model, its tests and why they pass, and its root cause (fn-understand-defect): from a defect reported anywhere, the developer who will write its tests finds the feature the defect breaks, the tests that already check that behaviour and why they pass, and the root cause, and writes only what the fix needs; a defect no feature covers is named as a new need and not fixed.
- Write the tests that prove the defect, and show each one fails (fn-write-defect-tests): before any fix code, a test writer who is not the builder writes a code-level test for each wrong result the report names, and the separate check shows each one fails because the defect is there.
- Fix the code and run every test, then tidy it, without seeing the tests (fn-fix-defect-code): the builder changes the code from the cause and what the fix changes until a separate check, which runs every test of the project through a tool on the model or service the test model setting names, finds them all passing, then tidies the code it changed while they stay passing; when a test still fails after the tries the project allows, the defect goes back to be understood again.

What is not built yet:
- The bug fix play, /fix-bug, is built and live only in a full install. It is not laid in Garura's own repository, and it last ran under its old name, fix-it, in May 2026. It traces the cause, writes a full fix design with another way weighed and steps for the builder, writes one failing test and proves it fails before any code, has the code builder make the fix, and has another agent run that test after it.
- Nothing matches a defect to the product model, and nothing names a defect that no feature covers as a new need. A bug in a plan sits under a story that names the feature it stands for, but nothing reads that to understand a defect.
- Nothing finds the tests that already check a behaviour and says why they pass. The old skills that listed a project's tests, and the tests a change could touch, are stale.
- The bug fix play goes through a design step, a fix design with another way weighed and ordered steps for the builder, which is the full design the product owner does not want for a fix.
- The bug fix play's design agent writes the test, which is not a developer apart from the builder, and it writes it from the fix design, so the test can check that the planned change was typed, not that the defect is gone.
- The bug fix play hands its code builder the test's path as a file it may read, and the code builder's test mode reads "the corresponding test" to make it pass. That is against this capability's rule.
- Where memory gives no answer, the bug fix play's design agent goes on with the AI model's own reasoning, and the play's own check accepts it. Memory now says an agent "never falls back to the model".
- The bug fix play has no tidy, and its own check runs only the new test, not the entire testing.
- The bug fix play starts only from an open issue in the tracker, not from a report given anywhere else.
- The test model setting does not exist, and nothing sends the writing or the running of a fix's tests to another model or service.
- No memory tier holds a rule for test-driven development.

### Benefit hypothesis
- Who it serves: the developer who understands and fixes the defect, as test writer or as builder; the product owner, who wants a defect fixed quickly, without a full design; and the technical lead, who agrees the fix when the project's setting asks for it.
- What we believe: when a reported defect is first matched to the feature it breaks, its tests and its cause understood, then proven by tests written and shown to fail before any fix code by someone who is not the builder, and fixed by a builder who never sees them while every test of the project is run, the fix is quick, removes the cause and breaks nothing that passed before, if the fix stands on these rules:
  - A defect is fixed only when a feature of the product model covers it; otherwise it is a new need.
  - The tests that already exist are found, with why they pass, and the cause names the file, the logic and why it is wrong.
  - Each wrong result the report names has a test, written before any fix code by a test writer who is not the builder, and shown to fail on the record of a check the builder does not run.
  - The builder never sees, writes or changes a test, and learns from the check only what still fails.
  - Every test of the project passes on the check's record after the fix and after the tidy.
  - What the fix follows comes from the project's code and memory, never from what the AI agent knows by itself.
- How we will know: each fixed defect names its feature, and each defect with no feature went to Specify the product unfixed; the check's record shows each new test failing before the fix and every test of the project passing after the fix and after the tidy; no test file differs between the first run and the last except by the test writer with its reason; the fix session's record shows no read of a test; and no fix wrote a design document.
  - This is not tested today, because nothing fixes a defect under these rules.

### Boundary (In / Out / Never)
- In: taking in a defect reported anywhere: a person's words, a finding in a review, the eval after the work was accepted, or a bug in a plan.
- In: understanding the defect: the feature it breaks, the tests that exist and why they pass, the root cause, and what the fix changes.
- In: naming a defect that no feature of the product model covers as a new need, for Specify the product, with no fix.
- In: writing the code-level tests that prove the defect, before any fix code.
- In: running every test of the project by a check apart from the builder, through a tool on the model or service the test model setting names: before the fix to show each new test fails, while the builder fixes to tell it what still fails, and after the tidy to show every test still passes.
- In: fixing the code until every test passes, and tidying the code the fix changed while they stay passing.
- In: the technical lead's yes on the fix when the project's setting asks for it.
- In: understanding the defect again, and updating the tests first, when a test still fails after the tries the project allows.
- Out: recording a defect in the tracker, as a bug under the story that brought it in, with its text and its severity. Orchestration owns it, and Turn intents into agent work holds the changes to the plan today; in the product owner's words, "making the plan is part of the orchestration, not this intent".
- Out: turning a new need into intents, capabilities and features. Specify the product owns it.
- Out: matching the product model to what is built when the model misses a part. Keep the spec matched to what's built owns it.
- Out: gathering the work under a plan item. Gather the work under a chosen plan item owns it, and hands on each bug it gathers.
- Out: designing the work. Design the work owns it; a fix never goes through it.
- Out: building stories, chores and spikes, and a failure the eval finds before the work is accepted. Build the work test first owns them.
- Out: writing the evals and the hidden file of failure conditions. Write the evals that check the work owns them.
- Out: running the evals, giving the verdict, writing the handoff plan, and checking the code against the project's standards. Code → Validation owns them, through Test with evals the builder never sees and Validate its own code.
- Out: choosing which defect is fixed next, the status of each item, and tracking the work in the tracker. Orchestrate agent work through planning owns them.
- Out: opening the branch, committing, reviewing and landing the change. Ship every change the same way, in Developer tooling, owns them.
- Out: setting up the place where the code runs while it is fixed. Environment setup owns it, through its dev sandbox.
- Out: keeping the settings, and which model each part runs on. Settings and Intelligent model routing own them; this capability reads them.
- Never: send a fix through a full design: no design document, no fix design for review, no steps for the builder. The reason, in the product owner's words: "We don't want it to go through the full-blown design and all these and stuff and things like that. It just takes too much time".
- Never: fix a defect that no feature of the product model covers. The reason, in the product owner's words: "If it can't find it in a product model, then it really isn't a defect per se".
- Never: give the builder a test, a test file, an eval, the hidden file or the evals folder, or show it a test's code. The reason, in the product owner's words: "the code, when being written, should not get to see what tests there were". A builder "cannot teach to a test it cannot see."
- Never: let the builder write, change, weaken or take out a test. The reason: a test the builder can change no longer checks the builder, and Code → Validation must not let a builder "weaken a check to pass".
- Never: write fix code before every test that proves the defect has failed on the check's record. The reason, in the product owner's words: "make sure they are failing"; a test that passes before the fix proves nothing about the defect.
- Never: take the builder's word that a test passes. The reason: "any builder self-report of pass/fail is not a valid signal", and Code → Validation must not "Let a builder grade itself".
- Never: understand or fix a defect from what the AI agent knows by itself. The reason: an agent that works through the memory tool "never falls back to the model", and a source in the project or in memory can be checked and read back.
- Never: change a work item, the plan file or a status, or fix a second defect found on the way. The reason, in the product owner's words: "This intent's job is to execute on the plan", and a second defect is its own report.

### Guiding rules
- Quick, with no full design. The fix writes only what it needs, and never goes through Design the work. The reason, in the product owner's words: "we want it to be really quick", and "writing tests and getting the tests to be right is still important."
- Matched to a feature first. A defect is fixed only when a feature of the product model covers it; otherwise it is named as a new need for Specify the product. The reason, in the product owner's words: "There needs to be a matching map to a product model that says this is a feature a user wants, and it's a defect."
- The tests that exist, and why they pass. Before the cause is named, the tests the project already has for that behaviour are found and run, and when they pass while the defect is there, the reason is written down. The reason, in the product owner's words: "Identify whether any tests exist and, if they are passing, why."
- The cause, not the symptom. The cause names the file, the logic and why it is wrong, apart from the report's own words. The reason: "Find the root cause, which is part of understanding tests and everything and whatnot.", and what is built already holds that "Restating the issue title or description is not RCA.", where RCA is the root-cause analysis.
- All the tests, then the fix, then the tidy. Every test that proves the defect comes before any fix code. The reason, in the product owner's words: "This can be grouped so that all the tests are written, and then all the code is written to make sure all the tests are passing."
- The tests prove the defect, not the planned change. They call the code, do what the report says goes wrong and check the right result; they never check the text of the code. The reason: a test written to the planned change passes once the change is typed, whether or not the defect is gone, and the built test skill picks a check that "asserts the fix was applied".
- Shown to fail, for the right reason. Each test fails on the code as it is because of the defect. A test that passes, or that cannot run because of a fault of its own, goes back to the test writer. The reason: "if it passes on the unfixed code, the test is not a regression test and the skill fails."
- Two developers, kept apart. The test writer, who understands the defect, and the builder are never the same one for the same defect. The reason: understanding reads the tests, and an earlier build "has the same agent writing tests and code (context bias)".
- The entire testing, by a separate check, and its record is the proof. The check runs every test of the project, not only the new ones. The reason, in the product owner's words: "Do the entire testing and stuff.", and in the bug fix play "the verifier is never the implementer".
- The tests on their own model, run by a tool. The test model setting picks the model or service that writes and runs the tests, apart from the model that fixes the code. The reason, in the product owner's words: "test running can be done via a tool."
- Inside what the fix changes. The fix changes the files the understanding names; another file is changed only with the builder's reason in the fix's record. The understanding names what changes, never the steps. The reason: what is built already passes a changed file only "when it appears in design.affected_files, OR it carries a" reason, and the Design → Code business intent must not "Tell the builder the steps".
- The tidy changes how the code is written, never what it does. The reason: a refactor is to "Improve code without changing what it does."
- Stuck goes back, never round in circles. When a test still fails after the tries the project allows, the defect is understood again, the tests are updated first, and the builder fixes again; a person decides when the test writer and the builder disagree. The reason: the bug fix play revises its understanding when its tries run out, and "it does not halt blindly."
- The technical lead agrees the fix when the setting asks. The reason: the older agreed line, "its fix is agreed with a person", and what is built already makes that yes a setting: "so the config switch now governs them too."
- The project's memory first, then Garura memory, then Phoenix memory, then research through a memory update a person approves. What nothing answers stays open, with no default, and the rest goes on. The reason: research is new knowledge that nobody has checked yet, and the person's approval is the check.
