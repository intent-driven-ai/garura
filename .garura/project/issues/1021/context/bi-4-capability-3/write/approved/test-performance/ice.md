## Intent
- Goal: Once the work is built and runs in the testing environment, a part that is not its builder measures it on each declared surface, as one person meets it and under the load the pass bar names, against the product profile's performance level, its pass bar and each capability's performance need, so that every part of the pass bar has a pass or a fail in the conditions it names and the verdict is a pass only when every part passes; each finding goes back as a handoff plan to the developer when the builder can fix it alone, or to the product owner when a person must decide; and the tests run again as the product changes and when the performance level goes up.
- Limit: What is measured, its numbers and how it is measured come only from the product profile and each capability's performance need; nothing that was not measured, or was measured in other conditions than the bar names, counts as a pass, and no figure is worked out from a measure in another size of environment.
- Limit: The builder never gets the performance tests, their figures or the verdict, only the handoff plan, which names what is slow, where and the way back, never the test, its rule, its id or its tool.
- Limit: Nothing is measured or loaded outside the testing environment, in production or on a builder's own machine; no test changes an environment's size or data; the records of the review of each change and of the build's separate test run are taken as evidence and not run again; and nothing comes from what the AI agent knows by itself.
- Fails if: The verdict is a pass while a part of the pass bar or a capability's performance need failed, was not measured, or was measured in other conditions than it names.
- Fails if: A test touched or loaded production, a builder's own machine or a system the testing environment does not hold, or changed an environment's size to reach a pass.
- Fails if: The builder was given a performance test, its figures or the verdict, or a finding that needs a person's judgment or authority went to the developer.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the product profile's performance level and its pass bar with how it is measured, each capability's performance need in the product model, the declared surfaces and how each is reached in the testing environment, the testing environment's declaration and any environment of its own for performance tests with its size and data, which tests the deployment design places where and what they cost on each cloud, the records of the review of each change and of the build's separate test run, the decisions that moved the performance level, the earlier performance verdicts, and the project's setting for rounds.
- Never read: the value of any secret other than the testing environment's own, which a test takes at run time and never writes down; anything in production, such as its data or its traffic; and any ICE page.
- Persona: the product owner, who set the performance level, reads the verdict and decides each finding a person must decide; the developer gets back, as a handoff plan, each finding the builder can fix alone.
- Scope: In: measuring the running build in the testing environment, as one person meets it and under the load the pass bar names, the verdict against the profile's performance level, the handoff plans, and testing again as the product changes. Out: the review of each change with its performance rules, the tests inside the code, a story's own speed lines, the other kinds of testing, setting or moving the performance level, the deployment design, its costs and the environments, fixing, recording defects and running the plan.

## Expectation
- Scenario: A shop's checkout is built, and its profile sets performance at high, with a pass bar that says how long the checkout page may take to load when the number of shoppers it names use it at once, and how that time is measured. In the testing environment, the page loads in time for one shopper; under the named load, at the size Environment setup declared for load tests, it is too slow, because the basket is read again for each item. The product owner sees a verdict with that part failed and the conditions it was measured in. The developer gets a handoff plan that says the checkout page is slower than the level allows when many shoppers buy at once, and that the basket must be read once, with no figure and no test named. After the fix, the tests run again in the same conditions and pass.
- Done means: Someone other than the one who ran the tests runs them again on the same built work in the same conditions, gets the same verdict, and finds every part of the pass bar and each capability's performance need with a pass, a fail or a reason it was not measured, every figure with its conditions, no part counted as passed that was not measured in the conditions it names, no test outside the testing environment, and each finding sent where its way back says.
