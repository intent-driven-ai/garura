# Capability: Test performance

## Directional intent
Test performance, against the product profile's performance level: the running build is measured in the testing environment, as one person meets it and under the load its pass bar names, against the performance level the product profile commits to, and each finding goes back to the developer or to a person.
The product profile is the record of the product's shape and the quality levels it commits to. For performance, which the profile means as speed, it holds a level, one of none, low, medium, high and xhigh, and a pass bar: the standard or the measure that says when the product meets that level, such as how long a page takes to load and how that time is measured. Specify the product sets the profile, and each capability adds its own performance need under it: a level, a target someone can measure, and how it is checked, such as a test under load. In the product owner's words, Code → Validation "also needs to handle other forms of testing i.e. security and performance and accessibility, ux (responsive)", and he moved the planned performance testing here from Validation → Run: "The product is tested for how it performs." This capability runs those tests once the work is built and runs in the testing environment:
- How fast it answers one person. On each declared surface, it measures what the pass bar and each capability's performance need name, the way a person or another system meets the product there: how long a page takes to load, an endpoint takes to answer, a command takes to finish or an agent takes to reply. A surface is a place where a person or another system uses the product, such as a browser page, a command line or an endpoint another system calls.
- How fast it answers under load. When the pass bar or a need names a load, such as a number of people using the product at once, it puts that load on the running build, in the environment set up for it, and measures the same things.
- The verdict. Each part of the pass bar and each capability's performance need gets a pass or a fail, each part not measured is named with its reason, and the verdict is a pass only when every part passes.
- The way back. Each finding goes back as a handoff plan: what is slow, where, and the way back, never the test itself. It goes to the developer when the builder can fix it alone, and to a person when a person must decide.
- Again as the product changes. The tests run again after a fix, when more work is built, and when an approved decision raises the performance level, so that a pass stays true.

The review of each change is not repeated here. Check the code against its standards matches the review's performance rules, such as a database query inside a loop, against the lines each change adds, and Build the work test first runs the tests inside the code by a separate check. This capability takes both records as evidence. The builder's own word is not evidence: "A builder believes its own work, so its opinion isn't evidence."
What the tests measure comes from memory first: the project's own code and memory, then Garura memory, the memory Garura keeps for the project, then Phoenix memory, the shared memory on the machine that every project draws from. Only when none of them has an answer is it researched, and what research finds is raised as a memory update, a proposed addition to memory, and used only after a person approves it. Nothing comes from what the AI agent knows by itself, and above all no number: "A numeric constraint without a source is a hallucination dressed up as a fact."
It matters to software delivery planning because that domain turns a business intent into working code that a check from the outside can prove. This capability is that check for the performance level the product commits to.

Features:
- Measure how fast the running build answers, in the testing environment (fn-test-running-speed): once the built work runs in the testing environment, measures on each declared surface, by a part that is not the builder, what the pass bar and each capability's performance need name, as one person or one other system meets the product there, and records each figure with the conditions it was measured in.
- Measure how fast the running build answers under the load the pass bar names (fn-test-under-load): when the pass bar or a capability's performance need names a load, puts that load on the running build with made-up users, in the environment the deployment design places the load tests in and at its declared size, measures what the bar names under it, and never sends load outside that environment.
- Give the performance verdict, and send each finding to the developer or to a person (fn-send-performance-findings): gives one verdict for the built work against the profile's performance level, with a pass or a fail for every part of the pass bar and each capability's performance need, and sends each finding back as a handoff plan to the developer when the builder can fix it alone, or to the product owner when a person must decide.
- Test performance again as the product changes (fn-retest-performance): runs the performance tests again after a fix, when more work is built, when an approved decision raises the performance level, and when the environment the tests run in changes size, keeps each verdict, names what passed before and fails now, and sends a finding that keeps coming back to a person once the rounds the project allows are used up.

What is not built yet:
- Nothing tests a product against its performance level. Garura's own profile sets no performance level at all: it sets reliability, maintainability and security, and no capability in its model has a performance need.
- The old slice check, /validate-epic, is stale and waits for a rebuild. It ran page audits only on a local page, "Code-level + local-page audits only (C5).", read every score the audit gave, so one run could give both a performance score and an accessibility score, and compared each with a target written for the slice. It had nothing that put load on a build or timed an endpoint or a command.
- The quality auditor, an agent, can "Run Lighthouse audits (if threshold defined and URL provided)", a page audit, when a check asks; only the stale plays ask.
- The review of each change has performance rules, and it belongs to Check the code against its standards. They match words on the lines a change adds and the names of the files it changes, and at most they highlight: "Highlights without blocking."
- The scored quality check, built and never used, names three performance standard files that are in no memory tier.
- No testing environment is declared or built, and nothing says which tests run in which environment or what running them costs, because Environment setup and Deployment design are not built.
- Memory holds no rule for what a performance test must measure, how often a measure is repeated and which figure counts, or how a figure measured in an environment smaller than the real one is read. Whether the profile's scalability level, how much more load the product can take, is tested here is not decided.
- /validate-perf, the play name agreed for this work, is a name only.

### Benefit hypothesis
- Who it serves: the product owner, who set the performance level through the product profile, reads the verdict, and decides each finding that a person must decide; and the developer, who builds the code and gets back, as a handoff plan, each finding the builder can fix alone.
- What we believe: when the running build is measured in the testing environment, by a part that is not its builder, against the performance level and pass bar the profile commits to, a pass shows that the product meets that level in the conditions the bar names, if the work stands on these rules:
  - The yardstick is the profile's performance level and pass bar, with each capability's performance need under it.
  - A part that was not measured, or was measured in other conditions than its pass bar names, never counts as a pass.
  - The builder knows the level it must meet, but never gets the tests, their results or the verdict.
  - A handoff plan names what is slow, where, and the way back, never the test, its rule, its id or its tool.
  - No test touches anything outside the testing environment, and no test changes an environment's size.
- How we will know: two runs on the same built work, in the same conditions, give the same verdict; every part of the pass bar and each capability's performance need has a pass, a fail or a reason it was not measured; each figure names the conditions it was measured in; no test touched production; and no person finds, after a pass, the product slower than its pass bar allows in the conditions the bar names.
  - This is not tested today, because nothing tests performance.

### Boundary (In / Out / Never)
- In: measuring the running build in the testing environment, on its declared surfaces, as one person or one other system meets it, for what the pass bar and each capability's performance need name.
- In: measuring the running build under the load the pass bar or a need names, in the environment the deployment design places the load tests in.
- In: giving the verdict against the profile's performance level, after taking the records of the review of each change and of the build's separate test run as evidence.
- In: sending each finding back as a handoff plan, to the developer or to a person.
- In: testing performance again as the product changes, and when an approved decision raises the performance level.
- Out: the review of each change against its standards, with the review's performance rules on the lines a change adds. Check the code against its standards owns it; this capability reads its record and never runs the same rules again.
- Out: the tests inside the code, such as a test that times one piece of code. Build the work test first runs them by a separate check, and this capability takes that check's record as evidence.
- Out: a speed line in a story's expectations, such as a page that loads in under one second. The slice's eval tests it, in Test what the product does, with evals the builder never sees.
- Out: testing security, accessibility and the user experience on each surface. The other capabilities of Code → Validation own them. One run of a page-audit tool may give both a speed figure and an accessibility figure; a tool is not a capability, and the accessibility figure is Test accessibility's.
- Out: setting the performance level, its pass bar and each capability's performance need, and moving any of them. Specify the product sets them, and only an approved decision moves them; this capability reads them and never writes them.
- Out: which tests run in which environment, and what running the environments in the path costs on each cloud, the environment for load tests included. Deployment design owns them, and this capability reads them.
- Out: declaring and building the testing environment, and any environment of its own for performance tests, with its size, its data and its test accounts. Environment setup owns it.
- Out: fixing what fails. Build the work test first fixes a finding before the work is accepted, and Fix defects test first fixes one after.
- Out: recording a defect in the tracker, and making and running the plan, with the loops that run building and validation in rounds. Orchestration owns them.
- Never: test or load anything outside the testing environment: not production, not a builder's own machine, and no system the testing environment does not hold, such as a payment provider's live service. The reason, in the product owner's words: "We are never touching production."; and a builder's machine "is not where the path's tests are counted".
- Never: make an environment bigger or smaller, or change its data, to reach a pass. The reason: the size is set by Environment setup, and "The size declared here for each environment is what that cost is worked out for, so a change of size calls for the cost to be worked out again."
- Never: work out a figure for one environment from a figure measured in another, such as a larger load from a smaller one. The reason: no memory holds a rule for it, and "A numeric constraint without a source is a hallucination dressed up as a fact."
- Never: give the performance tests, their figures or the verdict to the builder or to any part that builds the work. Only the handoff plan reaches the builder. The reason: the level shapes how the builder writes code, as "performance budgets" do, but a result checked after the work exists is a failure condition, and "giving it to the builder only invites teaching-to-the-test."
- Never: skip, switch off or let through a finding, or loosen a test or its conditions, to reach a pass. The reason: Code → Validation must not "weaken a check to pass", and "The box moves ONLY by an approved decision."
- Never: count a part of the pass bar that no test measured as a pass. The reason: "An unmeasured bar is not a passed bar."
- Never: make a choice, such as what to measure, how often or under what load, from what the AI agent knows by itself. The reason: a source in the project or in memory can be checked and read back, while the agent's own knowledge cannot.

### Guiding rules
- Against the profile, per product. What is measured, its numbers and how it is measured come from the product profile and each capability's performance need, never from this capability. The reason: the approved list tests performance "against the product profile's performance level", and "The NUMBERS live in the product profile, per product — never in this KB."
- A tool's own score is not the verdict. Each figure is compared with the pass bar, and a page-audit score counts only when the pass bar names that score. The reason: the old slice check held that "Green is the entry condition, never the verdict".
- Not measured is never passed. A part that no test measured, a test that could not run, and a part the environment could not give the conditions for are fails, each named with its reason. The reason: "An unmeasured bar is not a passed bar."
- In the conditions the bar names, never worked out from another size. A figure counts only for the conditions it was measured in: the environment and its declared size, the made-up data and the load. When the environment cannot give the conditions the pass bar names, the part is named as not measured, and the product owner decides. The reason: no memory says how a figure from one size reads for another, and a guessed figure is no measure.
- The same conditions each run. How many tries a measure takes, and which figure of them counts, come from how the pass bar says it is measured; each run records its conditions, and a second run repeats them. The reason: the pass bar is "(the standard / how it's measured)", and a verdict that two runs cannot repeat proves nothing.
- Not the builder. A part that is not the builder runs the tests, on a copy of the built work. The reason: "A builder believes its own work, so its opinion isn't evidence."
- The builder knows the level, never the tests. The performance level and its pass bar shape how the builder writes code, so it knows them; the tests, their figures and the verdict are kept where no part that builds the work reads them. The reason, from the rule that divides the two: "Would knowing this change how the builder writes code?"
- What is slow, where, and the way back. A handoff plan says what is slow, on which surface and in what conditions, and what must be true again, as guidance, never code, and never names the test, its rule, its id, its tool or the figures measured. The reason: a handoff plan "never names the failure condition, its id or the check", and the builder gets no results.
- The builder only when it can fix it alone. A finding goes to the developer only when its way back is a change of the code the builder controls, from what it already has. One that needs judgment or authority the builder does not hold, such as a change of the architecture, of the deployment design or of an environment's size, or the performance level itself, goes to the product owner. When in doubt, a person. The reason: the recovery rule's test, "Can the builder fix this from information it already has, deterministically?", and the product owner's approval that he is "the one who gets a finding that changes the architecture".
- In the testing environment. The running build is measured on a copy in the testing environment that Environment setup declares, or in an environment of its own for performance tests that it declares, with its made-up data and its own test accounts, never in production and never on a builder's own machine. The reason: the assumption recorded with the product owner's list, that the performance tests of Code → Validation run "in the testing environment Environment setup declares, never in production."
- Inside the cost that is known. The load tests run where the deployment design places them, at the size Environment setup declares, so their cost is part of what Deployment design works out on each cloud; each run records how long it ran and what load it put on, so that cost can be checked. The reason, in the product owner's words: "For each one, we need to know what the cost looks like to get this piece figured out, running it across, and whatnot."
- Only a person moves the bar. A fail is fixed, or the product owner moves the performance level by an approved decision; a finding is never let through any other way. The reason: "The box moves ONLY by an approved decision."
- Records are evidence, not run again. The record of the review of each change and the record of the build's separate test run are taken as evidence. The reason, from the product owner's approved list: "BI-4 takes the record of BI-3's separate test run as evidence and does not run the same tests again."
- Rounds have an end. When the same finding comes back after the rounds the project allows, it goes to a person, not round again to the builder. How many rounds is a project setting. The reason: the old slice check stopped "after 3 rejections on the same epic", and "Everything that can be turned on or off lives in settings."
- The project's memory first, then Garura memory, then Phoenix memory, then research through a memory update a person approves. What nothing answers stays open, with no default, and is named as not measured. The reason: research is new knowledge that nobody has checked yet, and the person's approval is the check.
