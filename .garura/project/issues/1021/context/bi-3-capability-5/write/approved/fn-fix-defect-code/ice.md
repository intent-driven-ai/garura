## Intent
- Goal: Once every test that proves the defect has failed on the check's record, the builder changes the code from the cause and what the fix changes, with no design to follow and in the order it chooses, until the record of a separate check, which runs every test of the project through a tool on the model or service the test model setting names, shows them all passing; then it tidies the code it changed without changing what it does, with every test still passing and no test file changed by it, all without ever seeing a test; and when a result still fails after the tries the project allows, the defect goes back to be understood again, the tests updated first.
- Limit: The builder is never handed a test, a test file, the test writer's part of the understanding, an eval, the hidden file or the evals folder, never writes or changes a test, and learns from the check only which results still fail.
- Limit: The builder changes only the files the understanding names, or writes why in the fix's record; the tidy stays inside the code the fix changed; and after the tries the project allows it stops, so the defect is understood again rather than tried again the same way.
- Limit: The check is never the builder; it runs every test of the project, changes no code and no test, takes each test file's fingerprint at its first run and its last, and a pass counts only on its record, never on the builder's word.
- Fails if: The builder was handed or read a test, a test file, an eval or the evals folder, or a test changed, was weakened or went away between the check's first run and its last with no reason from the test writer.
- Fails if: The defect is called fixed while the check's record shows any test of the project failing, or when the check ran only the new tests, or with no check run after the tidy.
- Fails if: A file outside the understanding changed with no reason, the tidy changed what the code does, or the same fix was tried again after the tries ran out with no new understanding.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the builder's part of the understanding, with the feature, the cause and what the fix changes; the project's code and coding standards; the dev sandbox where the code runs while it is fixed; the project's test model setting; the project's test tool and how it runs every test; what the check says still fails; and the check's earlier records for the same fix.
- Never read: for the builder, any test of the project, the test writer's part of the understanding, the plan's evals folder, the eval, the slice's hidden file and any ICE page; for the check, the plan's evals folder, the eval, the slice's hidden file and any ICE page.
- Persona: the developer who fixes the code, a person or an AI agent who is never the test writer of the same fix and never the one who understood it, and who learns from the check what is left to fix.
- Scope: In: the fixed code, changed to the cause and what the fix changes until every test of the project passes on the check's record; the check's runs at its three moments, through a tool on the model or service the setting names, with their records and fingerprints; telling the builder what still fails; the tidy; and sending a fix that does not hold back to be understood again. Out: understanding the defect, writing and updating the tests, the evals, checking the code against the standards, landing the change, the dev sandbox, and keeping the setting.

## Expectation
- Scenario: In a bank's payments service, a report says a transfer of exactly the daily limit is refused. The understanding names the feature, Send a transfer, the cause, a limit check that lets a transfer through only when it is below the limit, and the one function to change. The builder is handed that, and no test. It changes the comparison and asks the check, which runs every test of the project through a tool on the model the test model setting names: two of the three new tests pass, but the result for a transfer of exactly the limit in a foreign currency still fails. The builder is told which result fails, not the test. After the two tries the project allows it still fails, so the builder stops. The defect is understood again: the foreign-currency path checks the limit in a second function, and the earlier understanding is kept with why it changed. The test writer adds a test for that second function, and the check shows it failing. The builder fixes the second function, and the check finds every test of the project passing. It joins two lines that read the limit the same way, and every test still passes, with no test file changed by the builder.
- Done means: Someone other than the builder compares what the builder was handed and the fix session's record with the check's records, and finds no test, eval or evals folder handed or read, every test of the project passing on the last record, no test file changed by the builder, each file outside the understanding with its reason, and each round after a stuck fix starting from a new understanding with its tests shown failing first.
