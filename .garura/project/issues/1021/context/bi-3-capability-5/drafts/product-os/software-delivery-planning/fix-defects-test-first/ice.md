Thin: proposed from the person's words; deepen with `/discover-capabilities`.

## Intent
- Goal: A defect reported anywhere is fixed quickly and test first, with no full design: the developer who will write its tests matches it to the feature of the product model it breaks, finds the tests that exist and why they pass, and finds its root cause; the tests that prove the defect are written by that test writer and shown to fail by a separate check before any fix code; then the builder fixes the code, without seeing a test, until the check finds every test of the project passing, and tidies the code it changed while they all stay passing. A defect no feature covers is named as a new need and not fixed.
- Limit: The builder is never given a test, a test file, an eval, the hidden file or the evals folder, never writes or changes a test, and learns from the check only which results still fail.
- Limit: The fix writes only what it needs, never a design document or steps for the builder, and never goes through Design the work; what it follows comes from the project's code and memory first, then Garura memory, then Phoenix memory, or from research only after a person approves it as a memory update; and it changes no work item, plan file or status.
- Limit: A pass counts only on the record of the separate check, which runs every test of the project through a tool on the model or service the test model setting names, apart from the model that fixes the code, never on the builder's word.
- Fails if: A defect is fixed with no feature of the product model named, or a defect no feature covers is fixed instead of named as a new need.
- Fails if: Fix code was written before every test that proves the defect failed on the check's record, or the builder read or was handed a test, or a test changed or went away with no reason from the test writer.
- Fails if: The defect is called fixed while any test of the project fails on the check's record, or the fix went through a full design.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the defect report as it was given; the product model's features and capabilities; for a bug in a plan, the plan file and the story it sits under; for the test writer, the project's code and its history, the tests it already has, its test tool and the way its tests are written; for the builder, the cause, what the fix changes, the project's code and its coding standards; for all, the project's settings, the dev sandbox where the code runs while it is fixed, and the ontology's rules for a feature, a story, a bug and what a builder reads.
- Never read: for the builder, any test of the project, the test writer's part of the understanding, the plan's evals folder, the eval, the slice's hidden file and any ICE page; for the test writer, the builder's code while it is written, the plan's evals folder, the eval, the slice's hidden file and any ICE page.
- Persona: the developer, a person or an AI agent, in two parts never held by the same one for the same defect: the test writer, who understands the defect and writes the tests that prove it, and the builder, who fixes the code; the technical lead agrees the fix when the project's setting asks for it.
- Scope: In: taking in a defect reported anywhere, understanding it against the product model, its tests and its code, naming a new need, writing the tests that prove the defect and showing each one fails, running every test of the project apart from the builder through a tool, fixing and tidying the code, and understanding the defect again when the fix does not hold. Out: recording the defect in the tracker, specifying a new need, keeping the model matched to what is built, gathering the work, designing the work, building stories, chores and spikes, the evals, running them and the verdict, checking the code against the standards, choosing and tracking the work and its statuses, landing the change, the dev sandbox, and keeping the settings.

## Expectation
- Scenario: In a shop's checkout, a person reports that a guest's total is wrong when the same discount code is entered twice. The test writer finds the feature in the product model, Apply a discount code, and two tests for discounts that both pass, because neither enters a code twice. It traces the cause to the function that adds discounts, which adds a code again each time it is entered, and names the one file the fix changes. The same week another report asks the checkout to split a bill between two cards; no feature covers it, so it is named as a new need for Specify the product and not fixed. The test writer, on the model the project's test model setting names, writes two tests for the discount, and the check shows both fail. The builder, handed the feature, the cause and the file to change, and no test, changes the function, and the check finds every test of the project passing. The builder joins two lines that read the codes the same way, and the check finds every test still passing and no test file changed. No design document was written.
- Done means: Someone other than the builder compares the check's records with the tests, and finds each new test failed before any fix code, every test of the project passing after the fix and after the tidy, and no test file different between the first run and the last.
- Done means: Someone other than the test writer reads the understanding against the product model, the code and the report, and finds the feature named, each test that existed with why it passed, and a cause with the file, the logic and why it is wrong, and finds no design document and no test in what the builder was handed.
