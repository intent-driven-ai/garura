## Intent
- Goal: Once every test for the work has failed on the check's record, the builder writes all the code for every story, chore and spike under the chosen item, from its own part, each story's collected context and the design, in the order it chooses, until the record of a separate check, which runs the tests through a tool on the model or service the test model setting names, shows every test for the work and every test the project already had passing; then it tidies the code where it needs it without changing what it does, with every test still passing and no test file changed, all without ever seeing a test.
- Limit: The builder is never handed a test, a test file, the test writer's part, an eval, the hidden file or the evals folder, never writes or changes a test, learns from the check only which expected results still fail, and a read of a test file or the evals folder is flagged in the build's evidence.
- Limit: The builder builds and tidies to the design and the project's code and coding standards, found in the project's memory first, writes just enough, keeps the design's names and interfaces in the tidy and stays inside the work, sends each departure from the design back to the technical lead with its reason, and sends an expected result it cannot make pass after the tries allowed back to the technical lead or the test writer.
- Limit: The check is never the builder; it runs the tests through a tool on the model or service the test model setting names, apart from the model that builds the code, changes no code and no test, takes each test file's fingerprint at its first run and its last, and a pass counts only on its record, never on the builder's word.
- Fails if: The builder was handed a test, a test file, the test writer's part, an eval, the hidden file or the evals folder, or a read of one in the session's record has no flag, or a test changed, was weakened or went away between the check's first run and its last.
- Fails if: The work is called built while the check's record shows a test for it, or a test the project already had that passed before the build, failing, or with no check run after the tidy.
- Fails if: The tidy changed what the code does, code outside the work or a name the design gave, or the tests were run by the builder, by an agent's judgment instead of the tool, or on another model or service than the test model setting names.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the builder's part of each gathered story and its collected context, the design of the work with its components, classes, functions, interfaces, data model, libraries and patterns and where each part runs, the project's code and coding standards, the dev sandbox where the code runs while it is built, the project's test model setting, the project's test tool and how it runs the tests, the tests it already has, what the check says still fails, and the check's earlier records for the same work.
- Never read: for the builder, the tests for the work, the test writer's part, the plan's evals folder, the eval, the slice's hidden file and any ICE page; for the check, the plan's evals folder, the eval, the slice's hidden file and any ICE page.
- Persona: the developer who builds the code, a person or an AI agent who is never the test writer of the same work, and who learns from the check what is left to build; the technical lead receives each departure from the design.
- Scope: In: the code for every story, chore and spike under the chosen item, built to the design in the order the builder chooses until every test passes on the check's record; the check's runs at the three moments, through a tool on the model or service the setting names, with their records and fingerprints; telling the builder what still fails; the tidy; and the departures and the work that could not be made to pass, sent back. Out: the tests, the evals, updating the design, a bug's fix, checking the code against the standards, the dev sandbox, keeping the setting and which models there are, and choosing what is built next.

## Expectation
- Scenario: In a library's loans service, the project's test model setting sends the tests to a different model from the one that builds the code, and a tool runs them. The builder is handed two stories' parts, their collected context and a design that names a renewal function in the loans module, and no test. It builds the function and the endpoint, asks the check, and learns that one expected result, a renewal refused when the book is reserved, still fails. It adds the reserve check, and the check's record shows all eleven tests and the project's earlier tests passing. The design named a separate notice module, but the project's code already sends notices from the loans module, so the builder builds it there and sends the departure with that reason to the technical lead. It then joins two functions that read a due date the same way into one helper inside the work, and the check's record shows every test still passing and every test file the same as at the first run. The session's record shows no read of a test file or the evals folder.
- Done means: Someone other than the builder compares what the builder was handed and the session's record with the check's records, and finds no test, test writer's part or eval handed or read, no test changed, and each departure from the design sent with its reason.
- Done means: Someone other than the builder reads the check's records and the code before and after the tidy, and finds every test passing on the last record, the tests run through the tool on the model or service the setting names, every fingerprint the same as at the first run, and no tidy outside the work or to a name the design gave.
