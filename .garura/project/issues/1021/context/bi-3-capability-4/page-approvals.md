# Page approvals, BI-3 capability 4 (Build the work test first)

- The product owner's words on this capability, given on 2026-11-09 and recorded here as given so the pages can quote them:
  - "we have to do this such that coding is also test driven"
  - "You write the test, make sure they are failing, then you build the code, then you refactor if needed, and then you move forward. Make sure that is incorporated properly."
  - "write just enough ... Don't take it literally, because we are in coding. What we don't want is that every single line of code is being written sequentially. This can be grouped so that all the tests are written, and then all the code is written to make sure all the tests are passing. The only difference is that the code, when being written, should not get to see what tests there were ... That needs to be hidden out. That functionality is also being built somewhere."
  - "The coding will be done by the developer, including the TDD."
  - "this design is input for writing code and building the application"
- The name, agreed: "Build the work test first". It takes over "Build the work" from the Code → Validation list ("Each work item, whether a slice, a feature, a story or a chore, is built end to end from its design."), and test-driven development is its rule, not a capability of its own.
- No page of this capability is approved yet. The drafts wait for his review, one page at a time.
- 2026-11-09, the product owner on the first overlap brief (six features, eight leans, and the proposal to merge running the tests, building and tidying into one feature): "i need a config that would send test building and running to a differnet model, like a codex or another service. test running can be done via a tool. rest is fine". Agreed: four features (write the tests first and show they fail; build the code until every test passes, then tidy it, without seeing the tests; write the usage guide; update the tests and the code as the work changes); the test writer reads the design's classes, functions and interfaces; on a rename the test writer updates the tests and shows them failing first, and the builder never edits a test; the builder writes the usage guide and the names are matched when the eval runs; the tests are never handed to the builder, and a read of a test file is flagged; the capability ends when every test passes after the tidy and the guide is written, and a failing eval the builder can fix comes back here; no status set, nothing landed; the developer as persona in two roles never held by one for the same work; how much the builder is told about a failing test left open. Added: a setting that sends the writing and the running of the tests to a different model, such as Codex, or another service; the tests can be run by a tool.
