## Intent
- Goal: Every agent decides only from memory it finds through the one memory tool, in short-term memory, then Garura memory, then Phoenix memory; nothing from the model or the web enters memory before a person approves it, one update at a time; every memory write lands in the issue's short-term memory and moves up a tier only on a person's yes; every decision keeps its trace and its sources are checked again; Phoenix memory reaches each machine, stays in step with Garura's source and is versioned per release; and what memory holds is checked before it is used, so that nothing an agent decides from sits outside memory.
- Limit: Only a person decides a memory update or a promotion; an agent drafts and never decides.
- Limit: No part reads a memory file by its path, and a play reads no memory.
- Limit: Every memory write goes to the issue's short-term memory, and nothing is copied from Phoenix memory into a project.
- Limit: The cards where a person decides, building a project's Garura memory, laying the tool in a project, and what each rule says stay with their owners.
- Fails if: An agent decides from a page it did not find through the memory tool, from the model or the web with no approved update, or from an update that waits for a person.
- Fails if: Garura memory or Phoenix memory changes with no person's yes on record.
- Fails if: A decision has no trace, or the trace check does not name a step whose source changed or is gone.
- Fails if: At a release, a page differs between Phoenix memory and Garura's source and no person decided on it.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the memory tool's contract, settings and commands; the memory guide and the shared Memory Reading Protocol; each issue's memory updates and decision records; the component linter's memory rules; Phoenix memory's source, its approved version and its place on the machine; the pages that differ between Phoenix memory and Garura's source; the approved pages that hand memory work here; and the product owner's answers on the engine's rules and on promotion.
- Never read: any memory file by its path, and any ICE page; nor another issue's short-term memory, or a memory update that waits for a person, as a source to decide from.
- Persona: the product owner, who approves or rejects each memory update and each promotion; and the developer, a person or an AI agent who builds the code and decides from memory.
- Scope: In: finding memory across three tiers through one tool, memory updates decided by a person, each decision's trace and its check, the rule and the checks that every part reads through the tool, bringing Phoenix memory to a machine and keeping it current; and, not built yet, keeping Phoenix memory in step with Garura's source with versions and notes, moving a page up a tier and choosing what is learned, checking what memory holds, and keeping what agents decide from inside memory. Out: the cards in Argus, proposing what was learned, building a project's Garura memory, laying the tool in a project, Garura's own release, the product model's content, what each rule says, where the tiers' folders sit and what each setting means, a loop's questions, and the way past a gate.

## Expectation
- Scenario: In a clinic's booking app, the developer's agent needs to know how long a password reset link lasts. Short-term memory and Garura memory have nothing, and Phoenix memory's user-management page answers; the agent cites the page's lines with their fingerprint. A week later the agent needs a rule no tier holds, so it raises a memory update that blocks its work; the product owner approves it with their own words, the update is written to the issue's short-term memory, and the product owner later says yes to moving it up to Garura memory. In a bank's payments service on the same machine, a page in Phoenix memory changes after a decision rested on it, and the trace check names that step.
- Done means: Someone other than the one who built it reads the clinic's issue folder, its memory updates, its decision records and Garura memory, and finds the reset-link decision citing Phoenix memory's lines; the update approved by the product owner, with their exact reply, before it was applied; the page in Garura memory only after the product owner's yes on its promotion; no memory file read by its path; and, for the bank, the trace check naming the changed step.
