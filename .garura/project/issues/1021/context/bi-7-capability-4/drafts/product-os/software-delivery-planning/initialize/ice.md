## Intent
- Goal: After the install, with Phoenix memory reachable, one run of Initialize sets the project up from the product owner's answers to one short set of questions built from Phoenix memory, each with its choices and a proposed answer that names its source: the project's Garura memory holds only the memory blocks its own answers call for, from the one Phoenix memory on the machine and never a copy of a whole Phoenix file, so two projects with different answers hold different blocks; the product profile records the answers; a record names each review rule group as kept or skipped with the answer that decided it; the tracker holds each issue type Garura files, or a stand-in the product owner said yes to, or the brief names the type as still missing; and a later run follows the project and Phoenix memory as they change.
- Limit: Never make a tracker type or a stand-in before the product owner's typed yes, and read memory only through the memory tool.
- Limit: Never write an answer the product owner did not give or confirm, and never write Phoenix memory or another project's memory.
- Limit: Never decide what memory may hold, what a rule group checks or what a tracker type means; Initialize asks and records.
- Fails if: a proposed answer names no source, or an answer is recorded that the person never gave.
- Fails if: a review in the project still runs a rule group the answers rule out, or its record does not name the groups it skipped.
- Fails if: after initialize ran, an issue type Garura files is neither in the tracker nor mapped to a stand-in the product owner said yes to, and the brief does not name it as missing.
- Fails if: initialize builds a project's memory while Phoenix memory cannot be reached.
- Fails if: a project's Garura memory holds a whole Phoenix file, or a part of Phoenix memory its answers did not select.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: what Phoenix memory holds for each question's choices; the project's files and settings, and the trackers its settings name; the product profile and any earlier answers in it; the review's rule groups as the review's owners name them; each tracker's types, through the adapter; and the project's own Garura memory with its list of blocks.
- Never read: any memory file by its path, and any ICE page.
- Persona: the product owner, who sets the project up right after the install and says yes before anything is made in the team's tracker.
- Scope: In: the setup questions, building the project's memory, the rule-group record, the tracker's issue types, running again as the project changes, and each project's own blocks as Phoenix memory changes. Out: the install, the upgrade, each coding tool's shape, how Phoenix memory reaches the machine, what may enter each memory tier and promotion, running the review and what each group checks, what each tracker type means and filing work items, the profile's levels, and changing the review and the filing plays to read Initialize's records.

## Expectation
- Scenario: A clinic's booking app has just had the install, in a GitHub organization with no Epic type. The product owner starts Initialize and answers one brief: a React front end, a database, patient data, and no running service yet. The project's Garura memory then holds what was built from the React, database and personal-data parts of Phoenix memory and nothing else; the product profile lists each answer with its question; the rule-group record skips the running-service group with its answer and keeps the rest; and after the typed yes the Epic type is made and named in the record. A second run with the same answers changes nothing.
- Done means: Someone other than the one who ran Initialize checks, on a test project, its memory folder (only the selected parts, and no whole Phoenix file), the product profile, the rule-group record and the tracker's type list against the answers and the yes replies, and finds them matching.
