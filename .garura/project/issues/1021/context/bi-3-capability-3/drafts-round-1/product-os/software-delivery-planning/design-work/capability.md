# Capability: Design the work

## Directional intent
Design the work under a chosen plan item before it is built: how it is built, and what a person meets on its surface, against the project's standards.
A business intent is what a person or the organisation wants, in their own words. Its plan holds its work items as a tree, and each work item is an issue in the team's tracker, the tool where the team keeps its issues. Each slice, an ordered group of features that one person can test end to end on one surface, has one epic that stands for it. Under an epic sit stories; a story stands for one feature of the product and delivers it. Under a story sit its chores, bugs and spikes: a chore is upkeep for the story, a bug is a defect its work brought in, and a spike is a proof tried on the built story.
The technical lead names one item of the plan by its ID, and Gather the work under a chosen plan item gathers it and every item under it into short-term memory, the issue's own folder where a run keeps its working files. This capability designs that gathered work, every item under the chosen one, in one design with two parts:
- the technical design: the low-level design of how the work is built. It names the classes and functions to create or change, each with its one job, the reusable patterns to follow, where each part lives in the project's code, and code samples that show their shape;
- the surface design, the UX design in the product owner's words: what the person or system that uses the work sees and does on its surface, such as a command and what it prints, a screen with its flows and states, or an endpoint and what it gives back. A surface is a place where a person, or another system, opens the product to use it.

In the product owner's words: "Doing that means doing a low-level technical design and understanding what classes, what functions, and any reusable patterns need to be created. You should probably be putting some code samples that need to be put in."
The design is made against the project's standards, which Spec → Design sets for the whole project: the project's architecture with its technology, the declared surfaces with their properties and guidelines, the deployment design and the environments. The design follows them and never changes them. A need they do not cover is named as a gap and goes back to the capability that owns it, and the design goes on.
The design reaches the builder, the developer who later builds the code test first. So it starts only from the builder's part of the gathered work, and it never holds an eval, a test, a success scenario or a story's expectations. In the product owner's words: "the code, when being written, should not get to see what tests there were".
Each choice comes from memory first: the project's own code and memory, then Garura memory, the memory Garura keeps for the project, which holds the product model, then Phoenix memory, the shared memory on the machine that every project draws from. Only when none of them has an answer is it researched, and what research finds is raised as a memory update, a proposed addition to memory, and used only after a person approves it. Nothing comes from what the AI agent knows by itself.
An AI agent proposes the design and the technical lead confirms or changes each choice. Nothing waits for the design, and it is updated as the work changes.
It matters to software delivery planning because that domain turns a business intent into work that agents can build. This capability is where the gathered work gets its design before the developer builds it, so everything under the chosen item is built to one design. In the product owner's words: "everything under it gets designed".

Features:
- Design the chosen work, how it is built and what its surface shows (fn-design-chosen-work): for the tree gathered under the item the technical lead names, designs each story, chore and spike in one design with a technical part, down to its classes, functions, reusable patterns and code samples, and a surface part, what a person sees and does there, against the project's standards and with no test in it.
- Update the design as the work changes (fn-update-work-design): when the work, a project standard or what the build finds no longer matches the design, the technical lead confirms an update, and what held before stays readable with why it changed.

What is not built yet:
- Neither feature is built. Nothing designs a story, a chore or a spike, or the work under a chosen item.
- The only live design of a piece of work is the design of a bug fix, inside the bug fix play: the root cause, a fix with at least one other way weighed and why it lost, each file it changes, and the steps a code builder follows. It is live only in a full install, and Fix defects test first keeps it.
- The old design plays for one slice are stale and wait for a rebuild. One designed the parts a slice passes through and their technology; one designed its screens, flows and states. They designed one slice at a time, so the first slice's choices would have become the whole product's.
- An older skill writes a low-level design: the components with their jobs and interfaces, the libraries, a data model, and which component each feature lives in. No play calls it, and the files it reads were deleted with the retired planning chain.
- A play where a person designs one story with the agent, in a design with a tech part and a surface part, is recorded and not built (#978). It asks for one standard for a design; no memory tier holds a standard or a template for one.
- None of the project's standards from Spec → Design is built, and the product model has no kind for any of them, so where the design reads them is not decided.

### Benefit hypothesis
- Who it serves: the technical lead, who designs the work under the chosen item; and the developer, who builds the code test first from the design.
- What we believe: when the work under a chosen item is designed before it is built, everything under it is built to one design that fits the project's standards, and the developer does not invent its own classes, patterns or surface, if the work stands on these rules:
  - Every story, chore and spike under the chosen item is designed, technically and for its surface.
  - The design follows the project's standards and never changes them; what they do not cover is named as a gap.
  - The design holds no eval, test, success scenario or story expectation.
  - Each choice comes from the project's code and memory first, names its source, and the technical lead confirms it.
- How we will know: the developer builds each item from the design without asking for a class, a pattern or a screen the design left out; the items built under one chosen item share the classes and patterns the design named; no built item breaks a project standard; and a search of the design finds no eval, test, success scenario or expectation.
  - This is not tested today, because nothing designs the work under a chosen item.

### Boundary (In / Out / Never)
- In: designing every story, chore and spike under the chosen item, in one design, from the builder's part of the gathered work and each story's collected context.
- In: the technical design: the classes and functions to create or change, each with its job and how it is called; the reusable patterns to follow, the project's own first; each file the work adds or changes; and code samples that show their shape.
- In: the surface design: on the work's one surface, what the person or system that uses it sees and does, such as the command and what it prints, the screens with their flows and states, or the endpoint and what it gives back.
- In: reading the project's standards from Spec → Design and the project's code, and naming each need the standards do not cover as a gap for the capability that owns it.
- In: updating the design as the work changes, keeping what held before and why it changed.
- Out: choosing the item, gathering the tree under it, splitting each story into the builder's part and the test writer's part, and collecting each story's context. Gather the work under a chosen plan item owns them.
- Out: setting or changing the project's architecture and technology, its surfaces with their properties and guidelines, its deployment design and its environments. Design the technology and architecture, Manage surfaces, Deployment design and Environment setup own them, and each gap named here goes back to the one that owns it.
- Out: how the project runs: where the work runs, and how it is tested and released in each environment. Deployment design owns it, and nothing about it is designed here.
- Out: writing the evals and the slice's hidden file of failure conditions. Write the evals that check the work owns them; this capability never reads them.
- Out: writing the tests and the code from the design, and the order the developer builds in. Build the work test first owns them, and the developer does that work.
- Out: the root cause and the fix design of a bug gathered under the chosen item. Fix defects test first owns them; the design names the bug and leaves its fix there.
- Out: making and changing the plan and its work items, and writing each story. Turn intents into agent work holds them today. When the design finds a work item that does not fit, it names it.
- Out: putting what the design decides into the product model. Keep the spec matched to what's built owns it.
- Out: writing or deepening an ICE, the agent's intent for one capability or feature. Specify the product owns it.
- Never: put an eval, a test, a success scenario, a story's expectation or a failure condition in the design, or name the evals folder, the hidden file or an ICE page. The reason, in the product owner's words: "the code, when being written, should not get to see what tests there were". A builder "cannot teach to a test it cannot see."
- Never: read the test writer's part, the plan's evals folder, an eval, the hidden file or an ICE page. The reason: the design reaches the builder, so what the designer reads can pass into it.
- Never: change a project standard, or decide for the whole project what Spec → Design has not set. The reason: each piece of work is "designed and built on the project's architecture, and does not choose its own", and a choice made in one piece of work would bind every later one.
- Never: stop the work on a missing standard. The design goes on from the project's code and memory, says what it chose, and the gap stays on record. The reason: "Nothing waits for the architecture", and the Spec → Design business intent blocks no work.
- Never: make a choice from what the AI agent knows by itself. The reason: a source in the project or in memory can be checked and read back, while the agent's own knowledge cannot.
- Never: change a work item, the plan file or a status. The reason, in the product owner's words: "This intent's job is to execute on the plan".

### Guiding rules
- The whole tree, one design. Every story, chore and spike under the chosen item is designed in the same run, in one design, so what they share is designed once. The reason, in the product owner's words: "everything under it gets designed".
- Down to the classes and functions. The technical part names each class and function to create or change, the reusable patterns, and code samples that show their shape. The reason, in the product owner's words: "what classes, what functions, and any reusable patterns need to be created".
- Both parts, every time. Each item has a technical part and a surface part; an item with nothing on a surface says so, with the reason. The reason, in the product owner's words: "both technical design and surfaces are important".
- What the project already has comes first. The design reads the project's code for the classes, functions and patterns already there, and reuses or extends them before it names a new one. The reason: the design agent that exists starts from "What already exists? What patterns are used?", and for each pattern it finds it says "how to follow/extend this pattern".
- The project's standards bind the design. It follows the project's architecture and technology, the declared surface the work is on with its properties and guidelines, the deployment design and the environments. The reason: "Without shared positions, each builder invents its own answer."
- Made for its one surface. The design is made for the surface the work's slice names, and keeps to that surface's properties and guidelines, such as working within the project's design system, the shared colours, type and components every screen is built from. The reason: a design made for the wrong surface is drawn again, as when "a surface meant to be a web page was designed as a terminal command".
- Each choice names its source and what else was weighed. The reason: a person can check each choice without a search, and the one design that is built already refuses a choice with no other way weighed: "Every alternative must carry a concrete `rejection_reason`."
- Code samples show the shape of a class, a function or a pattern, and are never a test. The reason, in the product owner's words: "You should probably be putting some code samples that need to be put in.", and the code "should not get to see what tests there were".
- The project's memory first, then Garura memory, then Phoenix memory, then research through a memory update a person approves. A choice that nothing answers stays open, with no default, and the rest of the design goes on. The reason: research is new knowledge that nobody has checked yet, and the person's approval is the check.
- The technical lead confirms the design. The agent proposes each choice, and the technical lead confirms or changes it. Nothing waits for the design, and it can be updated at any time. The reason, in the product owner's words: "designs are going to be done by, let's say, a technical lead or an architect, maybe a technical lead.", and on the project's design, "we can run this anytime."
- What does not fit is named, not fixed. A work item that does not fit the design, or a standard that does not cover it, is named for the capability that owns it. The reason: the design changes no work item and no standard, and a person is never stopped without a choice.
