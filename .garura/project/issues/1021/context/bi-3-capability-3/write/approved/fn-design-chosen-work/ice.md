## Intent
- Goal: Every story, chore and spike in the tree gathered under the item the technical lead names gets, before it is built, a technical part that names its components, classes, functions, data model, interfaces, libraries, reusable patterns and files, drawn as diagrams in the project's design style that a CTO who is not hands-on can read, and a surface part that says what a person or system sees and does on its one surface and shows each screen as the project's screen design setting says, in one design that is the input for writing the code, made against the project's standards and confirmed by the technical lead.
- Limit: The design starts only from the builder's part of the gathered tree and each story's collected context; it never reads the test writer's part, the evals folder, an eval, the hidden file or an ICE page, and neither it, its sample code nor its prototype holds an eval, test, success scenario, story expectation or failure condition.
- Limit: The design follows the project's architecture and technology, the declared surface with its properties, guidelines and design system, the approved deployment design and the environments, and never changes them; libraries and data stay inside the architecture's technology, each component runs where the deployment design runs it, and a need they do not cover is named as a gap for the capability that owns it.
- Limit: Each choice and each design style reuses what the project's code and memory already have first, then Garura memory, then Phoenix memory, or comes from research only after a person approves it as a memory update; each choice names its source and the other ways weighed; sample code is written only when the sample code setting is on.
- Fails if: A story, chore or spike under the chosen item has no technical part drawn as diagrams, or no surface part that shows each screen as the screen design setting says and no line that says why it has none, or the design covers an item from outside the chosen item's tree.
- Fails if: The design, its sample code or its prototype holds an eval, a test, a success scenario, a story's expectation or a failure condition, or names the evals folder, the hidden file or an ICE page.
- Fails if: A choice in the design breaks a project standard, such as a library or data store the architecture does not name or a component placed where the deployment design runs nothing, or has no source in the project, in memory or in a memory update a person approved.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the builder's part of the gathered tree and each story's collected context, the one surface the work's slice names, the project's architecture with its technology, the declared surface with its properties, guidelines and design system, the approved deployment design with its services, container platform and cloud, the environments, the components, classes, functions, data, files and patterns already in the project's code, the project's sample code, design style and screen design settings, the styles for drawing a design that memory holds, and the memory's learnings for that kind of surface and technology.
- Never read: the test writer's part, the plan's evals folder, the eval, the slice's hidden file and any ICE page.
- Persona: the technical lead, who designs the work under the chosen item with an AI agent and confirms each choice; a CTO reads it from its diagrams, and the developer later builds from it, test first.
- Scope: In: the technical part with its diagrams and, when the setting asks, its sample code, and the surface part with the look of each screen, for every story, chore and spike under the chosen item; the gaps in the project's standards, the work items that do not fit, and the bugs named for their fix. Out: gathering the work, setting the project's standards, keeping the settings, updating the design later, the tests, the code and building the application, the evals and the hidden file, a bug's fix, and the product model.

## Expectation
- Scenario: The technical lead of a team's task tool, a command a person runs in a terminal, names a story with a chore and a bug under it. The sample code setting is off. The design gives the story a new component beside the project's existing task store, its interface, the one new field in the data model and the library it already uses, drawn as diagrams in the project's design style and placed in the one service the deployment design runs; its surface part names the command, what it prints and how a person answers. The chore gets a technical part and a line that says it has no surface because it only tidies the store's files; the bug is named for Fix defects test first. A choice of how long a task is kept, which no memory tier holds, is raised as a memory update and stays open. The design holds no sample code, and the technical lead confirms it.
- Done means: Someone other than the one who designed the work compares the design with the gathered tree, the project's standards and its settings, and finds every story, chore and spike with its diagrams and both parts or a reason for no surface, each screen shown as the setting says, none from outside its tree, each choice with its source, and no standard broken.
- Done means: Someone other than the one who designed the work searches the design, its sample code and its prototype, and finds no expectation, eval, test, success scenario or failure condition, and no name of the evals folder, the hidden file or an ICE page.
