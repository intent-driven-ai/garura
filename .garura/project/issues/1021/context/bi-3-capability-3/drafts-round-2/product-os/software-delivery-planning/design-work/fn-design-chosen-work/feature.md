# Feature: Design the chosen work, how it is built and what its surface shows

## What it does
For the tree gathered under the item the technical lead names, this feature designs every story, chore and spike in one design, with a technical part and a surface part, against the project's standards, before any of it is built. The design is the input for writing the code and building the application.
- It starts from what Gather the work under a chosen plan item put in short-term memory, the issue's own folder where a run keeps its working files: the builder's part of the gathered tree, which holds each story's title, goals, limits and Context guidance and the text of each chore, bug and spike, and each story's collected context. A story stands for one feature of the product; a chore is upkeep for a story, a bug is a defect its work brought in, and a spike is a proof tried on the built story. The builder is the developer who later builds the code test first.
- It reads the project's standards from Spec → Design itself: the project's architecture with its technology; the declared surface the work is on with its properties, guidelines and design system; the approved deployment design, which says which services run, what each part runs as, on what container platform and on which cloud; and the environments. It reads the project's code for the components, classes, functions, data and patterns already there.
- It reads three of the project's settings. A setting is a choice a team makes once for the project, kept in Garura's settings with everything that can be turned on or off. The sample code setting says whether the design also writes sample code; the design style setting says the style the technical part is drawn in; the screen design setting says whether each screen is shown as wireframes in Markdown files or as a prototype built with the project's design system.
- The technical part, for each item:
  - the components, each with its one job, and the classes and functions inside them, each with its job and how it is called;
  - the data model: the things the work keeps, their fields and how they relate, in the data store the architecture names;
  - the interfaces: what each component offers the others, such as its functions, its endpoints or its messages;
  - the libraries it uses, each with its version and why, within the technology the architecture names;
  - the reusable patterns to follow, the project's own first, and each file the work adds or changes;
  - where each component runs, in a service the approved deployment design names.
- The technical part is drawn as diagrams, with text beside them, in the style the design style setting picks, so that a CTO who is not hands-on can read what will be built. What each style draws, and how, comes from memory.
- When the sample code setting is on, the design also writes sample code that shows the shape of a component, a class, a function or a pattern, for anyone who wants to review it. When it is off, the design holds none.
- The surface part, for each item, on the one surface its slice names: what the person or system that uses it sees and does there. For a command line, the command, what it prints and how a person answers; for a browser page or a mobile app, the screens, the flows through them and the states each screen can hold; for an endpoint, what it takes and what it gives back. Each screen is shown as the screen design setting says: as wireframes in Markdown files, or as a prototype built with the project's design system. An item with nothing on a surface, such as a chore inside the code, says so, with the reason.
- Each choice names its source and the other ways weighed, each with why it lost.
- A need the project's standards do not cover is named as a gap for the capability that owns it, with what the design chose meanwhile from the project's code and memory.
- A bug under the chosen item is named in the design, and its fix is left to Fix defects test first.
- An AI agent proposes the design, and the technical lead confirms or changes each choice. The design is written into short-term memory, with who confirmed it and when.
- The design, its sample code and its prototype hold no eval, test, success scenario, story expectation or failure condition, and name no evals folder, hidden file or ICE page. A check that the designer does not run reads them before they are handed on.
- How it meets the capability: this is the capability's design job. The whole tree under the chosen item gets one design, both parts, against the project's standards, so the developer builds everything under it to one design, and a reviewer reads it from its diagrams. In the product owner's words: "both technical design and surfaces are important", and "this design is input for writing code and building the application".

Status: not built. What exists covers only parts of it:

A check later fails a changed file the design did not name, unless the builder wrote why. It is live only in a full install, and it belongs to Fix defects test first.

Another drew the system's parts as a text diagram. No play calls either.

Phoenix memory holds learnings a surface design can read, such as the states every screen must handle and a small set of design tokens with a reused component set, and learnings on architecture and technology.

## Inputs / Outputs
- In: the builder's part of the gathered tree and each story's collected context, from short-term memory.
- In: the project's standards: its architecture with its technology, the declared surface the work is on with its properties, guidelines and design system, the approved deployment design with its services, container platform and cloud, and the environments.
- In: the project's sample code, design style and screen design settings.
- In: the project's code and its own memory, then Garura memory, then Phoenix memory, through the memory tool, and a memory update a person approved.
- Out: the design of the chosen work in short-term memory: for each story, chore and spike, its technical part with its diagrams and its surface part with the look of each screen, each choice with its source and the other ways weighed.
- Out: sample code for review, when the sample code setting is on.
- Out: wireframes in Markdown files, or a prototype built with the project's design system, as the screen design setting says.
- Out: each gap in the project's standards, with the capability that owns it and what the design chose meanwhile.
- Out: each work item that does not fit the design, and each bug named for Fix defects test first.
- Out: a memory update for each choice or style that no tier answered, waiting for a person, and the choice named as open with no default.
- Out: the technical lead's confirmation of the design, with when it was given.

## Rules & behavior
- It starts from the builder's part and the collected context, and never reads the test writer's part. The reason, in the product owner's words: "the code, when being written, should not get to see what tests there were", and the design reaches the builder.
- It never reads the evals folder, an eval, the hidden file or an ICE page. The hidden file holds each feature's failure conditions, beside the slice's eval. The reason: they hold what the eval judges the build by, and what the designer reads can pass into the design.
- The design, its sample code and its prototype hold no eval, test, success scenario, story expectation or failure condition, and a check the designer does not run reads them before they are handed on. The reason: a builder "cannot teach to a test it cannot see", and the doer does not check its own work.
- The whole tree, one design: every story, chore and spike under the chosen item, and nothing outside it. The reason, in the product owner's words: "I can choose to implement at the level of an epic, which means everything under it gets designed".
- Down to the components, the data and the interfaces: the components with their classes and functions, the data model, the interfaces and the libraries. The reason, in the product owner's words: "what classes, what functions, and any reusable patterns need to be created", and "data model, interfaces, librris and component level design yes".
- Libraries and data stay inside the architecture. A library is chosen within the technology the architecture names, and the data model lives in its data store; a new framework or data store is a gap for Design the technology and architecture. The reason: the low-level design that exists already holds this line, "do not invent new stack choices".
- The deployment design feeds the technical part. Each component is placed in a service the approved deployment design runs, on its container platform and its cloud, and nothing about how the project runs is designed here; a need it does not cover is a gap for Deployment design. The reason, in the product owner's words: "knowledge of deployment should also feed into technical design", and "Nothing about how the project runs is designed in a slice."
- The technical part is drawn as diagrams, with text beside them, for a reader who is not hands-on. The reason, in the product owner's words: "simple for a CTO level to understand, not all CTOs are very hands on".
- The style of the diagrams is the design style setting's. What each style draws, and how, comes from the project's memory first, then Garura memory, then Phoenix memory; when none holds it, it is researched and raised as a memory update, and used only after a person approves it. The reason, in the product owner's words: "the style of design can be configured", and a style in memory can be checked and read back.
- Sample code is written only when the sample code setting is on. It shows the shape of a component, a class, a function or a pattern, and is never a test. The reason, in the product owner's words: "add a config to see if this skill sould generate sample code for nayone who wants to review those".
- Each screen is shown one of two ways, as the screen design setting says: wireframes in Markdown files, or a prototype built with the project's design system, the one Manage surfaces names. The reason, in the product owner's words: "the ux design shoudl show wirerames in MD files as to how screens will look or build prototypes using the project's design system".
- What the project's code already has comes first: an existing component, class, function or pattern is reused or extended before a new one is named. The reason: the design agent that exists starts from "What already exists? What patterns are used?"
- The project's standards bind the design, and the design never changes them. A need they do not cover is a gap for the capability that owns it, not a stop: the design goes on from the project's code and memory and says what it chose. The reason: each piece of work "does not choose its own" architecture, and the Spec → Design business intent blocks no work.
- The surface part is made for the one surface the work's slice names, and keeps to that surface's properties and guidelines, such as working within the project's design system. It never designs for another kind of surface. The reason: "Re-deriving the surface downstream is the failure this rule exists to stop", and a design made for the wrong surface is drawn again.
- An item with no surface says so, with the reason, and never leaves the part empty. The reason: work with no surface is legitimate, "but must be declared" so it is never mistaken for a surface left out.
- Each choice names its source, a file of the project, a memory file or an approved memory update, and the other ways weighed, each with why it lost. The reason: "Every alternative must carry a concrete `rejection_reason`.", and a person can check each choice without a search.
- The project's memory first, then Garura memory, then Phoenix memory, then research through a memory update a person approves. A choice that nothing answers stays open, with no default, and the rest goes on. Nothing comes from what the AI agent knows by itself. The reason: research is new knowledge that nobody has checked yet, and the agent's own knowledge can be neither checked nor read back.
- The technical lead confirms or changes each choice, and the confirmation is recorded. Nothing waits for it. The reason, in the product owner's words: "designs are going to be done by, let's say, a technical lead or an architect, maybe a technical lead."
- It changes no work item, plan file, status, project standard or setting. What does not fit is named for the capability that owns it. The reason, in the product owner's words: "This intent's job is to execute on the plan".
- Not decided: one standard for a design, with its parts and where it is kept. A play recorded for later asks for one, and no memory tier holds it.
- Not decided: which design styles there are, and what each setting does when a project has not set it.
- Not decided: what the screen design does when the setting asks for a prototype and the project names no design system.
- Not decided: whether the design may read the tests the project already has around the code it changes.

## Acceptance criteria
- Given an epic with two stories and a chore under it, when its ID is named and the work is designed, then the design has a technical part with its diagrams and a surface part for each story and the chore, the chore's surface part says why it has none, and nothing is designed for an item outside the epic.
- Given a story that keeps new data, when it is designed, then its technical part names the components, their interfaces, the data model in the architecture's data store and each library with its version, and no framework or data store the architecture does not name.
- Given an approved deployment design that runs the project as two services, when a story is designed, then each of its components is placed in one of those two services, and nothing about how they run is designed.
- Given a design style set for the project, when the work is designed, then its technical part is drawn as diagrams in that style, and a reader who is not hands-on can name each component and what it does from the diagrams alone.
- Given the sample code setting on, when the work is designed, then the design holds sample code of the new components' shape and no test; given it off, then the design holds no sample code.
- Given the screen design setting set to wireframes, when a story on a browser page is designed, then each of its screens is shown as a wireframe in a Markdown file; given it set to a prototype, then each screen is shown in a prototype built with the design system the declared surface names.
- Given a story whose work needs a class the project already has, when it is designed, then the design reuses or extends that class, names its file, and names the other way weighed with why it lost.
- Given a project whose declared surface is a command line, when a story on it is designed, then its surface part names the command, what it prints and how a person answers, and designs no screen.
- Given a story that needs something the project's architecture does not cover, when it is designed, then the gap is named for Design the technology and architecture with what the design chose meanwhile, and the architecture is unchanged.
- Given a finished design, when it, its sample code and its prototype are searched for each story's expectations, an eval, a test, a success scenario and the names of the evals folder, the hidden file and the ICE pages, then nothing is found.
- Given a choice that no tier of memory answers, when the work is designed, then a memory update is raised, the choice is named as open with no default, and the rest of the design is written.
- Given a bug under the chosen story, when the work is designed, then the bug is named for Fix defects test first, and the design holds no fix for it.

## Out of scope
- Choosing the item, gathering the tree under it, splitting each story and collecting its context. Gather the work under a chosen plan item does them.
- Setting or changing the project's architecture, surfaces, design system, deployment design and environments. Design the technology and architecture, Manage surfaces, Deployment design and Environment setup do them.
- Keeping the three settings and changing their values. Settings, where everything that can be turned on or off lives, does it.
- Updating the design once it is written. Update the design as the work changes (fn-update-work-design) does it.
- Writing the tests and the code, and building the application, in the order the developer chooses. Build the work test first does them, with this design as their input.
- Writing the evals and the hidden file. Write the evals that check the work does them.
- The root cause and the fix of a bug. Fix defects test first does them.
- Putting what the design decides into the product model. Keep the spec matched to what's built does it.
