## Intent
- Goal: How the whole project runs is designed once, with its physical architecture, which services run, on what container platform and on which cloud, the path a change takes through the environments Environment setup declares, ending at pre-production, the pipeline for continuous integration and continuous delivery, the tests in each environment, how a release goes live and is rolled back, where secrets and settings are kept, and what it costs on each of AWS, GCP and Azure from each cloud's cartridge, each choice with its reason, its source and the person who confirmed it, and every change runs that way, while the design is updated as the project changes.
- Limit: Each choice is proposed from the project's own memory and code first, then from Garura memory, then from Phoenix memory; only when none of them answers is it researched, and the research is used only after a person approves it as a memory update. Nothing comes from what the AI agent knows by itself.
- Limit: The path runs through the environments Environment setup declares, each built and managed on its own from one reused design and only when a deployment to it is needed, and ends at pre-production. Nothing here ever touches production.
- Limit: Nothing waits for the design, and only a person confirms a choice, an update or the cloud; an update replaces what held before without editing it, and neither the design nor a cartridge ever holds the value of a secret.
- Fails if: A choice is made with no person's confirmation, or with nothing behind it but what the AI agent knows by itself.
- Fails if: Anything in the design, its pipeline or a deploy it plans touches production.
- Fails if: A change runs, is tested or is released in a way the design does not hold and no gap or update explains it, or work stops because a choice of the design is missing.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the project's code and its settings, such as its container files, its Kubernetes files, its pipeline files, its deploy scripts, its infrastructure files and its hosting settings; the project's approved architecture and its surfaces; the product profile with its quality levels and its compliance needs; each cloud's cartridge; Phoenix memory's architecture and technology learnings for running, testing and releasing a product, with the conditions each fits and when each is outgrown; and the deployment design as set so far, with the decisions behind it.
- Never read: the value of any secret, such as a password or a key.
- Persona: the devops engineer, who decides how the project runs, is tested and is released, and the product owner, who asked that the whole project run one way and that the cloud be chosen with its cost in view.
- Scope: In: proposing, setting and updating how the whole project runs: the physical architecture, the path through the environments Environment setup declares and the one design each is built from, the pipeline for continuous integration and continuous delivery, the tests in each environment, release and rollback, stored data, secrets and settings, the cost on each cloud, the cartridges and the rules every release keeps. Out: production, setting up each environment, the architecture and its technology, the surfaces, any design of how the project runs inside a slice, carrying out the pipeline, writing and running the tests, the files that carry out the design, the product profile, decision records, seeding memory, moving a memory update into Phoenix memory, and the lock.

## Expectation
- Scenario: The devops engineer of a new team tool, one deployable unit with a database, sees it mapped onto AWS, GCP and Azure from their cartridges, each with a managed service that runs containers and a managed database, and its cost on each for one team, a wider trial and the whole company. The engineer chooses a cloud. Each change is then built and tested by continuous integration and taken by continuous delivery through dev, testing and pre-production, passing the tests named for each, and no step reaches production. When a cloud's prices change, its cartridge and the costs drawn from it are updated, and what held before stays readable with why it changed.
- Done means: Someone other than the one who set the design checks each choice and finds behind it a source in the project, in a cartridge or in memory, its reasons and the person who confirmed it, and for each update, what held before and why it changed.
- Done means: Someone other than the one who released compares two releases with the design, finds no difference that the design or a recorded update does not explain, and finds no step of either that touched production.
