# Capability: Deployment design

## Directional intent
How the product gets deployed is designed.
This is how the whole project is run. It is not one play, and it is never designed one slice at a time. The design is written down with the reason for each choice, and it holds:
- the physical architecture: the approved architecture of the project turned into what actually runs. That means which services run, what each part of the architecture runs as, the container platform the services run on, and the cloud the project runs on, with what each offers and how it behaves. A container is a packed copy of a service with everything it needs to run. A container platform runs containers, for example Docker on a server, Kubernetes, or a cloud's own service that runs containers;
- the path a change takes: through the environments Environment setup declares, at least dev, testing and pre-production, in that order, with what each is for, the checks a change must pass before each step, and who says yes. An environment is one place where a copy of the project runs. Each environment is built and managed on its own, from one design of its underlying technology that is reused for every environment, and it is built only when a deployment to it is needed. The path ends at pre-production. Nothing here ever touches production, the live product that people use;
- the pipeline for continuous integration and continuous delivery. Continuous integration builds and tests each change together with the rest. Continuous delivery takes each accepted change along the path automatically;
- how the project is tested in each environment: which tests run in dev, in testing and in pre-production, what a change must pass to move on, and how the team knows a release came up healthy;
- how a release goes live in each environment, how it is rolled back, which means taken back to the version before, and how stored data survives it;
- where secrets, such as passwords and keys, are kept, and where the settings that differ between environments are kept;
- what running the environments in the path costs on each of three clouds, AWS, GCP and Azure, worked out the same way for each, so a person can choose the cloud. Production is never touched, so its cost is not estimated;
- a dedicated cartridge for each of those clouds. A cartridge, in the product owner's word, is one ready pack for one cloud that the design reads: that cloud's services a physical architecture maps onto, its container platforms, and how to work out what running on it costs. Where a cartridge lives, and what more it holds, is not decided;
- the rules every release must keep, each following from what the cloud and the platform offer or from what the product profile commits to;
- for each part, its reason, its source and the person who confirmed it.

The design is set once for the project, before the slices are designed, and it is updated as the project changes. A slice is an ordered group of features that one person can test end to end on one surface. Each slice is then built, tested and released the way the design says, and does not choose its own way. A slice that needs something the design does not cover names it as a gap, and the design is updated. A product that keeps nothing running, such as a command a person installs, still has a deployment design: it says how the product reaches the people who use it, or that there is nothing to deploy, with the reason.
An agent proposes each choice, and a person confirms it. The agent looks first at what the project already holds, its code, its settings and its own records, then at Garura memory, then at Phoenix memory. Garura memory is the memory Garura keeps for the project, and it holds the product model, the shared map of the product that people and agents read. Phoenix memory is the shared memory on the machine that every project draws from; its architecture and technology learnings say which platform and which way of releasing fit a product in given conditions, and when each is outgrown. Only when none of them has an answer does the agent research it. It then raises what it found as a memory update, a proposed addition to memory, and a person approves it before it is used. Nothing comes from what the AI agent knows by itself.
It matters to software delivery planning because that domain prepares the work before agents build it. Without one design for how the project runs, each builder invents where its part runs and how it is tested and shipped, and the cloud is chosen without anyone seeing what it costs.

Features:
- Design how the project runs (fn-design-how-project-runs): turns the approved architecture into a physical architecture, which services run, on what container platform and on which cloud, and designs the path through the environments Environment setup declares, with the one design each environment is built from, the pipeline for continuous integration and continuous delivery, the tests in each environment, release and rollback, where secrets and settings are kept, and the cost on each cloud, each with its reason, so every change runs the same way.
- Prepare a dedicated cartridge for each cloud: AWS, GCP and Azure (fn-cloud-cartridges): prepares one ready cartridge for each of the three clouds, with its services, its container platforms and how to work out what running on it costs, so the design can map the project onto any of them and set the three costs side by side.
- Update the deployment design as the project changes (fn-update-deployment): when the project outgrows how it runs, or a part of the design or a cloud's cartridge must change, a person confirms an update, and what held before stays readable with why it changed.

What is not built yet:
- None of the three features is built. Nothing designs how the whole project runs.
- As built, each slice's own run design decides it alone. The design play for a slice's run is stale and waits for a rebuild. For its own slice, it records how a release goes live and is rolled back, how stored data changes, how the slice is built, tested and shipped, what running it costs on the chosen cloud with the alternatives weighed, and its environments, one at a time. Its list of environments ends with production. It reuses a choice an earlier slice recorded as a decision, so the first slice would set the cloud for the whole product.
- The plays that bring a slice up for a person to accept, and that deploy it to a cloud environment, are stale. They refuse to deploy to production, but they leave production to continuous delivery from the main line of the code. Continuous delivery is not built, and under this capability its path ends at pre-production.
- An older chain of skills drew a physical architecture for the whole project. It was deleted with the retired planning chain. An older skill wrote a hosting platform for each part inside a whole-project architecture; no play calls it.
- Reading memory first exists only in parts. Phoenix memory has learnings for running and releasing in some conditions, most of them on one cloud, GCP. It has a little for AWS, about agents, and nothing for Azure beyond its name in a list. It has nothing for a product that is installed rather than kept running. Its learnings also put production at the end of their paths, so a proposal drawn from them leaves that step out.
- No cartridge exists. Nothing in Garura or in memory uses the word; it is the product owner's new idea.
- The product model has no kind for the deployment design. An older decision left the place of project-wide design to the model's ontology, the agreed list of the kinds of things a product is made of, and the ontology has not answered it.
- No work for this capability is planned in the tracker.

### Benefit hypothesis
- Who it serves: the devops engineer, who decides how the project runs, is tested and is released; the product owner, who asked that the whole project run one way and that the cloud be chosen with its cost in view; and the agents that build, test, release and deliver each slice.
- What we believe: every change of the project runs, is tested and is released the same way, never reaches production, and runs on a cloud chosen with its cost known, if the work stands on these rules:
  - How the project runs is decided once for the whole project, never in a slice.
  - The path runs through the environments Environment setup declares, and ends at pre-production.
  - Each choice comes from the project's code or memory, or from research a person approved into memory, and a person confirms it.
  - The physical architecture gives every part of the approved architecture a place to run, and the design says how every release is rolled back without losing stored data.
  - The cost of running the environments in the path is shown on each of the three clouds, worked out the same way from each cloud's cartridge, before the cloud is chosen.
  - The design is updated as the project changes, and what held before stays readable with why it changed.
  - Nothing waits for the design.
- How we will know: two slices released at different times run on the same physical architecture and go through the same path and the same tests, each difference between them traces to the design or to a recorded update of it, nothing the project releases reaches production, and the record of the chosen cloud shows the cost on all three.
  - This is not tested today, because nothing designs how the whole project runs.

### Boundary (In / Out / Never)
- In: turning the approved architecture into the physical architecture: which services run, what each part runs as, the container platform and the cloud, with what each offers and how it behaves.
- In: designing the path through the environments Environment setup declares, with what each environment is for, and the one design of the underlying technology that every environment is built from; the pipeline for continuous integration and continuous delivery; the tests in each environment and what a change must pass to move on; how a release goes live and is rolled back, and how stored data survives it; where secrets and settings are kept; the cost on each cloud; and the rules every release must keep.
- In: preparing a dedicated cartridge for each of AWS, GCP and Azure.
- In: updating the deployment design and the cartridges as the project changes, keeping what held before and why it changed.
- Out: which environments exist, how many, and how each is set up: at least dev, testing and pre-production, each built and managed on its own when a deployment to it is needed, with its data, its size, its network and who can reach it. Environment setup owns it, with the minimum of three and their names. This capability holds the path a change takes through them, what each is for, and the one design each is built from.
- Out: the parts of the system and what each is built with, such as its language, its framework, its data store and their versions. Design the technology and architecture owns it. This capability turns that architecture into the physical one. A change here can call for an update of the architecture, and the other way round.
- Out: the project's surfaces, the places where people or other systems use the product. Manage surfaces owns them. This capability makes each declared surface reachable the way its kind needs, such as an address for a browser page or an install for a command line.
- Out: any design of how the project runs inside one slice. Nothing about how the project runs is designed in a slice. Use the lenses on each slice (Design → Code) designs the rest of each slice, and a slice that needs something this design does not cover names it as a gap, which an update here closes. A lens is one view of a slice's design, such as its screens or its architecture.
- Out: carrying out the pipeline. Continuous integration and Continuous delivery (Validation → Run) carry out what is designed here, along the path designed here and no further.
- Out: writing and running the tests. The testing capabilities of Validation → Run (security, automated functional, performance, other testing and user acceptance testing) and Test with evals the builder never sees (Code → Validation) own the tests, and Design for evaluation and testing designs each slice's eval. This capability says which tests run in which environment and what a change must pass to move on.
- Out: bringing one slice up for a person to accept, and deploying a slice to an environment. The plays that do it read the design and never change it.
- Out: making the files that carry out the design, such as container files, pipeline files and infrastructure files. Build the work makes them, from work items.
- Out: the product profile, the record of the product's shape and the quality levels it commits to, such as how reliable it must be. Specify the product sets it. This capability reads its quality levels and its compliance needs to size each choice, and never writes them.
- Out: writing the decision record behind each choice, accepting it and keeping its history. A decision record says what was decided, why, and what else was weighed. Manage ADRs (Orchestration) owns the records; this capability decides what each choice says and hands it over.
- Out: putting the memory that fits the deployment design into the project. Seed the memory for the lenses, a part of the project set-up step (initialize), owns it.
- Out: moving an approved memory update into Phoenix memory. A memory update goes to the project's short-term memory, and moving it up is a promotion a person makes on purpose, outside this work.
- Out: locking the design before agents take over. Lock the design owns the lock, the only gate.
- Never: touch production. No design, pipeline or deploy here ever touches production; the path ends at pre-production. The reason, in the product owner's words: "We are never touching production."
- Never: block work on a missing choice. The work goes on from the project's code and memory, and the open choice is named. The reason: the Spec → Design business intent must not block on anything except the lock.
- Never: make a choice from what the AI agent knows by itself, or write a choice that no person confirmed. The reason: a release made on an agent's guess is found wrong only when it fails, and a cloud chosen on a guess is paid for every month.
- Never: write the value of a secret into the design or a cartridge. The design names only where each secret is kept. The reason: every agent reads the design and it is kept with the project's files, so a secret written there is no longer secret.
- Never: change the design's words in place. An update replaces what held before and keeps it. The reason: releases already made on the old design must still be explainable.

### Guiding rules
- Once for the whole project, never in a slice. The reason: how a project runs is the same for every slice, and slices that decide alone end up run, tested and shipped in different ways, with the first slice deciding for every later one.
- The path runs through the environments Environment setup declares, in order, and ends at pre-production. The reason: the product owner set the end of the path, so every change is tested in environments of its own, and production stays out of the project's reach.
- Each environment is built and managed on its own, from one design of the underlying technology that is reused for every environment, and only when a deployment to it is needed. Building one more environment repeats the design and never invents it again. The reason, in the product owner's words: "each env can be built separately and managed separately, the underlying tech and reusability is important but we needed these to be done only [when] a deployment is needed".
- The approved architecture comes first. Every part of it runs as a named service, on a named container platform, on the chosen cloud, or is named as a gap; and every declared surface can be reached the way its kind needs. The reason: a part with no place to run is found only when it fails to start, and a surface nobody can reach cannot be tested or used.
- The project's memory first, then Garura memory, then Phoenix memory, then research. Each choice is proposed first from what the project holds: its container files, its Kubernetes files, its pipeline files, its deploy scripts and infrastructure files, its hosting settings, and the architecture and surfaces set so far. Then from each cloud's cartridge, from Garura memory, and from Phoenix memory's architecture and technology learnings, matched to the project's conditions: its architecture, its stage, its users, how often it releases, and the quality levels in the product profile. Only when no memory has an answer does the agent research it, and it raises what it found as a memory update for a person to approve. A choice is never made from what the AI agent knows by itself. The reason: a source in the project or in memory can be checked and read back, while the agent's own knowledge cannot.
- Research is used only after a person approves it. Until then the choice stays open, with no default, and the work goes on. The reason: research is new knowledge that nobody has checked yet, and the person's approval is the check.
- What the project already does is described as it is. When the project already runs somewhere, its services, its platform, its cloud, its pipeline and its tests are read from its files and proposed as they are. The reason: a design that contradicts how the project already runs sends every builder after a setup that nobody uses.
- Each proposal names its source: a file of the project, a cartridge entry, a memory file or an approved memory update. The reason: a person can check each choice without a search, and when a source changes, the choices built on it can be found.
- Each environment names the tests that run there, and a change moves to the next one only when they pass. The reason: a path with no checks between its steps carries a broken change as fast as a good one.
- The cost is shown on all three clouds, worked out from each cloud's cartridge, the same way and for the same sizes of use, each naming what it leaves out. The reason: the product owner asked to know the cost on each cloud, and costs worked out in different ways cannot be set side by side.
- The design says how every release is rolled back, and how stored data survives it. The reason: a release with no way back turns one bad change into an outage, and the review already treats a change to stored data with no tested way back as its most serious finding.
- The product profile sizes each choice. The design meets the quality levels and the compliance needs the profile commits to, without going far beyond them. The reason: a design below the profile breaks what the product commits to, and one far above it costs every release time and money.
- A person confirms each choice and each update, and a person chooses the cloud. The reason: the design decides how every change is run and released, and what the project pays to run, so it is never an agent's decision alone.
- A missing choice is a gap, not a stop. The builder goes by the project's code and memory and names what it chose, and the gap stays on record so a later step knows it was skipped, not forgotten. The reason: the business intent's only gate is the lock.
- The design is kept where every agent looks first. Agents gather context from the project's code and the project's own memory, Garura memory, before Phoenix memory, and the product model is part of Garura memory. The reason: a design that builders do not find is no design. Not decided: the place in the model, because the model has no kind for the deployment design, and where the cartridges live.
