## Intent
- Goal: Every change, whoever starts it, goes from opening to merge through the same steps: it is opened on a branch cut from where it will land, committed by concern with its issue named and nothing sensitive, raised as one pull request against where it lands after the machine checks, reviewed from outside, and merged there on the review's approval and a person's typed yes; every push is scanned first, the docs and command pages move with the change, and a plan's branch lands on main whenever the plan pauses and its review approves it.
- Limit: Nothing is merged without the review's approval and a person's typed yes, and no setting turns the yes off.
- Limit: The path never judges a change; the review, its verdict and who decides it belong to Check the code against its standards.
- Limit: Where a change lands is read from its branch and the plan files, never guessed; an issue in a plan never lands on main, and open work never holds a plan's branch off main.
- Limit: Nothing is committed on main, and no secret and no client, company or personal reference is committed or pushed.
- Fails if: A change lands without its issue named in its commits and its pull request, without an approval verdict, or without a person's yes.
- Fails if: An issue in a plan merges straight into main, or a plan's branch is held off main for its open issues or for a plan it needs.
- Fails if: A secret, or a client, company or personal reference, reaches the code host.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: what the person typed and the issue it names, the plan files on main and on the plan's branch, the branch names, the changed files and which of them are sensitive, the review's verdict and who decided it, whether the change can be merged and its required checks, the setting of each checkpoint, and the docs and command pages a change touches.
- Never read: any memory file by its path, and any ICE page.
- Persona: the developer, a person or an AI agent who builds the code, who opens, commits and raises each change; and the product owner, who starts a plan's work and gives each merge their yes.
- Scope: In: opening, committing, raising, running the outside review as one step, merging, landing a plan's branch on main, landing several ready issues in one change, scanning every push, and keeping the docs and command pages in step. Out: the review and its verdict, reviewing what agents made in the review tool, making and changing plans and their items, laying the plays into a project, the plays' names and settings, and production.

## Expectation
- Scenario: Two changes go through the path in one week. In a bank's payments service, a developer fixes a one-off bug: the change is opened from main, committed in two commits that name the issue, raised as one pull request to main, approved by the review, and merged after the product owner's yes; the bug's issue closes and its branch is gone. In a clinic's booking app with a plan for online check-in, a story's change is opened from the plan's branch, raised against it, approved, and merged there after the yes; its issue closes and its item reads Done, while the epic above it stays open. When the plan pauses, its branch is raised to main and lands after its review and the yes, with the plan's other story still open.
- Done means: Someone other than the one who made the changes reads the code host, the plan file and the run records, and finds for each change its issue named in every commit and in its pull request, the pull request's target where its branch lands, an approval verdict and a recorded yes before the merge, and no change branch left; and finds the issue in the plan closed on the plan's branch, not on main, with only its own item set Done.
