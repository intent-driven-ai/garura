## Intent
- Goal: A person gives a loop one goal and what it starts from, and the loop runs its plays in rounds on one issue and one branch, asking first only what it needs to start, until its done check holds and a checker that did not run it passes the result, or until it briefs the person on what no play, memory or approved research could close; every loop follows the same run, keeps its status in one file, ends through the change plays with the person's typed yes on the merge, and each transition between phases has its own loop.
- Limit: The loop does no play's work and answers nothing from the model alone; every product rule stays in its plays.
- Limit: No play takes another play's output as its input, and no play inside a loop opens an issue, a branch or a pull request of its own.
- Limit: The loop never ends done without the checker's pass, and a missing or malformed verdict is never a pass.
- Limit: The loop asks the person only after a round that closed nothing new or at its round limit, and only with a brief, never a bare question.
- Fails if: A loop writes outside its issue, opens a second issue or branch, or lets a play inside it open one.
- Fails if: A loop ends done with a play's done check unmet, without a checker's pass, or with a checker on the session's own model.
- Fails if: A person is asked a question that a play, memory or approved research could answer, or is asked before the round's knowledge step ran.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the loop's own values (its plays, questions, documents, source, settings keys and end), the Shared Loop Run, the loop contract rule, the loop's settings (runner, checker, round limit and evidence), each play's done check and review record, the round records, the open questions and the memory updates still waiting, the checker's bundle and verdict, and the run's status file.
- Never read: any memory file by its path, and any ICE page; and, for the checker, anything outside its bundle or the loop's reasoning.
- Persona: the product owner, who gives the loop its goal and what it starts from, is briefed on what no play could close, and gives the merge their yes; and the developer, a person or an AI agent who builds the code, who starts a loop and follows its status.
- Scope: In: the run every loop follows, its runner and checker, the questions first, the knowledge step and the brief, the status file and its display, and one loop for each transition. Out: building and changing loops, the loop settings, each loop's plays, the review a loop ends in and the merge, the link rules of the step after each round, approving memory updates, choosing what runs next, the tracker, ADRs, and the way past a gate.

## Expectation
- Scenario: The product owner of a clinic's booking app gives the Discovery loop a working prototype and its write-up. The loop opens one issue and one branch, asks only where the prototype is and how it starts, reads it once, and runs its three plays in rounds; after round one the step after the round gives two capabilities with no features to the play that writes them, and round two runs only that play. At the round limit one question is still open; the knowledge step drafts our proposed answer, and the product owner reads the brief and types yes. A checker on a model that is not the session's passes the result, and the change lands after the product owner's yes on the merge. In a shop's checkout project the same loop's checker finds a capability no domain holds, rejects the result, and the loop halts with no pull request.
- Done means: Someone other than the one who ran the loop reads the run's records, the status file and the code host, and finds for the clinic one issue and one branch with every run file under that issue, each play's done check reading done, the brief shown only after a round that read ask, a pass from a checker whose model is not the session's, the status file reading done, and one pull request merged after a recorded yes; and for the shop a reject with its reason, the status file reading halted, and no pull request.
