## Intent
- Goal: A change to Garura that changes a memory page in its source also changes Phoenix memory, through the change plays, in the same release; a check names every page where the two differ, with its written direction; no release goes out with a gap nobody decided on; and each release of Phoenix memory has a version that matches Garura's release and its own notes, so every project's agents decide from the rules Garura now follows.
- Limit: A page on one side only is not deleted or overwritten before its direction and reason are known.
- Limit: Phoenix memory holds no names of a client, an organisation or a person.
- Limit: Garura's own release, bringing a version to a machine and what each rule says stay with their owners.
- Fails if: A change to a memory page in Garura's source lands while Phoenix memory does not have it in the same release.
- Fails if: A release goes out while a page differs between the two and no person decided on it.
- Fails if: A release of Phoenix memory has no version, or no notes naming each page added, changed or removed.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the memory folder of Garura's source, Phoenix memory at its approved version, the pages that differ and the direction of each, the change plays, Garura's release and its notes, and the open issues on Phoenix memory in step and versioned.
- Never read: any memory file by its path, and any ICE page.
- Persona: the developer, a person or an AI agent who builds the code: the one who changes Garura's rules and lands its release, and the one in any project who decides from Phoenix memory.
- Scope: In: the same change in Phoenix memory in the same release, the check of the differences with each page's direction, and Phoenix memory's version and notes per release. Out: Garura's own release, bringing a version to a machine, promoting a project's answer, what each rule says, and opening and landing the change.

## Expectation
- Scenario: In a harness team's own repository, a change renames a loop in the naming rule; the change lands only once Phoenix memory has the same rule, and the release notes name the page and why. In a bank's payments service on another machine, after the new release reaches it, the agents check names against the same rule.
- Done means: Someone other than the one who built it compares Phoenix memory at the release's version with Garura's source at that release, and finds no page that differs without a person's decision and a written direction, and the release notes naming the renamed rule with its reason.
