# Capability: Test the user experience on each surface

## Directional intent
Test the user experience on each surface, against the surface's properties and guidelines (for a browser page, how it lays out across screen sizes) and the screen design from Design the work: the running build is tested in the testing environment, by tools and by a person who walks it on each declared surface, against what Manage surfaces declares that surface offers and what every design on it must handle, and against the screen design the work was built to, and each finding goes back to the developer or to a person.
A surface is a place where a person, or another system, opens the product to use it, such as a browser page, a mobile app, a command line, a coding agent that a person runs in a terminal, or an endpoint another system calls. Manage surfaces declares each surface with its properties, what the surface offers and how it behaves, such as whether one layout reflows across screen sizes or each device gets a layout of its own and which screen sizes it serves, and with its guidelines, what every design on it must handle, such as working within the project's design system, the shared colours, type and components that every screen is built from. Design the work writes the screen design: what a person sees and does on the work's surface, with each screen shown as wireframes, simple drawings of each screen in Markdown files, or as a prototype built with the project's design system, as the project's screen design setting says. In the product owner's words, Code → Validation "also needs to handle other forms of testing i.e. security and performance and accessibility, ux (responsive)", and the list he approved adds this capability as new. It runs those tests once the work is built and runs in the testing environment:
- With tools. On each declared surface, a part that is not the builder opens each screen the screen design shows, at each screen size the surface names, keeps a picture of it with the text and the controls it shows, and checks what a tool can: that each screen opens and shows at each size, and what a guideline says a tool checks. For a command line or a coding agent, the tool runs the command or the play in a test project with set answers and keeps what it printed and asked.
- By a person. What only a person can judge, whether each screen lays out at each size as the surface's properties say, keeps to its guidelines such as the design system, and matches the screen design, a person who is not the builder, named by the product owner, judges by walking the slice end to end on its surface, with the screen design and the tools' pictures beside them. A slice is an ordered group of features that one person can test end to end on one surface.
- The verdict. Each property and guideline of the surface and each screen of the screen design gets a pass or a fail, each part not tested or not walked is named with its reason, and the verdict is a pass only when every part passes.
- The way back. Each finding goes back as a handoff plan: what a person meets on which screen and at which size, and the way back, never the test itself. It goes to the developer when the builder can fix it alone, and to a person when a person must decide.
- Again as the product changes. The tests run again after a fix, when more work is built, when a surface's properties or guidelines are updated, and when the screen design is updated, so that a pass stays true.

Where the user experience ends and the other tests begin is drawn by the yardstick. What a surface's accessibility guideline, the accessibility level, its pass bar or a capability's accessibility need names is tested by Test accessibility, even when it is about layout, such as text that must still read when a person makes it larger. What the product does, against each story's goals and expectations, is tested by the slice's eval, in Test what the product does, with evals the builder never sees. What the surface's other properties and guidelines name, and what the screen design shows, is tested here. One run of a tool, or one walk by a person, may serve more than one of them; each capability reads only what its own yardstick names.
The review of each change is not repeated here. Check the code against its standards matches the review's rules against the lines each change adds, such as a colour, a padding or a margin written as a fixed value, and Build the work test first runs the tests inside the code by a separate check. This capability takes both records as evidence. The builder's own word is not evidence: "A builder believes its own work, so its opinion isn't evidence."
What the tests cover comes from memory first: the project's own code and memory, then Garura memory, the memory Garura keeps for the project, then Phoenix memory, the shared memory on the machine that every project draws from. Only when none of them has an answer is it researched, and what research finds is raised as a memory update, a proposed addition to memory, and used only after a person approves it. Nothing comes from what the AI agent knows by itself.
It matters to software delivery planning because that domain turns a business intent into working code that a check from the outside can prove. This capability is that check for what each surface promises and what the screen design shows.

Features:
- Test the running build's user experience with tools, in the testing environment (fn-test-user-experience-with-tools): once the built work runs in the testing environment, opens on each declared surface, by a part that is not the builder, each screen the screen design shows at each screen size the surface names, keeps a picture of it with the text and the controls it shows, checks what a tool can check, and records each result with what was checked and where.
- Walk the running build against its surface and its screen design, in the testing environment (fn-walk-against-screen-design): once the built work runs in the testing environment, a person who is not the builder, named by the product owner, uses the slice end to end on its surface at each screen size the surface names, and judges each screen against the surface's properties, its guidelines and the screen design, recording what they found, where, and how they walked.
- Give the user experience verdict, and send each finding to the developer or to a person (fn-send-user-experience-findings): gives one verdict for the built work against each surface's properties and guidelines and the screen design, with a pass or a fail for every part, and sends each finding back as a handoff plan to the developer when the builder can fix it alone, or to the product owner when a person must decide.
- Test the user experience again as the product changes (fn-retest-user-experience): runs the tools and the walk again after a fix, when more work is built, when a surface's properties or guidelines are updated and when the screen design is updated, keeps each verdict, names what passed before and fails now, and sends a finding that keeps coming back to a person once the rounds the project allows are used up.

What is not built yet:
- Nothing tests the user experience of a built product on its surface. Garura's own model declares no surface, no work has a screen design, and its one slice is on the Claude Code command line.
- No surface is declared, so no surface has properties or guidelines yet, because Manage surfaces is not built.
- No screen design is written, because Design the work is not built, and its screen design setting does not exist. The stale design play for a slice's screens drew wireframes from a record of each screen, so a product owner could look at the design; the retired design pipeline's rules for one Markdown file for each screen, with its wireframe, are still in Phoenix memory. Nothing builds a prototype with a project's design system.
- The prototype capture and the prototype walk, built for Specify the product, open a page in a browser and keep a full-page picture of it with its text, and the walk keeps the controls and fields on screen after each step. Both open the page at one screen size fixed in their code, and neither opens a built product. Nothing opens a page at several screen sizes.
- The rebuild eval, a tool that rebuilds a product from the model and tries what its prototype does on the rebuild, leaves layout out on purpose: "Words, layout and design may differ". Nothing compares a built screen with a wireframe or a prototype.
- The old slice check, /validate-epic, is stale and waits for a rebuild. For a browser surface it planned "a browser open of each `must_open`", to see each page show; it named no screen size and compared nothing with a design.
- The quality-check runner, a skill that runs each quality check written down for a slice, is built, and no live play runs it. A check a person owns is skipped in view, never judged by it: "Human-owned cards are visibly skipped, never judged.", and its test example of such a check is "Layout matches the approved UX direction". Nothing does the person's part or records what the person found.
- The review of each change has a row that matches a colour, a padding or a margin written as a fixed value in the lines a change adds. It belongs to Check the code against its standards.
- For a command line, and for a coding agent's play, the only steps written down are the eval's: a runner "starts the play as a command in the test project and gives it the scripted answers". The runner is not built.
- No testing environment is declared or built, and nothing says which tests run in which environment, because Environment setup and Deployment design are not built.
- Memory holds learnings for a browser surface on layout across screen sizes, on the design system and its shared components, on navigation and on the states each screen must handle. No tier says how to test a built screen against them, how to compare it with a wireframe or a prototype, or how to test a mobile app, a command line or a coding agent's surface for its user experience.
- No play name is agreed for this work: the agreed names hold /validate-perf and /validate-security, and none for the user experience.

### Benefit hypothesis
- Who it serves: the product owner, who reads the verdict, names who walks the build, and decides each finding that a person must decide; and the developer, who builds the code and gets back, as a handoff plan, each finding the builder can fix alone.
- What we believe: when the running build is tested in the testing environment, by tools and by a person, neither of them its builder, against each surface's declared properties and guidelines and the screen design in force, a pass shows that a person meets on each surface what its declaration promises and what its screen design shows, if the work stands on these rules:
  - The yardstick is each declared surface's properties and guidelines and the screen design in force, read and never set.
  - A part that no tool checked and no person walked never counts as a pass, and a tool's clean run never passes a part that a person must judge.
  - The builder knows the surface and the screen design it must meet, but never gets the tests, their results or the verdict.
  - A handoff plan names what a person meets, where and the way back, never the test, its rule, its id or its tool.
  - No test touches anything outside the testing environment.
- How we will know: two runs of the tools on the same built work open the same screens at the same sizes with the same results; a second person who walks the same steps at the same sizes finds the same parts met and not met; every property, guideline and screen has a pass, a fail or a reason it was not tested; each walk names who walked, on which surface and at which sizes; no test touched production; and no person finds, after a pass, a screen that lays out, looks or reads other than its surface and its screen design say.
  - This is not tested today, because nothing tests the user experience.

### Boundary (In / Out / Never)
- In: testing the running build in the testing environment with tools, on each declared surface, at each screen size the surface names, for what a tool can check, with a picture kept of each screen at each size.
- In: a person who is not the builder walking the slice end to end on its surface, at each screen size the surface names, and judging each screen against the surface's properties and guidelines and the screen design.
- In: giving the verdict against each surface's properties and guidelines and the screen design, after taking the records of the review of each change and of the build's separate test run as evidence.
- In: sending each finding back as a handoff plan, to the developer or to a person.
- In: testing the user experience again as the product changes, when a surface's properties or guidelines are updated, and when the screen design is updated.
- Out: what the product does, against each story's goals and expectations. The slice's eval tests it, in Test what the product does, with evals the builder never sees.
- Out: what a surface's accessibility guideline, the accessibility level, its pass bar or a capability's accessibility need names, even when it is about layout. Test accessibility owns it.
- Out: testing security and performance. The other capabilities of Code → Validation own them; a figure a tool gives for them while it opens a screen is theirs.
- Out: the review of each change against its standards, with the review's rules on the lines a change adds, such as a colour written as a fixed value. Check the code against its standards owns it; this capability reads its record and never runs the same rules again.
- Out: the tests inside the code. Build the work test first runs them by a separate check, and this capability takes that check's record as evidence.
- Out: declaring each surface with its properties and guidelines, and updating them. Manage surfaces owns it, and this capability reads it.
- Out: writing and updating the screen design, and the screen design setting. Design the work owns the design and Settings owns the setting; this capability reads both.
- Out: which tests run in which environment. Deployment design owns it, and this capability reads it.
- Out: declaring and building the testing environment, with its data and its test accounts. Environment setup owns it.
- Out: fixing what fails. Build the work test first fixes a finding before the work is accepted, and Fix defects test first fixes one after.
- Out: recording a defect in the tracker, and making and running the plan, with the loops that run building and validation in rounds. Orchestration owns them.
- Out: users testing the product and accepting it. User acceptance testing, in Validation → Run, owns it.
- Never: test anything outside the testing environment: not production, not a builder's own machine, and no system the testing environment does not hold. The reason, in the product owner's words: "We are never touching production."; and a builder's machine "is not where the path's tests are counted".
- Never: give the user experience tests, their results, the pictures they kept or the verdict to the builder or to any part that builds the work, or let the builder walk its own work. Only the handoff plan reaches the builder. The reason: "A builder believes its own work, so its opinion isn't evidence.", and a result checked after the work exists is a failure condition: "giving it to the builder only invites teaching-to-the-test."
- Never: skip, switch off or let through a finding, or loosen a test, to reach a pass. The reason: Code → Validation must not "weaken a check to pass", and a surface or a screen design changes only by an update a person confirms.
- Never: count a part that no tool checked and no person walked as a pass, or count a tool's clean run as a pass for a part a person must judge. The reason: "An unmeasured bar is not a passed bar.", and the quality-check runner already holds that a check a person owns is never judged by a tool.
- Never: make a choice, such as what to check, at which sizes, with which tool or in which way, from what the AI agent knows by itself. The reason: a source in the project or in memory can be checked and read back, while the agent's own knowledge cannot.

### Guiding rules
- Against the surface and the screen design, per product. What is tested comes from each declared surface's properties and guidelines and from the screen design in force, never from this capability and never straight from a learning in memory. The reason: the approved list tests the user experience "against the surface's properties and guidelines (for a browser page, how it lays out across screen sizes) and the screen design from Design the work", and what memory says fits a kind of surface reaches a surface only through Manage surfaces, where "A person confirms each surface, property and guideline".
- The screen design in force. When the design was updated, also when the build departed from it and the technical lead confirmed the new version, the updated design is the yardstick; a built screen that departs from the design in force with no confirmed update is a finding for the product owner. The reason: "From its confirmation, the updated design is the one in force.", and a departure "goes back to the technical lead as a design update".
- Every screen size the surface names. A browser page is opened and walked at each screen size its surface names, and a surface that gives each device a layout of its own is tested on each device's sizes against that device's design. A surface that names no screen size is named as not tested for its layout and goes to the product owner. The reason: a browser surface's properties include "which screen sizes (viewports) it serves", in the product owner's words "web would be responsive, adaptive, view ports etc."
- Each kind of surface by what it offers. A browser page and a mobile app are tested screen by screen at each size; a command line and a coding agent's surface by running the command or the play in a test project with set answers, and reading what it prints and how it asks against its declared characteristics, its guidelines and the surface part of the design; an endpoint another system calls only for what its own properties and guidelines name, while what it gives back for a story is the eval's. A kind of surface that nothing says how to test is named as not tested and goes to the product owner. The reason, in the product owner's words: "same for agentic like claude-code we need to use the characteristics.", and the design's surface part is, "For a command line, the command, what it prints and how a person answers".
- A tool gathers, a person judges. A tool opens each screen at each size, keeps its picture, its text and its controls, and checks only what needs no judgment, such as that each screen opens and shows, and what a guideline says a tool checks. Whether a screen lays out as its surface says, keeps to the design system and matches its screen design is the judgment of the person who walks. The reason: as built, the quality-check runner never judges a check a person owns, and its own example of one is "Layout matches the approved UX direction".
- Beside the wireframe or the prototype. A wireframe in a Markdown file is read beside the picture of the built screen at each size; a prototype is walked with the same steps as the build and pictured at the same sizes, and the two are judged side by side. The reason: the screen design is one of two ways, in the product owner's words "wireframes in MD files as to how screens will look or build prototypes using the project's design system", and the prototype walk already walks a prototype step by step, "click, type, press a key, go back".
- A tool's own score is not the verdict. Each result is compared with its part of the yardstick. The reason: the old slice check held that "Green is the entry condition, never the verdict".
- Not tested is never passed. A screen no tool opened, a size no tool reached, a part no person walked, and a tool that could not run are fails, each named with its reason. The reason: "An unmeasured bar is not a passed bar."
- Not the builder. A part that is not the builder runs the tools, and a person who is not the builder walks the build, on a copy of the built work. The reason: "A builder believes its own work, so its opinion isn't evidence."
- The product owner names who walks. The person who walks is named for the project or for the run, and each walk records who walked, on which surface, at which sizes and which steps, so a second person can walk the same steps. The reason: the product owner decides each finding a person must decide, and a walk no one else can repeat proves nothing.
- The builder knows the surface and the screen design, never the tests. The surface's properties and guidelines and the screen design shape how the builder writes code, so it has them; the screen design is, in the product owner's words, "input for writing code and building the application". The tests, their results, the pictures, the walks and the verdict are kept where no part that builds the work reads them. The reason, from the rule that divides the two: "Would knowing this change how the builder writes code?"
- What a person meets, where, and the way back. A handoff plan says what a person meets that differs from the surface or the screen design, on which surface and screen and at which size, and what must be true again, as guidance, never code; it never names the test, its rule, its id, its tool or a figure measured. The reason: a handoff plan "never names the failure condition, its id or the check", and the builder gets no results.
- The builder only when it can fix it alone. A finding goes to the developer only when its way back is a change of the code the builder controls, from what it already has. One that needs judgment or authority the builder does not hold, such as a change of the design system, of the screen design, of a part the builder does not control, or of a surface's declaration, property or guideline, goes to the product owner. When in doubt, a person. The reason: the recovery rule's test, "Can the builder fix this from information it already has, deterministically?", and the product owner's approval with Test accessibility that "a finding about the design system's colours or the screen design goes to the product owner".
- In the testing environment. The tools run, and the person walks, on a copy in the testing environment that Environment setup declares, with its made-up data and its own test accounts, never in production and never on a builder's own machine. The reason: the product owner's list recorded it for security and performance tests, "in the testing environment Environment setup declares, never in production.", and he approved the same for the eval and for Test accessibility; a builder's machine "is not where the path's tests are counted".
- Only a person moves the yardstick. A fail is fixed, or a person confirms an update of the surface through Manage surfaces or of the screen design through Design the work; a finding is never let through any other way. The reason: for a surface, "A person confirms each update.", and for the design, "the technical lead confirms or changes each choice".
- Records are evidence, not run again. The record of the review of each change and the record of the build's separate test run are taken as evidence. The reason, from the product owner's approved list: "BI-4 takes the record of BI-3's separate test run as evidence and does not run the same tests again."
- Rounds have an end. When the same finding comes back after the rounds the project allows, it goes to a person, not round again to the builder. How many rounds is a project setting. The reason: the old slice check stopped "after 3 rejections on the same epic", and "Everything that can be turned on or off lives in settings."
- The project's memory first, then Garura memory, then Phoenix memory, then research through a memory update a person approves. What nothing answers stays open, with no default, and is named as not tested. The reason: research is new knowledge that nobody has checked yet, and the person's approval is the check.
