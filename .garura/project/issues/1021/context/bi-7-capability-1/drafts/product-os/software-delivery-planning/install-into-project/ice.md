## Intent
- Goal: A team puts Garura into its project in one step, through one install engine behind both front doors, the one-line command and the install play: the parts of the kind it chose are laid whole for its coding tool, with the version and every part laid kept in the project's install record, checked to run before the install counts, and with no file of the project's own written over; the team can update what the project gets as the project changes, and can take Garura out again from the record, keeping its work, its product model and its own files.
- Limit: Nothing of the project's own is written over, moved or deleted without the person's yes, on any install or take-out; Garura's version of a file the project already has goes beside it.
- Limit: Only what the install record says Garura laid is ever taken out, nothing is taken out before the person has seen the list, and the project's product model and its work are never changed.
- Limit: The install brings no memory, lays no stale or deprecated part and no part without what it needs to run, and names no coding tool in its own steps; each tool's shape is laid by that tool's own part.
- Limit: The engine stops and names what is missing, such as a version that does not exist or a tool that does not load; it never guesses and never falls back to something else.
- Fails if: After a first install, a file the project had before is changed, replaced or gone, or after a take-out, the team's work, its product model or one of its own files is gone.
- Fails if: The two front doors lay different parts for the same version and kind, or an install leaves no record of what it laid and its version.
- Fails if: An install counts as done while the memory tool or a tool it laid cannot run, or a laid part points to a file the install did not lay.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the files the project already has where Garura lays its parts, such as its instructions file for its coding tool and its own skills and agents; the install record and the version of an earlier install; the kind of install chosen and any named plays; that version's parts with their workers and shared files, and which are stale or deprecated; the coding tool the team uses; and what the memory tool's check and each tool's check report.
- Never read: any memory file by its path, and any ICE page.
- Persona: the product owner, who brings Garura into the project, chooses what it gets and can take it out again.
- Scope: In: installing in one step through the one engine, choosing the kind, checking what was laid, laying the guardrails, updating what the project gets, and taking Garura out. Out: moving to a new version, each coding tool's shape, setting the project up after the install, what a guardrail guards and the way past it, what each setting means, how the memory tool works, and where each part lives.

## Expectation
- Scenario: A team's clinic booking app already has its own instructions file for its coding tool and two skills of its own. From one command in the project's folder, Garura is laid in the full kind: Garura's instructions go beside the team's file, the two skills stay as they were, the memory tool and each tool pass their check, and the record names every part, the kind and the version. A month later the team takes Garura out: the list of what goes and what stays is shown first, and after the yes the project holds its code, its instructions file, its two skills, its work and its product model, as before.
- Done means: Someone other than the one who ran the install compares the project before the install, after it and after the take-out, and finds no file of the project's own changed or gone, every part laid named in the record with the version, each check passed, and the same parts laid by both front doors for the same version and kind.
