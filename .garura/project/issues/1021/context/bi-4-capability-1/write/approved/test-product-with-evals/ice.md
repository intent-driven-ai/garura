## Intent
- Goal: Each slice's eval runs on the built work with no agent, through its usage guide, in the testing environment, so that every goal, expectation and failure condition of its stories has a pass or a fail from an eval the builder never saw; each failure goes back as a handoff plan to the builder or to a person; and the evals run again as the product changes, so that nothing that passed breaks.
- Limit: Each step is done exactly as its step library says; there is no score, the eval passes only when every scenario of every story passes, and nothing that was not tested counts as a pass.
- Limit: Only the handoff plan reaches the builder, never the eval, the verdict, the hidden file or the evals folder; the run reads only the recovery parts of the hidden file, never its failure conditions.
- Limit: The code-level tests are not run again, the record of the build's separate check is the evidence for them, nothing runs in production, and nothing comes from what the AI agent knows by itself.
- Fails if: An eval is called passed while a scenario failed, ran past its time limit or did not run, or on a build whose evidence holds a flag for a read of the evals folder.
- Fails if: A handoff plan names a failure condition, its id, a scenario or the check, or one whose recovery says a person must decide went to the builder.
- Fails if: A scenario that passed before fails after a change and the verdict does not name it, or a failure goes round again to the builder after the rounds the project allows.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: each slice's eval files, the step library of its kind of surface, the eval rules, the slice's usage guide, the recovery parts of its hidden file, the build's evidence with its flag and the record of its separate check, the earlier verdicts, the testing environment the deployment design names, and the project's setting for rounds.
- Never read: the failure conditions of the hidden file, any ICE page, and the code the build made, which the eval reaches only through the usage guide.
- Persona: the product owner, who reads the verdict, trusts a pass only when the build never saw the eval, and decides each failure a person must decide; the developer gets back, as a handoff plan, each failure the builder can fix alone.
- Scope: In: running each slice's eval on the built work, matching its names through the usage guide, the verdict, the handoff plans, and running the evals again as the product changes. Out: writing the evals, the hidden file, the step libraries and the flag; the code-level tests, the code and the usage guide; fixing; the other kinds of testing and checking the code against its standards; making and running the plan; landing the change; and the environments.

## Expectation
- Scenario: A clinic's booking slice on a browser page is built, with its usage guide and no flag in the build's evidence. Its eval runs in the testing environment: every goal and expectation passes, but two patients can book the same slot when they book at once. The product owner sees the verdict with that one failure. Its recovery says the builder can fix it alone, so the developer gets a handoff plan: two patients can book the same 10:00 slot at the same time, and the second one must see that the slot is gone. After the fix, the whole eval runs again and passes, and so does the eval of the reminder slice that passed before.
- Done means: Someone other than the one who ran the evals runs them again on the same built work, gets the same verdicts, and finds every line of each story with a pass, a fail or a reason it was not tested, no failed, timed-out or untested line counted as a pass, the flag read before each pass, and no handoff plan that names a failure condition, its id or the check.
