# Phoenix memory stays up to date as Garura is built, and is versioned per release with its own release notes

Serves business intent #899 (the source, Phoenix memory and the projects stay in step). Filed with no parent: #899 is not shaped yet, and a business intent's children are only its epics. The model part (this feature under its capability, with its ICE) is owed.

## What is wanted

As Garura is built, Phoenix memory stays up to date with it. Phoenix memory is the shared memory every project's agents read through the memory tool (`intent-driven-ai/phoenix-memory`, kept on each machine at `~/.phoenix/core/memory`). A Garura project holds no standards of its own (its Garura memory tier is only its product model), so whatever Phoenix memory says is what its agents decide from. When a change to Garura changes a standard, a template, a rule or a schema, Phoenix memory gets the same change in the same release, and nothing is left behind.

Phoenix memory is also versioned per release. Each Phoenix memory release has a version that matches the Garura release it goes with, and its own release notes: what pages were added, changed or removed, and why.

## Why (found on 2026-10-28, #920)

Comparing Garura's source memory (`core/components/memory/`) with Phoenix memory:

- 49 pages differ, 7 are in the source only, and 16 are in Phoenix memory only.
- Pages the agents read still use names the naming rule (ADR 046) replaced, for example `standards/rules/pipeline-position.md` (`play-creator`, `review-change`, `/vision`, "drive") and the ADR template (`/adr`, `author-adr`, "drive").
- `loop-contract.md`, `naming.md`, `naming.yaml` and `rename-map.yaml` are not in Phoenix memory at all, so no agent finds them through the memory tool. Phoenix still holds the old `drive-contract.md`.
- Promotion today is a manual copy, commit and push into another repository, outside the change plays, with no record of which Garura change needed it.

The product owner, 2026-10-28: "as we are building garura, we need to keep updating phoenix memory too … this is a big intent: how we ensure phoenix memory is not stale as garura and other parts of phoenix are built". And: "the phoenix memory is kept up to date and memory needs versioning too, which goes per release and is its own release notes".

## Done when

- A change to Garura that changes a memory page also changes Phoenix memory, through the change plays, and the change is not done until both land.
- A check names every page where Phoenix memory and Garura's source disagree; a release does not go out with a gap nobody decided on.
- Phoenix memory has a version per release and release notes for each.
- The direction of each page (source to Phoenix, or Phoenix's own) is decided and written down, so a Phoenix-only page is not overwritten by mistake.
