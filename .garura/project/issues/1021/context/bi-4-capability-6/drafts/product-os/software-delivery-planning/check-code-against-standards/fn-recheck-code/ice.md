## Intent
- Goal: When a change is fixed after its review, more work is built, a defect is fixed, a standard changes by a confirmed update, or an approved decision raises a level, the change is reviewed again or the whole built work is checked again against every standard as it is now, each run kept as a new verdict that names every standard that passed before and fails now; and when the same finding comes back after the rounds the project allows, the next handoff plan goes to the product owner with each round's verdicts.
- Limit: Each run answers every standard as it is now, and never skips, switches off or loosens a check to reach a pass.
- Limit: Each verdict, with how and where each standard was checked, is kept beside the earlier ones and never written over.
- Limit: The number of rounds comes from the project's setting, and when each run starts is the plan's.
- Fails if: A standard that passed before fails after a change, and the verdict does not name it.
- Fails if: A standard was updated or a level raised, and the built work kept its earlier pass without being checked again.
- Fails if: The same finding went round again to the developer after the rounds the project allows, or an earlier verdict was written over.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: what changed in the code and why, the confirmed updates of each standard, the approved decisions on the levels, the standards and the levels as they are now, the earlier verdicts with how and where each standard was checked, the handoff plans, and the project's setting for rounds.
- Never read: the value of any secret, such as a password or a key; anything in production; and a plan's evals folder with the slice's hidden file.
- Persona: the product owner, who trusts that what passed before still passes, and decides a finding that keeps coming back.
- Scope: In: reviewing a change again after a fix, checking the whole built work again when more work is built, when a standard changes and when a level is raised, keeping each verdict, naming what passed before and fails now, and sending a finding that keeps coming back to a person. Out: fixing the code, updating a standard or moving a level, starting each run and the loop, and the first review, the whole-work check, the verdict and the handoff plans.

## Expectation
- Scenario: A team's release command passed its review. A later change adds a step that uploads the release notes, and its review finds the step logs the upload's key in plain words; the developer fixes it from the handoff plan, and the change is reviewed again and passes, with both verdicts kept. Later, a confirmed update of the architecture says every step must go through the command's one place for settings, and the whole built work is checked again: two older steps read their settings straight from the environment, so the verdict names them as broken by the change. A finding on one of them comes back after the rounds the project allows, so the next handoff plan goes to the product owner with every round's verdicts.
- Done means: Someone other than the one who ran the checks compares the verdicts of each round with the standards and the levels of the time, and finds every standard answered each time, each standard that passed before and fails now named, each earlier verdict kept, the updated standard and the raised level checked, and the finding sent to a person once the rounds the project allows were used up.
