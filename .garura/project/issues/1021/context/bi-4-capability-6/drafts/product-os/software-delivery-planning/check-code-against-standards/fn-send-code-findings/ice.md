## Intent
- Goal: Once a change is reviewed or the whole built work is checked, one verdict gives each standard touched a pass or a fail with how and where it was checked, names each standard not checked with its reason, says so plainly where there is nothing to check against, and follows one fixed rule over the findings, decided by a person or by that rule as the project's setting says, with a person's differing decision on record beside the rule's; and each finding goes back, in plain words for people and as a handoff plan with what is wrong, where and the way back: to the developer through Build the work test first when the builder can fix it alone, to the test writer when it is about a test, to the product owner when a person must decide, and to Fix defects test first when the work was already accepted.
- Limit: The same findings always give the same verdict, a standard that was not checked never makes a pass, and the merge is left to Ship every change the same way.
- Limit: A handoff plan never names the check, its rule, its id or its tool, and its way back is guidance, never code.
- Limit: A finding goes to the developer only when its way back is a change of the code the builder controls; one about a test goes to the test writer; one that changes the architecture, the deployment design, an environment, a standard or a level, or is in doubt, goes to the product owner.
- Limit: The verdict and the findings are kept where no part that builds the work reads them.
- Fails if: The verdict is a pass while a standard failed or was not checked, or nothing to check against is read as a pass.
- Fails if: A person's decision that differs from the rule's verdict is not on record with each finding it left open.
- Fails if: A handoff plan names a check, a rule, an id or a tool, or the builder was given the verdict or a finding about a test.
- Fails if: A finding that needs a person's judgment or authority, such as a change of the architecture, went to the developer.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the findings of the review of each change and the results of the check of the whole built work, each with its standard, where it was found and its rank; each standard not checked; the rank table in force and the profile's pass bars; the project's setting for who decides the review; the person's decision; what the builder controls; the owners of each standard; whether the work was already accepted; and the recovery rule.
- Never read: the value of any secret, such as a password or a key; anything in production; and a plan's evals folder with the slice's hidden file.
- Persona: the product owner, who reads the verdict, decides the review when the setting asks a person, and decides each finding a person must decide; the developer gets back, as a handoff plan, each finding the builder can fix alone, and its test writer each finding about a test.
- Scope: In: the one verdict for a change or for the whole built work, who decides it, the plain-words findings, and writing and sending each handoff plan. Out: reviewing and checking, merging, fixing, updating a standard or moving a level, recording a defect in the tracker, and reviewing again.

## Expectation
- Scenario: A shop's checkout service gets a change. Its review finds the order search joining what a shopper types into the database query, a finding of the rank that blocks, and a new test that asserts nothing; the project's type check could not run. The setting asks a person, and the product owner rejects the change. The verdict is not a pass, names the type check with its reason, and records both the rule's verdict and the person's. The developer gets a handoff plan: in the order search, what a shopper types reaches the database query, and the search must pass it as a value only. The test writer gets the one about the test. Neither names a check, a rule, an id or a tool.
- Done means: Someone other than the one who gave the verdict reads it beside the findings and the setting, and finds the rule's verdict and the decision on record with who made it, every standard with a pass, a fail or a reason it was not checked, no pass while a standard failed or was not checked, and each handoff plan with what is wrong, where and the way back, sent where the recovery rule's test says, with no check, rule, id or tool in it.
