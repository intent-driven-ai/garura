## Intent
- Goal: When a project moves to a new version, from either front door, every part Garura laid that the new version renamed or dropped is taken out, a part under an old name once its new name is laid and a part the new version no longer has through the same step a change of choice uses, each shown first and named in the report, so the project never holds an old name beside its new one, and a project with no install record gets one.
- Limit: A part is taken out only when the install record names it or its own file proves Garura laid it; a part the project wrote itself is never touched, even with an old Garura name.
- Limit: A renamed or dropped part that a person edited goes only on the person's yes.
- Limit: Nothing goes before it is on the list the person saw, and only paths inside the project are touched.
- Fails if: After the upgrade, a part Garura laid under an old name is still beside its new one, or a dropped part Garura laid still shows as a command, when the person did not choose to keep it.
- Fails if: A part or folder the project wrote itself is changed or gone.
- Fails if: A part went that was not on the list shown first or is not named in the report, or a project that had no record still has none.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the install record and the version the project has, or that it has none; the new version's parts and its rename map, with the names removed with no new name; the name line in each part's own file; and which parts a person edited.
- Never read: any memory file by its path, and any ICE page.
- Persona: the product owner, who moves the project to a new version and sees which parts go.
- Scope: In: taking out renamed and dropped parts on an upgrade, by the record or the proof in each file, in a project with or without a record, and writing the record. Out: showing the list and the report, a change of choice at the same version, settings that name a renamed part, taking all of Garura out, and the naming standard itself.

## Expectation
- Scenario: A team's planning tool was installed by the one-line command before the record existed. It holds the play that made plays under its old name, two old plays that both became the slice-shaping play, one play Garura dropped, and a folder of the team's own named like an old Garura play. On the upgrade, the list shows the three old-name parts and the dropped play to go. After the yes, only the new names are there, the dropped play is gone, the team's folder is as it was, the report names the four parts, and the record now exists.
- Done means: Someone other than the one who ran the upgrade lists the project's parts before and after against the rename map and the new version, and finds no old name beside its new one, no dropped part of Garura's left, every folder of the project's own as it was, and a record that names every part laid.
