## Intent
- Goal: A team moves its project to a new version of Garura through one run of the install engine, from either front door: it sees first the versions before and after, the notes of each release between them and the list of what changes in this project, and on the person's yes the project gets the new version, with the parts Garura laid that the new version renamed or dropped taken out, each installed part a person edited kept or replaced as the person chose, new settings brought in with every team value kept, the product model moved in its shape only and only on the person's yes, and the new version and every change kept in the install record and the report.
- Limit: Nothing a person changed, whether an installed part, a settings value or the team's instructions file, is replaced, moved or removed without the person's yes for it.
- Limit: The product model changes only in its shape (keys, file names, folders and headings), never in what it says, and only after the person has seen each change and said yes.
- Limit: Only what the install record names, or what a part's own file proves Garura laid, is replaced or taken out; the team's own parts, its work and its files are never candidates.
- Limit: A version that does not exist stops the upgrade with nothing changed, and a step that stops part way puts back what it changed; the engine names no coding tool in its own steps.
- Fails if: After an upgrade, a part, a settings value or a file a person changed is different, and no yes of the person's for it is on record.
- Fails if: A part the record or its own file shows Garura laid, which the new version renamed or dropped, is still in the project when the person did not choose to keep it; or the model's meaning changed, or its shape moved with no yes.
- Fails if: Something changed that the list shown first did not name, or the record or the report does not match what changed, or the new version is not recorded.

## Context
- Read: Gather it from the memory layer. Look first at the project's existing memory and its existing implementation, then Garura memory, then Phoenix memory. If none of them answers, research it and raise a memory update for a person to approve. For this part, look for: the install record and the version the project has; the version named and its release notes, with those of each release between; the new version's parts, its rename map and its settings; the installed parts a person changed since they were laid; the team's settings file and instructions file as they are; the shape the project's product model is in, and the moves to the new shape.
- Never read: any memory file by its path, and any ICE page.
- Persona: the product owner, who decides when the project moves to a new version, what happens to each part a person edited, and whether the model moves.
- Scope: In: the run over the earlier install, what is shown first and the yes, Garura's releases and their notes, taking out renamed and dropped parts, keeping a person's edits, bringing in new settings, the model's move, the record and the report. Out: the first install, the choice of parts at the same version, the take-out, each coding tool's shape, the set-up after the install, what each setting means, how Phoenix memory is versioned, and the model's shape itself.

## Expectation
- Scenario: A bank's payments service is on an older release. Its people edited one installed play to name their own tracker, set their own values in Garura's settings file, and their product model is in the earlier shape. The product owner runs the one command with the newest release. Shown first: the two versions, the notes of the release between, the parts to be added, replaced and taken out with two renamed ones among them, the edited play, three new settings, and the model's keys, files and headings to move. The product owner keeps the edited play and says yes to the rest. Afterwards the edited play is as it was and named in the report as not moved, every value of the team's is kept and the three new settings are there, no old name sits beside its new one, the model's pages say what they said, and the record holds the new version.
- Done means: Someone other than the one who ran the upgrade compares the project before and after with the list shown first and the report, and finds every change on the list and in the report, nothing a person changed altered without a yes on record, no part Garura renamed or dropped left in the project, the model's text unchanged apart from its keys, file names, folders and headings, and the new version in the record.
